概要資料

ui-design-grounding の使い方と仕組み

VERSION1.6.0DATE2026-11-16

ui-design-grounding は、AI コーディングエージェントに UI/UX の判断軸を持たせるスキル集です。この資料は、初めて使う開発者に向けて、導入から日々の使い方までを先に示し、その後でスキルが基準を外さずに動く仕組みを概略で説明します。

これは何か

ui-design-grounding は、UI の設計・実装・レビューで使う知識ベースです。アプリケーションではなく、Markdown で書いたスキル定義（エージェントが手順として読み込む指示書）とリファレンスでできています。

解決する課題

AI は UI のコードを書けます。しかし、その UI がなぜ使いやすいのか、どこを直すべきかを毎回同じ水準で判断するには、拠り所になる基準が要ります。ui-design-grounding は、次の判断をエージェントに持たせます。

判断の観点エージェントが確かめること
初見の分かりやすさ初めて見た人が、画面の目的を理解できるか
情報設計利用者が操作に迷わない構造になっているか
技術品質アクセシビリティとレスポンシブが破綻していないか
一貫性色・余白・タイポグラフィ・モーションがそろっているか
基準への準拠DESIGN.md に残した設計方針から外れていないか
追跡のしやすさ評価の結果を Markdown のレポートとして後から追えるか

スキルが守る方針

  • 主観的な良し悪しではなく、根拠と前提を示す。
  • 人が判断できるように、選択肢とトレードオフを出す。
  • 既存のコンポーネント・CSS・デザイントークンを尊重する。
  • いきなり大きく作り替えず、優先度に沿って段階的に直す。
  • 観察が要る評価では、実際の画面と操作の結果を根拠にする。

はじめの一歩

最初に /init-design で DESIGN.md を作ります。DESIGN.md は、プロジェクトの色・タイポグラフィ・余白・コンポーネントの方針を 1 つにまとめたファイルで、以降のすべてのスキルが判断の基準として読みます。どのスキルを使うか迷ったときは、/ui-help で一覧を出します。

やりたいことから選ぶ

やりたいこと使うスキル
デザインの基準（DESIGN.md）を作る/init-design
新しい UI を考える/design-ui
UI を実装する/implement-ui
既存の UI を良くしたいが、何が悪いかがはっきりしない/refine-ui
技術品質を監査する/audit-ui
UX と使いやすさを採点する/score-ui
初見で分かりにくい箇所を見つける/legibility-ui
外部サイトのデザインを分析する/scan-ui

迷ったときの選び方

上の行から順に当てはめ、最初に当てはまったスキルを使います。

#状況使うスキル
1DESIGN.md がまだ無い/init-design
2何を作るかを考える段階にある/design-ui
3実装したい/implement-ui
4問題がはっきりしない/refine-ui
5品質を測りたい/audit-ui か /score-ui
6初見で分かるかを見たい/legibility-ui
7直す観点がはっきりしている第 2 層のスキル（6 章）

典型的な使い方

よくある 4 つの場面では、スキルを次の順に使います。どの場面でも、コードを変えるスキルは、先に改善の提案を示して承認を得てから変更します（7 章）。

場面使う順ねらい
新しい UI を作る/init-design、/design-ui、/implement-ui、/audit-ui基準と設計方針を先に文書にし、それに沿って実装し、最後に技術品質を確かめる
既存の UI を直す/refine-ui、/audit-ui か /score-ui/refine-ui が問題の観点を診断し、/arrange-ui や /clarify-ui などへ修正を任せる
初見の分かりやすさを見直す/legibility-ui実装を読む前に画面だけを観察し、見た目から予想した意味と実際の挙動のずれを記録する
リリース前に確かめる/polish-ui、/score-ui空状態・エラー・hover・focus・loading などの細部を仕上げ、最後に UX を評価する

補足UI に閉じない実装では、/design-ui で作った機能設計を、プロジェクトの実装ワークフローへ設計の入力として渡します。/implement-ui は UI の部分だけを受け持ちます。

仕組みの全体像

ui-design-grounding は、ナレッジベース・コマンドスキル・DESIGN.md の 3 つが組み合わさって動きます。利用者が呼ぶのはコマンドスキルで、コマンドスキルが残りの 2 つを読んで判断し、結果を対象のプロジェクトへ書き出します。

部品置き場所役割
ナレッジベースskills/ui-design-grounding/（SKILL.md と reference/ の 23 件）UI/UX の原則と、スキルに共通の手順を持つ。利用者は直接呼ばない
コマンドスキルskills/<スキル名>/SKILL.md（23 件）利用者が呼ぶスラッシュコマンド。手順の最初に、必要なリファレンスを読み込む
DESIGN.md対象プロジェクトのルートプロジェクトに固有の視覚の基準。リファレンスより優先される
.design/対象プロジェクトのルートスキルが作る設計・実装計画・評価レポートの置き場所（8 章）

リファレンスの中身

23 件のリファレンスは、次の 6 つの領域に分かれます。各リファレンスの 1 行の説明は skills/ui-design-grounding/SKILL.md にあります。

領域リファレンス
ユーザビリティと認知usability.md・cognitive.md・information-arch.md・legibility.md
視覚color-system.md・typography.md・spatial-layout.md・motion-design.md
操作と品質interaction.md・accessibility.md・responsive-design.md・wording.md・anti-patterns.md
デザインシステムdesign-system.md・design-tokens.md・design-md-spec.md
進め方design-md-gate.md・change-gate.md・interview.md・design-artifacts.md・implementation.md
観察と出力playwright.md・ui-report.md

2 層のスキルと委譲

コマンドスキルは、役割で 2 つの層に分かれます。第 1 層は作業の入口で、第 2 層は 1 つの観点だけを直す実働のスキルです。第 1 層の /refine-ui と /implement-ui は、診断した結果に応じて第 2 層へ修正を任せます。

第 1 層：入口になるスキル

スキル役割
/init-designDESIGN.md を作り、更新する
/design-ui要件をインタビューで明確にし、UI の構造・画面遷移・状態を機能設計として残す
/implement-uiDESIGN.md と既存の実装に沿って UI を実装する
/refine-ui「読みにくい」「うるさい」などの曖昧な訴えを観点ごとに診断して直す
/audit-ui技術品質を 5 つの次元で監査する
/score-uiニールセンの 10 のヒューリスティクスで UX を採点する
/legibility-ui画面だけを見て、初見の分かりやすさを 7 つのレンズで監査する
/scan-ui外部サイトを分析し、デザインシステムを DESIGN.md として逆算する
/preview-uiDESIGN.md を preview.html に変換し、ブラウザで見た目を確かめる

第 2 層：観点ごとに直すスキル

観点スキル観点スキル
レイアウト・余白/arrange-uiパフォーマンス/optimize-ui
タイポグラフィ/typeset-ui印象を強める/boost-ui
色/recolor-ui印象を抑える/calm-ui
モーション/animate-ui簡素化/slim-ui
文言/clarify-uiコンポーネント・トークンの抽出/extract-ui
レスポンシブ/adapt-uiリリース前の仕上げ/polish-ui
堅牢性・エッジケース/guard-ui

委譲の流れ

  • オーケストレーター（/refine-ui と /implement-ui）は、利用者が承認した計画を第 2 層へ渡します。第 2 層は承認を取り直さずに修正します。承認を 2 回求めないためです。
  • 評価系のスキルは、見つけた問題ごとに、直すのに向く第 2 層のスキルを推奨の対応として書きます。その場で直さない P0・P1 の指摘は、プロジェクトのタスク管理へ登録します。タスク管理が無ければ、登録を提案します。
  • 直す観点が初めからはっきりしているときは、利用者が第 2 層のスキルを直接呼べます。

2 つのゲート

スキルの手順には、2 種類の関門（ゲート）が組み込まれています。DESIGN.md ゲートは、スキルが基準を読まずに作業すること、および修正の後に基準が取り残されることを防ぎます。変更承認ゲートは、スキルが利用者の承認なしにコードを変えることを防ぎます。コードを変えるスキルは、次の順に手順を進めます。

DESIGN.md ゲート

ゲート通る時点スキルがすること持つスキル
前段手順の最初DESIGN.md のトークンと設計指針を読み、リファレンスより優先する基準として扱う。DESIGN.md が無いときは /init-design を提案する。/design-ui と /implement-ui は提案で止めず、/init-design へ委譲して基準を先に作るDESIGN.md を作る側（init-design・scan-ui・extract-ui）を除くスキル
後段修正の後修正が DESIGN.md のトークンや規約を変えたかを判定し、変えていれば DESIGN.md の更新へ誘導する。色は /recolor-ui、ほかのトークンは /init-design へ誘導する値を実際に動かすスキル（第 2 層・recolor-ui・polish-ui）

第 1 層のスキルは前段ゲートだけを持ちます。値の確定を第 2 層へ任せるか、コードを変えないためです。

変更承認ゲート

コード・UI のファイル・DESIGN.md に書き込むスキルは、いきなり修正しません。スキルは、まず改善の提案を表で示し、利用者の承認を得ます。その後の工程は、変更の規模で分かれます。

次の条件のどれかに当てはまる変更は大規模、どれにも当てはまらない変更は小規模です。判定に迷うとき、スキルは大規模として扱います。

#大規模になる条件
1共通のコンポーネントに手を入れる、または複数の画面に波及する
22 つ以上の観点にまたがる（第 1 層が委譲する第 2 層のスキルが 2 件以上になる）
3レイアウトの再構成やコンポーネントの分割など、構造を変える

例外DESIGN.md のトークンだけを変えるときは、画面への波及があっても小規模として扱います。

承認スキルが承認とみなすのは、利用者の明示的な肯定だけです。無関係な返答や沈黙は承認とみなしません。利用者は提案の一部だけを承認できます。

省略利用者が「確認不要」「そのまま直して」のように承認が要らないことを依頼の中で明示したときだけ、スキルは承認待ちを省きます。

成果物の置き場所

スキルが作るファイルは、DESIGN.md を除いて、対象プロジェクトの .design/ にまとまります。DESIGN.md だけはルートに置きます。エージェントがルートの DESIGN.md を自動で読むことが、基準を共有する仕組みの要だからです。

project-root/
├── DESIGN.md
└── .design/
    ├── specs/yyyy-mm-dd-{name}.md
    ├── plans/yyyy-mm-dd-{name}.md
    ├── reports/yyyy-mm-dd-{name}.md
    ├── reports/yyyy-mm-dd-{name}/NN.png
    └── preview.html
パス中身作るスキル
DESIGN.md視覚の基準（デザイントークンと設計指針）init-design・scan-ui・recolor-ui
.design/specs/設計（機能設計と改善設計）。/implement-ui が読み込むので、コミットしておくdesign-ui・大規模の変更を扱うスキル
.design/plans/大規模の変更の実装計画大規模の変更を扱うスキル
.design/reports/評価レポートと、同じ名前のフォルダに入れたスクリーンショットaudit-ui・score-ui・legibility-ui
.design/preview.htmlDESIGN.md の見本帳preview-ui

評価レポート

評価レポートは、冒頭で結論と次の一手が分かり、その後に根拠と詳細を追える構成です。

スキル評価の枠組み冒頭の結論
/audit-uiアクセシビリティ・パフォーマンス・テーミング・レスポンシブ・アンチパターンの 5 次元（各 4 点、計 20 点）総合判定・合計スコア・P0/P1 の件数・次にやること
/score-uiニールセンの 10 のヒューリスティクス（各 4 点、計 40 点）とペルソナテスト評価帯・合計スコア・主要な UX リスク・次にやること
/legibility-ui見た目と機能の不一致・スコープの不整合など 7 つのレンズ総合判定・最も誤解されやすい画面と操作・次にやること

問題の一覧では、問題ごとに根拠・影響・推奨の対応（第 2 層のスキル）・スクリーンショットへのリンクを書きます。スクリーンショットへのリンクにより、レビューの後でも、何を見て何を根拠に判断したかを追えます。
