# スキルアーキテクチャ設計メモ（ADR）

このドキュメントは `ui-design-grounding` プラグインのスキル群を再編する際の設計判断と、その根拠を記録する。実装より前の「なぜそうするか」を残すことが目的。

最終更新: 2026-06-21

---

## 背景：このプラグインの成り立ちと目的

- **発端**: Claude Code でアプリを実装すると、デザインの観点が抜け落ち「動くがダサい」UI ができてしまう。
- **狙い**: アプリケーションエンジニアの感覚のままで、**ビジネスで通用する standard なレベルの UI** を作れるようにする。
- **方針**: Claude は実装自体は何でもできる。足りないのは判断軸。だから「**Claude にデザインを学ばせる**」方向でスキルプラグイン化した。

この成り立ちが、以降のすべての設計判断の前提になる。

---

## スキルの本質の再定義

スキルの価値は実行力**だけ**ではない（実装・修正はエージェントも本来できる）。スキルが上乗せするのは次の3つで、**その判断を効かせて実装・修正まで担いきる**：

1. **判断軸の注入** — 何を良しとするかの基準（＝ナレッジ）
2. **観点の網羅** — 見落としを防ぐチェックリスト
3. **意図の翻訳** — 「なんかうるさい」のような曖昧な訴えを、具体的なナレッジ適用に変換する入口

すなわちスキル群は「**Claude に良いデザイン判断を強制し、その判断を効かせて実装・修正まで完遂する、意図ベースのナレッジ・ルーター兼・実働オーケストレーター**」である。分割の善し悪しは「意図の解像度 × ナレッジ適用の確実性 × 保守コスト」で測る。

## 決定1：観点スキルは残す（統合しない）

### 検討した選択肢
- (A) 実行2軸（新規/修正）に集約し、観点はナレッジへ降格
- (B) 観点グループに中間集約
- (C) 観点スキルを残す

### 決定：C

### 根拠
観点スキルを残すのは、各観点が**独立した実働ユニット**だから。理由は3つ：

1. **関心の分離・保守** — 一観点＝一責務で修正手順を小さく保つ。`refine-ui` に全観点を詰めると巨大化し保守不能になる。
2. **直接入口** — 軸を自覚したユーザー（「タイポを直したい」）が最短で `typeset-ui` を呼べる。
3. **委譲先** — 第1層オーケストレーター（`implement`／`refine`）が観点ごとに呼び分ける実働の単位になる。

> 当初はこの決定の主根拠を「観点が独立して見えること自体が教育」としていたが、ユーザー確認により**本プラグインの価値は教育的可視化ではなく、判断軸を効かせて実装・修正を完遂すること**と確定した（`boost-ui` 等も「直す観点を見せる」ためでなく「その観点を実際に直す」ために在る）。よって根拠を実働ベースに差し替え、結論（残す）は維持する。

## 決定2：欠けているのは観点ではなく「実行軸」

現状の20スキルの問題は「分割しすぎ」ではなく、**実行軸（動詞）と観点軸（レンズ）という別次元を1平面に潰している**こと。`boost-ui` は「修正する（実行）」と「色・タイポを盛る（観点＋方向）」が癒着している。結果：

- **新規実装の入口が無い**（既存の調整系スキルはすべて「既存を直す」前提）。
- 観点を横断したいとき、複数スキルを個別に呼ぶ羽目になる。

### 決定：2層の入口に再編する

- **第1層（動詞・少数）＝5動詞**：`design-ui`（考える＝構造設計）/ `implement-ui`（作る＝新規実装）/ `refine-ui`（直す＝既存修正）/ `audit-ui`・`score-ui`（評価）/ `init-design`（基準化）。ユーザーはまずこの少数の動詞だけ覚えればよい。`scan-ui` は init-design の URL 版（基準化の入口）。
- **第2層（観点・実働ユニット）**：色・タイポ・レイアウト・モーション・文言・堅牢性・性能… 各観点を**実際に直す実働単位**。第1層から委譲され、軸を自覚したユーザーは直接も呼べる。`boost`/`calm`/`slim` のような主観の方向入口もここ。

`implement-ui` / `refine-ui` は、**観点スキルを呼び出す薄い実働オーケストレーター**にする。「作る」なら必要な観点を横断的に通し、「直す」なら**観点ベースで診断**（基準＝DESIGN.md からの逸脱観点を特定、複数可）して該当観点へ**委譲し、委譲先の実働ユニットが修正を完遂する**。これで「忘却対策（横断）」「実装・修正の完遂」「迷わなさ（少数の入口）」が同時に立つ。

#### implement-ui の名前問題
現 `implement-ui` は実態が「実装計画・構造翻訳」で、注意書きに「コードの最終決定は行わない」とある＝名前と実態が乖離。再編では `implement-ui` を**新規実装の第1層オーケストレーター**として再定義し、**計画で止めず実装まで担う**（計画自体はエージェント本来の能力＋ナレッジで足りる）。

## 決定5：design-ui を第1層「考える」に格上げ（init-design と直交）

> 番号は後付け。内容は決定2（第1層5動詞）を補強するため、文脈上ここ＝決定2 の直後に配置している（決定3・4 より前に読む想定）。

`design-ui`（構造設計）と `init-design`（視覚的憲法＝DESIGN.md 生成）は、"設計" という語を共有するため近接して見えるが、**直交する別レイヤー**である。

- `design-ui` = **構造の設計**（画面構成・遷移・情報設計・フロー）。機能/フロー単位で、成果物は PR や spec に載る一過性のもの。**DESIGN.md は書かない**。
- `init-design` / `scan-ui` = **視覚的憲法の定義**（トークン＋指針＝DESIGN.md）。リポジトリ全体・永続。

両者は統合しない。「設計＝DESIGN.md を書く」は "設計" を視覚基準側だけで読んだときの錯覚で、構造設計はそもそも DESIGN.md を書く行為ではない。

その上で `design-ui` を**第1層「考える」に格上げ**する（従来 第1層リストに無かった）。理由：このプラグインの読者はアプリエンジニアで、最も効くのは**コードを書く前に "デザイン観点で構造を考える" 瞬間**を独立した動詞として持つこと。これで第1層は「考える・作る・直す・評価する・基準化する」の5動詞に閉じ、ライフサイクル図の各ノードと一対一対応する。

`design-ui` は DESIGN.md を**制約として読む**（前段ゲート）が、書き換えはしない。

## 決定3：コンテキスト肥大による「観点の忘却」への構造的対策＝DESIGN.md の常駐化

### 問題
観点スキルは MANDATORY PREPARATION で自分の観点の reference しか読まない（例：`typeset-ui` は typography/a11y/spatial のみ）。結果「タイポは直したが色コントラストが壊れた」という**視野狭窄が構造的に起きる**。コンテキストが肥大するほど顕在化する。

### 2種類の記憶
- **スキル＝一過性の記憶**：呼んだときだけ効く。深い分析に向くが忘却する。
- **DESIGN.md＝永続の記憶**：ファイルとして残り毎回読まれる。結論を固定でき、忘却しない。

### 決定：観点スキルで「学び・分析」し、結論を DESIGN.md に「固定」する
- どの観点スキルを呼んでも、前段ゲート（→ `design-md-gate.md`）で DESIGN.md を読む。DESIGN.md に全観点の基準があれば、1観点スキルを呼んでも**全観点の基準が一度コンテキストに載る**＝視野狭窄を防ぐ。
- DESIGN.md が充実 → 忘却に強い。DESIGN.md が薄い → 忘却が顕在化。よって **DESIGN.md の整備促進と書き戻しが忘却対策の本丸**。
- 補強として、波及チェックを**二層**で入れる：**第2層（実働）＝最小の自己チェック**（自分の修正が DESIGN.md の他トークン水準を壊していないか）／**第1層オーケストレーター＝横断の波及判定**（委譲・修正後に他観点への波及を判定し、必要なら追加で別の第2層を呼ぶ）。深さは入口で変わる（直接呼び＝最小／オーケストレーター経由＝横断）。

### 逆説：DESIGN.md 常駐はトータルのコンテキストを"節約"する
DESIGN.md が無いと観点を効かせるたびに16個の reference を読む。あれば濃縮済みの結論を読むだけで済み、観点スキルを呼ぶ頻度自体が減る。DESIGN.md は「観点ナレッジをプロジェクト向けに蒸留・圧縮したキャッシュ」。

---

## 決定4：DESIGN.md は「結論だけ・2階建て・更新型」で肥大を防ぐ

DESIGN.md を全観点の常駐記憶にすると肥大化が懸念される。設計で小さく保つ：

1. **結論のみ。理由・汎用論は書かない**（理由は reference/ に委ねる）。「primary=oklch(...)」は書くが「なぜこの色か」は書かない。standard なプロジェクトで front matter 50〜100行＋散文50〜100行＝**150〜250行程度**（CLAUDE.md と同オーダー）。
2. **2階建て**：冒頭に10〜20行の**サマリ層**（全観点の見出しを一度に与える＝忘却防止はここが担う）、続いて**詳細層**（必要時に Read/Grep で取りに行く）。全量を毎回読む必要はない。
3. **書き戻しは「追記」でなく「更新」**：観点スキルを使うたびに新セクションを足すのでなく既存値を上書き・統合する。
4. **大規模化したらトークンを外出し**：`tokens.css` / `tokens.json` に分離し、DESIGN.md は「サマリ＋散文＋参照」に。
5. **重複が溜まったら `init-design` がスリム化（重複統合）**を担う。「大きくなった」は情報量でなく冗長の問題として扱う。

## 目指す全体像（ライフサイクル）

```
基準が無い → scan-ui / init-design で DESIGN.md（視覚憲法）を作る
   ↓
design-ui で構造を設計（画面・遷移・情報設計。DESIGN.md は制約として読む）
   ↓
implement-ui で実装（DESIGN.md に沿う／観点を横断的に通す）
   ↓
refine-ui で修正（DESIGN.md 準拠で診断し観点スキルへ委譲）
   ↓
audit-ui / score-ui で評価（DESIGN.md 準拠度も測る）
   ↓
polish-ui で仕上げ
```

DESIGN.md が全スキルの収束する「重力の中心」。育つほど観点スキルは準拠で足り、未熟なほど観点・方向スキルが手取り足取りを担う。

## 旧・未確定論点 → すべて決着（2026-06-21）

- `boost`/`calm` の扱い → **第2層の方向入口として残す**（決定1・2）。`refine-ui` から委譲もされ、直接も呼べる。独立スキルとして維持。
- `design-ui` と `init-design` の関係 → **直交・両方残す。design-ui は第1層へ格上げ**（決定5）。
- DESIGN.md ゲートとの整合 → **第1層オーケストレーターは前段のみ／後段は実働層（第2層・recolor・polish）のみ。`design-ui` に前段を追加**（→ `design-md-gate.md` 適用区分表を更新）。
- 波及チェックの粒度 → **二層**（決定3 を参照）。
- `refine-ui` の診断軸 → **観点ベース**（基準からの逸脱観点を特定、複数委譲可）。「うるささ」等の主観方向はその一分岐にすぎない。
