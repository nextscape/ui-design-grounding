# 変更承認ゲートと `.design/` 構造再編 設計仕様

- **日付**: 2026-09-26
- **対象**: 書き込みを伴うコマンドスキル全般（第1層 `refine-ui` / `implement-ui`、第2層 13 件）への承認ゲート導入、`design-ui` / 評価系の出力先変更、`.design/` 構造の再編
- **ステータス**: 設計レビュー待ち（承認後に実装計画を作成）

## 1. 背景・目的

スキルを使うと、改善点の提示とユーザーの承認を経ずにいきなりコードを修正してしまう場合がある。第1層・第2層を問わず起きている。

原因（現行スキルの調査結果）:

1. 第2層の実働スキルは「診断 → 改善の実施 → 検証」を直列に書いており、診断と実施の間に承認待ちの記述が無い
2. 即時修正を明文で指示している箇所がある
   - `skills/polish-ui/SKILL.md:35`「問題があれば即座に修正する」、`:30`「問題を発見次第、実際に修正する」
   - `skills/refine-ui/SKILL.md:79`「助言で止めず、自前修正または委譲で修正まで担う」
   - `skills/implement-ui/SKILL.md:97`「計画で止めず、実装まで担う」
3. 第1層から第2層へ委譲しても、どちらの層にもゲートが無いので、何段委譲しても承認の機会が生まれない
4. 既存のゲートは対象が違う。`design-ui` の合意ゲートは要件インタビュー用、`design-md-gate.md` の人間承認は DESIGN.md の値の更新用で、コード修正を止めるゲートは存在しない
5. ナレッジベースの出力ポリシー「判断や最終選択は、必ず人間に委ねる」（`skills/ui-design-grounding/SKILL.md`）は抽象原則のままで、各スキルの手順に落ちていない

目的: **改善点を提案し、ユーザーの承認を得てから変更に入る**ワークフローを全スキル共通の手順として定義する。変更の規模に応じて、大きければ「設計 → 実装計画 → 実装」、小さければ「実装計画 → 実装」の順に進める。

「スキルは教材ではなく実働であり、実装・修正まで完遂する」という既存方針は維持する。承認ゲートは作業を止めて助言で終わらせるものではなく、完遂の前に確認を挟むものとして位置づける。

## 2. 変更承認ゲート（`reference/change-gate.md` 新設）

`design-md-gate.md` と同じく共通プロトコルを1ファイルに定義し、対象スキルは MANDATORY PREPARATION で参照する。各スキル本文には「どこでゲートを通すか」だけを書き、ゲートの文言は重複させない。

### 2.1 フロー

```text
前段ゲート（DESIGN.md）→ 診断
→ ① 改善提案（変更点・対象・規模判定）→ 承認
   ├ 小: ② 実装計画 → 承認 → 実装 → 検証
   └ 大: ② 設計 → 承認 → ③ 実装計画 → 承認 → 実装 → 検証
→ 後段ゲート（DESIGN.md、実働層のみ）
```

- 承認回数は、小規模では2回（提案・計画）、大規模では3回（提案・設計・計画）。
- 小規模の実装計画は会話内で提示し、ファイルには残さない。
- 大規模の設計は `.design/specs/`、実装計画は `.design/plans/` にファイルとして保存し、会話ではその要約とパスを示して承認を求める。

### 2.2 改善提案の形式

提案には次を含める。

| 項目 | 内容 |
|---|---|
| 診断結果 | 何が問題か（根拠: DESIGN.md・リファレンス・観察結果） |
| 変更点 | 番号付きの一覧。1項目 = 1つの改善 |
| 対象 | 変更するファイル・画面・コンポーネント |
| 観点 / 委譲先 | 該当する観点と、委譲する場合は第2層スキル名 |
| 規模判定 | 小 / 大 と、判定理由（2.3 のどの条件に該当したか） |
| 次の工程 | 承認後に何を出すか（小: 実装計画、大: 設計） |

ユーザーは項目の一部だけを承認できる（例:「1 と 3 だけ進めて」）。規模判定もユーザーが上書きできる。

### 2.3 規模判定

次のいずれかに当てはまれば **大**、当てはまらなければ **小**。

1. 共通コンポーネントに手を入れる、または複数画面に波及する
2. 2つ以上の観点にまたがる（第2層への委譲が2件以上になる）
3. レイアウトの再構成・コンポーネント分割など、構造を変える

- **DESIGN.md のトークン変更のみ**の場合は、画面への波及があっても **小** とする。トークン変更と他の変更が混在する場合は、トークン以外の変更だけで判定する。
- 判定に迷う場合は大として扱い、提案の中でその旨を示す。

### 2.4 承認の扱い

- **承認とみなすのは、ユーザーの明示的な肯定だけ**。無関係な返答や沈黙を承認とみなさない。
- 修正の要望があれば、その工程の成果物（提案・設計・計画）を直して再提示する。
- 実装中に承認済みの範囲を超える変更が必要になったら、手を止めて差分を提案し、承認を得てから進める（スコープクリープの防止）。

### 2.5 ゲートの省略

ユーザーが依頼の中で「確認不要」「そのまま直して」などと明示した場合に限り、承認待ちを省略できる。

- 省略は、その依頼の範囲だけに有効とする。
- 省略しても、改善提案と実装計画は短く提示してから実装する（何をしたかの記録を残すため）。
- 大規模の場合は、省略しても設計と計画のファイルは保存する。

## 3. 層ごとの責務と委譲時の受け渡し

**ゲートは入口のスキルが持つ。**

| 呼ばれ方 | ゲートを実行するスキル | 委譲先の動作 |
|---|---|---|
| 第1層（`refine-ui` / `implement-ui`）から開始 | 第1層 | 承認済みの計画を受け取り、ゲートを省略して実行する |
| 第2層を直接呼ぶ | 第2層 | — |
| 評価系の推奨アクションから第2層へ進む | 第2層（直接呼びと同じ） | — |

- 第1層は委譲時に「承認済み実装計画の該当タスク」を明示して渡す。第2層は、受け取った計画があるかどうかで、ゲートを実行するか省略するかを切り替える。
- 委譲先が計画の範囲外の変更が必要だと判断した場合は、2.4 に従って手を止め、第1層経由でユーザーに提案する。

### 3.1 `design-ui` / `implement-ui` との接続

- `design-ui` の成果物（機能設計）は、2.1 の「設計」工程に当たる。インタビューの合意ゲートに加えて、保存した設計の承認を得る。
- `implement-ui` は、該当する設計（`.design/specs/`）があれば「設計承認済み」とみなし、実装計画から始める。
- 設計が無く、規模が大きい場合は、`design-ui` へ委譲して設計を作ってから復帰する。小さい場合は、実装計画から始める。
- 新規実装では「改善提案」を「実装方針の提案」と読み替える（診断対象が既存 UI ではなく要件になるため）。

## 4. `.design/` 構造の再編

```text
project-root/
├── DESIGN.md                                ← 視覚的憲法（ルート常駐、変更なし）
└── .design/
    ├── specs/yyyy-mm-dd-{name}.md           ← 設計（機能設計 / 改善設計）
    ├── plans/yyyy-mm-dd-{name}.md           ← 大規模の実装計画
    ├── reports/yyyy-mm-dd-{name}.md         ← 評価レポート
    ├── reports/yyyy-mm-dd-{name}/NN.png     ← そのレポートのスクリーンショット
    └── preview.html                         ← DESIGN.md の見本帳（変更なし）
```

### 4.1 命名

- `yyyy-mm-dd` は実行環境のローカル日付。
- `{name}` は小文字ハイフン区切りの短い名前。
  - specs / plans: 機能・画面・改善内容から導く（例: `2026-09-26-settings-page.md`）。同じ作業の spec と plan は同じ `{name}` にする。
  - reports: `{skill}-{対象}`（例: `2026-09-26-audit-ui-settings-page.md`）。
- 同名のファイルが既にあれば末尾に `-2`, `-3` を付け、上書きしない。
- スクリーンショットはレポートと同名のフォルダに `01.png` から連番で置き、レポートからは相対パス（`yyyy-mm-dd-{name}/01.png`）でリンクする。
- 現行の日付フォルダ（`reports/YYYY-MM-DD/`）と `HHmmss` 接頭辞は廃止する。

### 4.2 specs のテンプレート（2種）

| 種別 | 作るスキル | 内容 |
|---|---|---|
| 機能設計 | `design-ui` | 現行の FEATURE_DESIGN.md テンプレートを移行（課題・解決・体験原則・画面構成…要確認事項） |
| 改善設計 | `refine-ui` と大規模判定時の第2層 | 背景と診断結果 / 変更方針 / 影響範囲 / 検討した代替案 / スコープ外 / 検証方法 / 要確認事項 |

どちらも冒頭で種別を明示し、`implement-ui` や第2層が入力として読めるようにする。

### 4.3 plans のテンプレート

- 参照する設計（`specs/` のパス）
- タスク一覧（1タスク = 対象ファイル・変更内容・観点・委譲先）
- 実行順と依存関係
- 検証方法（観察手順・確認観点）

小規模の実装計画も、会話内で同じ項目を簡略に示す。

### 4.4 旧構造との互換

- `implement-ui` は旧パス `.design/<feature-slug>/FEATURE_DESIGN.md` も読む（新パスに無い場合のフォールバック）。
- 既存ファイルを自動で移動・改名はしない。旧構造を見つけたら、移行を提案するにとどめる。

### 4.5 リファレンスの再編

`.design/` の構造と specs / plans のテンプレートを1か所にまとめるため、`feature-design.md` を **`design-artifacts.md`** に改名・拡張する。

| リファレンス | 担当 |
|---|---|
| `change-gate.md`（新設） | 承認ゲートの手順・規模判定・提案の形式・省略条件・層ごとの責務 |
| `design-artifacts.md`（`feature-design.md` を改名） | `.design/` 構造・命名・specs テンプレート2種・plans テンプレート・DESIGN.md への昇格導線 |
| `ui-report.md`（改訂） | レポートの保存先を新構造へ変更。フォローアップの文言を承認ゲートと整合させる |

各スキルの description（フロントマター）で「修正する」「実装する」と言い切っている箇所は、トリガの精度を落とさない範囲で「提案し、承認後に修正する」趣旨を加える。

- `skills/ui-design-grounding/SKILL.md`: 出力ポリシーに「変更は提案と承認を経てから行う（`change-gate.md`）」を追加。参照ナビゲーションに `change-gate.md` と `design-artifacts.md` を追加・改名
- `design-md-gate.md`: フロー上の位置関係（前段ゲート → 変更承認ゲート → 実装 → 後段ゲート）を追記
- `playwright.md`: スクリーンショットの保存先を新構造へ
- `README.md` / `AGENTS.md` / `ui-help`: `.design/` 構造・ワークフロー・リファレンス一覧を更新
- `.claude-plugin/plugin.json` / `CHANGELOG.md`: バージョンを 1.7.0 に上げる（出力パスが変わる破壊的な変更を含むため、CHANGELOG に移行の注意を明記）

## 6. 検討した代替案

| 案 | 採否 | 理由 |
|---|---|---|
| 小規模は提案と計画を1回の承認にまとめる | 不採用 | 提案段階で範囲を絞ってから計画に進むほうが手戻りが少ない（ユーザー判断） |
| 大規模は提案と設計をまとめて2回にする | 不採用 | 規模判定と方向性を先に合意してから設計を書くほうが手戻りが少ない（ユーザー判断） |
| 小規模の計画もファイルに残す | 不採用 | 数行の修正ごとに plans が増えて探しにくくなる |
| スクリーンショットを `reports/screenshots/` に集約 | 不採用 | レポート単位で管理・削除しやすいレポートごとのフォルダを採る |
| 各スキルにゲートの文言を直接書く | 不採用 | 23 スキルで文言が分散する。`design-md-gate.md` と同じ共通参照方式に揃える |

## 7. スコープ外

- 評価系スキルに修正機能を持たせること（評価は引き続き実装を変更しない）
- ユーザープロジェクトの旧 `.design/` 構造を自動で移行すること
- 本プラグイン外の実装プロセス（プロジェクト固有のワークフロー）への介入

## 8. 検証方法

ビルド・テストが無いため、次で確認する。

- 対象の全 SKILL.md で、手順の中に変更承認ゲートがあること、または対象外であることを明示していることを grep で確認する
- 即時修正の文言（「即座に修正」「止めず」など）が残っていないことを grep で確認する
- 旧パス（`.design/<feature-slug>/`、`reports/YYYY-MM-DD/`、`HHmmss`）が互換の記述以外に残っていないことを確認する
- 代表的なシナリオ（第2層の直接呼び・小規模／`refine-ui` から複数委譲・大規模／`design-ui` → `implement-ui`／ゲート省略指示あり）について、各スキルの手順を追って承認の回数と成果物の置き場所が設計どおりになるかを机上で確認する
