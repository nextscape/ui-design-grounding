# legibility-ui 統合 設計仕様

- **日付**: 2026-07-05
- **対象**: 別プロジェクトで作成された `legibility-ui` スキルを `ui-design-grounding` プラグインへ移植・統合する
- **ステータス**: 設計合意済み（実装計画はこの後 writing-plans で作成）

## 1. 背景・目的

`legibility-ui` は別プロジェクトで作成された、初見のユーザー視点で画面の分かりやすさを監査するスキル。人間が実際に画面を見て初めて気づけるような不具合（見た目と機能の不一致、目的の不透明さ、重複表示、画面間の不一致など）を検出できる実績があり、これを `ui-design-grounding` プラグインに取り込む。

移植元は特定プロジェクト（React ルーター構成・`start-app` スキル・固定スクリーンショットパス等）に依存した記述を含むため、汎用プラグインとして成立させるための一般化と、既存20スキルとのアーキテクチャ整合が必要。

## 2. 位置づけ

`score-ui`（UXヒューリスティクス評価）・`audit-ui`（技術品質監査）と並ぶ**第3の評価系コマンドスキル**として `/legibility-ui` を新設する。既存スキルへの混ぜ込みは行わない。

**既存評価系との違い**:

| スキル | 評価軸 | 手法 |
|---|---|---|
| `score-ui` | ニールセン10ヒューリスティクス | 実装を読んでから評価 |
| `audit-ui` | 技術品質5軸（a11y/性能/トークン/レスポンシブ/アンチパターン） | 実装を読んでから評価 |
| `legibility-ui`（新設） | 初見の理解可能性（5レンズ） | **実装を読まず画面だけを見て判断 → 最後にコードは裏付けのみ** |

観察順序（コードを読まない）そのものが手法の核であり、他スキルと混在させると制約が薄まるため独立させる。

## 3. ファイル構成

```
skills/
  legibility-ui/
    SKILL.md                          ← 手順のみ（既存パターンに揃える）
  ui-design-grounding/
    reference/
      legibility.md                   ← 5レンズの判断基準（移植元 reference/perspectives.md を移設・一般化）
```

既存20スキルと同じく、`legibility-ui/SKILL.md` は `ui-design-grounding` を MANDATORY PREPARATION として呼び出し、リファレンスを参照する構造に統一する（移植元の自己完結型 `reference/` は廃止）。

## 4. SKILL.md 内容

### 4.1 front matter

- `name: legibility-ui`
- `description`: 移植元の内容を踏襲（5レンズのトリガ例を含む）
- `user-invocable: true`
- `argument-hint: "[対象画面 (画面名／機能横断／省略で全画面)]"`

### 4.2 MANDATORY PREPARATION

`ui-design-grounding` スキルを呼び出し、以下を読み込む:

- `ui-design-grounding/reference/legibility.md` — 5レンズの判断基準・重篤度・出力フォーマット
- `ui-design-grounding/reference/design-md-gate.md` — DESIGN.md ゲート（前段）の手順

### 4.3 Phase 0 — 対象確定 + 基準の確認

**対象確定**（移植元の3分岐を維持）:
- 画面名の指定 → 指定画面のみを対象にする
- 「機能横断」「一連の流れ」等の指定 → 関連する画面をまとめて対象化する
- 指定なし／「全画面」 → 一般的なルーター定義パターン（React Router / Next.js の `app/` ディレクトリ / Vue Router 等）を Glob/Grep で探索し画面一覧を推定する。**見つからなければユーザーに主要画面を確認する**（移植元の `packages/web/src/router.tsx` 決め打ちを廃止し、プロジェクト非依存にする）
- 対象が2画面以上ならレンズ⑤（画面間一貫性）も実施する

**基準の確認（DESIGN.md 前段ゲート、新規追加）**:
`design-md-gate.md` の前段ゲートを実施する。DESIGN.md があれば front matter のトークンと本文の指針を基準として読み込み、レンズ⑤（画面間一貫性）で「意図的な差異の正当性」を判定する材料にする。無ければ未整備として扱い `/init-design` を提案する。評価専用のため後段ゲートは不要（score-ui/audit-uiと同じ扱い）。

**準備**:
- Playwright（`mcp__plugin_playwright_playwright__*`）が使えることを確認する。**アプリが起動していなければ、プロジェクトにアプリ起動用のスキルがあればそれを使う。なければユーザーに起動方法を確認する**（移植元の `start-app` 固定依存を廃止）。
- この時点でも対象コンポーネントのソースは読まない。
- スクリーンショットは、プロジェクトの一時ファイル置き場の慣例（`.gitignore` が定める一時ディレクトリ等）に保存する。無ければ妥当な一時ディレクトリを使う（移植元の `.screenshots/legibility-ui/` 固定パスを廃止）。

### 4.4 Phase 1 — 素朴初見監査（画面ごと・コードを読まずに実施）

移植元の手順を維持しつつ、**視覚判定と機能判定でPlaywright操作手段を使い分ける**（トークン効率化、新規追加の指針）:

- **視覚判定**（レンズ①見た目と機能の不一致、④重複・冗長表示、⑤画面間一貫性の一部）: `browser_take_screenshot` を使う。見た目の重み・境界線の連結・不揃い・重複表示の判定にはレンダリング結果そのものが必要なため。
- **機能判定**（レンズ②目的の不透明さ、③スコープ不整合）: `browser_snapshot`（アクセシビリティツリーのテキスト表現）で要素の存在・状態遷移を確認すれば足りる。画像取得は不要。

手順自体（要素を見て予想→操作して実際の挙動を確認→ギャップを記録、影響範囲確認、重複洗い出し、同種コンポーネントのサイズ比較）は移植元を踏襲する。

### 4.5 Phase 2 — 横断一貫性監査（対象2画面以上のときのみ）

移植元を踏襲。DESIGN.md が読み込まれていれば、パターン差異の正当性判定にそれを使う。

### 4.6 Phase 3 — コード特定

移植元を踏襲（プロジェクト固有記述なし）。

### 4.7 Phase 4 — 出力

`reference/legibility.md` の出力フォーマットに従う（移植元を踏襲）。レンズ別指摘一覧・重篤度・推奨アクションを他スキル（score-ui/audit-ui）と同じ「優先度順アクションリスト」形式で出す。

## 5. reference/legibility.md（旧 perspectives.md）

移植元 `reference/perspectives.md` の内容（5レンズの定義・判断基準・典型例・判断が割れやすいケース・対象外の観点・重篤度定義・出力フォーマット・推奨アクションマッピング）をそのまま移設する。プロジェクト固有の記述は含まれていないため、内容の書き換えは不要。

## 6. 全体ドキュメントへの反映

- `.claude-plugin/plugin.json`: `version` を `1.2.1` → `1.3.0` に、`description` の「22件のコマンドスキル」→「23件のコマンドスキル」に更新
- `skills/ui-design-grounding/SKILL.md`: コマンドスキル一覧表に評価系として「初見の分かりやすさ監査 | `/legibility-ui`」を追加
- `skills/ui-help/SKILL.md`: 第1層の評価カテゴリ（`/audit-ui` `/score-ui` の並び）に `/legibility-ui` の行を追加。「典型的なワークフロー」「迷ったら」にも軽く反映（例: 「初見での分かりやすさを確認したい」→ `/legibility-ui`）
- `CLAUDE.md`（プロジェクトルート）: コマンドスキル早見表に1行追加

## 7. スコープ外（YAGNI）

- Playwright が使えない環境向けのフォールバック（WebFetch・静的解析等）は用意しない。本スキルの本質はレンダリング結果の実見であり、代替手段は判定精度を大きく損なうため。使えない場合はその旨を出力して終了する。
- スクリーンショット画像の自動比較・差分検出ツールの導入。人間相当の目視判断に留める。
- 対象確定のルーター探索ロジックの高度化（モノレポ横断、動的ルート解決等）。見つからなければユーザーに確認するフォールバックで十分とする。

## 8. 受け入れ基準

- `/legibility-ui` を画面指定なしで実行した場合、一般的なルーター定義が見つかればそこから画面一覧を推定し、見つからなければユーザーに確認を挟んでから Phase 1 に進む。
- DESIGN.md が存在するプロジェクトでは、レンズ⑤の判定時に DESIGN.md の指針が参照される。
- レンズ①④⑤の指摘にはスクリーンショットに基づく視覚的根拠が、②③の指摘には操作結果（snapshot）に基づく根拠が伴う。
- 出力に `ui-design-grounding` プラグイン内の他スキルへの推奨アクション（優先度順）が含まれる。
- `ui-help` 実行時に `/legibility-ui` が一覧に表示される。
