## このドキュメントの役割
UI/UX設計と実装における色の判断基準を整理し、
**色の意味・状態・階層・アクセシビリティ**を一貫して扱うための基準を提供する。

文脈・制約・ブランド方針と組み合わせて参照する。

## 色設計の目的

- **意味の共有**：色が示す状態・優先度・意図を明確にする
- **一貫性**：画面や機能を跨いで同じ意味を同じ色で表現する
- **可読性**：背景と文字・アイコンの関係を崩さない
- **可視性**：重要な情報や操作が埋もれないようにする
- **拡張性**：テーマやブランド変更に耐える構造を作る
- **知覚的均一性**：人間の目に等しく見える色差を保つ

## モダンCSSカラー関数

### OKLCH（推奨アプローチ）

OKLCHは**知覚的に均一な色空間**であり、色の設計・管理に最適である。

**構文：**
```css
color: oklch(L C H);
/* L: 明度 (0%〜100%), C: 彩度 (0〜0.4程度), H: 色相 (0〜360) */
```

**OKLCHを推奨する理由：**
- 明度の値を変えても色相がずれない（HSLでは明度変更時に色相シフトが起きる）
- 彩度の調整が直感的で、パレット生成が容易
- ダークモード対応時、明度チャンネルだけを操作すれば良い

**明度と彩度の関係（重要）：**
- 白に近づく（明度が高い）ほど、彩度を下げる
- 黒に近づく（明度が低い）ほど、彩度を下げる
- 最も鮮やかに見えるのは中間明度帯（L: 55%〜75%程度）
- この原則を無視すると、不自然に浮いた色やくすんだ色が生まれる

### color-mix()

2つの色を指定比率で混合する関数である。

```css
color: color-mix(in oklch, var(--color-primary) 70%, white);
```

**活用場面：**
- ホバー・アクティブ状態のバリエーション生成
- パレット間のグラデーション生成
- OKLCHカラースペースと組み合わせることで知覚的に均一な混合が可能

### light-dark()

ライトモード・ダークモードの値を一箇所で定義する関数である。

```css
:root {
  color-scheme: light dark;
}
color: light-dark(oklch(25% 0 0), oklch(90% 0 0));
```

**活用場面：**
- セマンティックトークンのテーマ切り替え定義
- `prefers-color-scheme` メディアクエリの簡略化

## 色の構造（レイヤーと役割）

### 1. 基本レイヤー（Surface / Text / Border）

- **Surface**：背景・面を表す色
- **Text**：文字情報の可読性を担保する色
- **Border**：区切り・境界・構造を伝える色

**判断基準：**
- Surface と Text は必ず十分なコントラストを確保する
- Border は情報の区切りに必要な最小限の強さに留める

**ティンテッドニュートラルの原則：**

ピュアグレー（彩度ゼロ）はUIを無機質で冷たく見せる。
Surfaceレイヤーのすべてのニュートラルカラーには、ブランドカラーの色相を彩度 ~0.01 で加える。

```css
/* ピュアグレー（避ける） */
--surface-base: oklch(98% 0 0);

/* ティンテッドニュートラル（推奨） */
--surface-base: oklch(98% 0.01 250);  /* ブランドの色相250を微量追加 */
```

**ティンテッドニュートラルの効果：**
- 視覚的な温かみと統一感を生む
- ブランドカラーとの自然な調和を実現する
- 彩度 0.01〜0.015 程度が適切（これを超えると色付きが目立ちすぎる）
- すべてのニュートラルに同じ色相を使うことで一貫性を保つ

### 2. 意味レイヤー（Semantic / State）

- **Action**：主要操作、注意を引く要素
- **State**：成功・注意・警告・エラーなど状態の表現
- **Feedback**：hover / active / disabled / focus など動作の表現

**判断基準：**
- 状態色は「意味の一貫性」を優先し、装飾に流用しない
- hover / active などは `color-mix()` で明度差を作ると効率的かつ一貫性が保てる
- セマンティックトークンとして定義し、ダークモードではこのレイヤーのみ再定義する

```css
/* color-mix() によるステートバリエーション */
--action-primary: oklch(55% 0.2 250);
--action-primary-hover: color-mix(in oklch, var(--action-primary) 85%, white);
--action-primary-active: color-mix(in oklch, var(--action-primary) 85%, black);
```

### 3. 階層レイヤー（Hierarchy / Emphasis）

- **Primary**：最も重要な情報・操作
- **Secondary**：補助的な情報・操作
- **Muted**：背景的な情報・補助表示

**判断基準：**
- 強調は「色だけ」に依存しない（サイズ・配置も併用する）
- Primary が多すぎると優先度が崩れる

**60-30-10 ルール：**

画面全体の色の配分バランスを維持するための指針である。

- **60%：ニュートラルカラー**（Surface、背景、余白）
- **30%：セカンダリカラー**（カード、セクション背景、補助テキスト）
- **10%：アクセントカラー**（CTA、アクティブ状態、重要な強調）

この比率を大きく逸脱すると、視覚的なノイズや階層の崩壊が起きる。
特にアクセントカラーが10%を超えると、強調の意味が薄れる。

## 色の使い分け指針

### 意味がある色（Semantic）を優先する

- 色は「値」ではなく「意味」で管理する（トークン化）
- 例：`color.text.primary` / `color.action.primary` / `color.state.error`

### 目立たせたいから色を変える、を避ける

- 色は意味付けの道具であり、装飾目的で乱用しない
- 強調が必要な場合は、まず「情報階層の再設計」を検討する

### 状態色の整合性

- 同じ状態は同じ色で表現する（成功=緑、警告=黄、エラー=赤 など）
- ただしブランド方針がある場合はそれに従う
- 「警告」と「エラー」を混同しない（強度を分ける）

### アルファ透明度の扱い

アルファ透明度（rgba の a や oklch の / alpha）を多用するのは**パレットが不完全であるサイン**である。

**透明度が適切な場面：**
- オーバーレイ（モーダル背景）
- フォーカスリング
- スケルトンスクリーン

**透明度で代替すべきでない場面：**
- ホバー状態の色差（→ 専用トークンを定義する）
- ボーダーの色（→ Surface との組み合わせで明示的に定義する）
- テキストの薄い表現（→ `text.muted` トークンを定義する）

透明度を3箇所以上使っている場合は、パレットの見直しを検討する。

## ダークモード設計

ダークモードは**ライトモードの色を反転させたものではない**。
独立した設計思想に基づく、もう一つのカラーシステムである。

### 基本原則

**1. 純粋な黒を使わない**

`#000000`（oklch 0%）は目に負担がかかり、コントラストが過剰になる。
背景色は oklch 12%〜18% の範囲を基準にする。

```css
/* 避ける */
--surface-base-dark: oklch(0% 0 0);     /* 純黒 */

/* 推奨 */
--surface-base-dark: oklch(15% 0.01 250); /* ティンテッドダーク */
```

**2. 深度の表現にはサーフェスの明度を使う**

ライトモードでは影（box-shadow）で深度を表現するが、
ダークモードでは影が見えにくいため、**面の明度を上げることで深度を表現する**。

```css
/* ダークモードの深度表現 */
--surface-base:     oklch(15% 0.01 250);  /* 最背面 */
--surface-elevated: oklch(20% 0.01 250);  /* 浮いた面 */
--surface-overlay:  oklch(25% 0.01 250);  /* モーダル・ドロワー */
```

**3. アクセントカラーを少し彩度を落とす**

暗い背景上では高彩度の色がギラつく。
ダークモードのアクセントカラーは、ライトモードより彩度を 10〜20% 落とす。

```css
/* ライトモード */
--action-primary: oklch(55% 0.22 250);

/* ダークモード（彩度を下げる） */
--action-primary: oklch(70% 0.18 250);
```

**4. テキストのウェイトを少し軽くする**

暗い背景上の明るいテキストは、同じウェイトでもライトモードより太く見える（ハレーション効果）。
ダークモードでは `font-weight` を 1段階下げることを検討する。

**5. セマンティックトークンレイヤーのみ再定義する**

ダークモード対応時にプリミティブトークンを変更してはいけない。
セマンティックトークンのマッピングを切り替えることでテーマを実現する。

```css
/* プリミティブ（テーマで変更しない） */
--blue-500: oklch(55% 0.22 250);
--gray-100: oklch(95% 0.01 250);
--gray-900: oklch(15% 0.01 250);

/* セマンティック（テーマで切り替える） */
:root {
  color-scheme: light dark;
  --color-text-primary: light-dark(var(--gray-900), var(--gray-100));
  --color-surface-base: light-dark(var(--gray-100), var(--gray-900));
}
```

### ダークモード設計のチェックリスト

- [ ] 背景色は oklch 12%〜18% の範囲である（純黒ではない）
- [ ] ニュートラルにティンテッドカラーが使われている
- [ ] 深度は面の明度差で表現している（影だけに頼っていない）
- [ ] アクセントカラーの彩度がライトモードより低い
- [ ] テキストのコントラスト比は 4.5:1 以上だが 15:1 を大きく超えない
- [ ] セマンティックトークンの再定義で対応している（プリミティブは変更していない）

## トークン設計との関係

### トークンの階層構造

**1. プリミティブトークン（値の集合）**

色の実値を定義する。テーマで変更しない。

```css
--blue-500: oklch(55% 0.22 250);
--blue-600: oklch(48% 0.22 250);
--red-500: oklch(55% 0.22 25);
--gray-100: oklch(95% 0.01 250);  /* ティンテッドニュートラル */
--gray-900: oklch(15% 0.01 250);
```

**2. セマンティックトークン（意味・役割）**

UIの役割を表す。テーマ切り替えはこのレイヤーで行う。

```css
--color-text-primary: var(--gray-900);
--color-surface-base: var(--gray-100);
--color-action-primary: var(--blue-500);
--color-state-error: var(--red-500);
```

### 推奨トークンのカテゴリ

- **text**：primary / secondary / muted / inverse
- **surface**：base / elevated / overlay
- **border**：default / strong / subtle
- **action**：primary / secondary / ghost
- **state**：success / warning / error / info
- **focus**：focus

### ガイドライン

- UI上では **semantic token** を優先使用する
- 直接値（#xxx や oklch直書き）の使用は、例外に限定する
- ダークモード対応はセマンティックトークンの再定義で実現する
- トークン命名や段階導入の詳細は `reference/design-tokens.md` を参照する

## アクセシビリティ観点の色設計

### コントラスト

- テキスト：4.5:1 以上（大きな文字は 3:1 以上）
- UIコンポーネントやアイコン：3:1 以上
- ダークモードでもコントラスト比を検証する（暗い背景 + 明るいテキストの組み合わせ）

### 色覚多様性

- 色だけに依存した情報伝達を避ける
- 色相差が小さい組み合わせ（赤×緑、青×紫など）は要注意
- 形状・アイコン・テキストで補助する

### フォーカスの視認性

- フォーカスリングは背景と十分にコントラストを取る
- 色だけでなく、アウトラインや影で補助可能
- ダークモードとライトモードの両方で視認性を確認する

## 危険な色の組み合わせ

以下の組み合わせはコントラスト不足や可読性の問題を引き起こす。
設計・レビュー時に必ず確認する。

### 高リスクの組み合わせ

| 組み合わせ | 問題 | 対策 |
|---|---|---|
| 薄いグレーテキスト on 白背景 | コントラスト不足で読めない | `text.muted` でも 4.5:1 を確保する |
| グレーテキスト on 色付き背景 | 背景色と溶け込む | 色付き背景には白/黒テキストを使う |
| 赤テキスト on 緑背景 | 色覚多様性で判別不可 | 色以外の識別手段を追加する |
| 青テキスト on 赤背景 | 色収差で文字がにじむ | 高彩度同士の組み合わせを避ける |
| 黄色テキスト on 白背景 | コントラスト不足 | 黄色は背景用に限定する |

### 検出方法

- デザインファイルのコントラスト比を機械的にチェックする
- グレースケール変換で色だけに依存した表現がないか確認する
- 色覚シミュレーションツール（P型・D型）で検証する

## よくある失敗パターン

### 純黒（#000）/ 純白（#fff）の使用

- **問題**：コントラストが過剰になり、目が疲れる。特にダークモードの `#000` 背景は非常に不自然
- **改善**：ティンテッドニュートラルを使う。最も暗い色は oklch 12〜18%、最も明るい色は oklch 95〜98% を基準にする

### AI的パレット（サイバー配色）の採用

- **問題**：ダーク背景にシアン、パープルグラデーション、ネオンアクセントなど。「先進的」に見えるが、可読性が低く、ブランドの差別化にならない
- **改善**：ブランドカラーを起点にパレットを構築する。高彩度のアクセントは 10% 以下の面積に限定する

### グラデーションテキスト

- **問題**：テキストにグラデーションをかけてインパクトを出そうとする。可読性が下がり、コントラスト比の保証が困難になる
- **改善**：テキストは単色で可読性を優先する。グラデーションは装飾的な背景やアイコンに限定する

### グレーテキスト on 色付き背景

- **問題**：色付き背景の上にグレーテキストを配置すると、背景色に溶け込んで読めなくなる
- **改善**：色付き背景には十分なコントラストがある白か黒のテキストを使用する

### 状態色の意味が一貫しない

- **問題**：成功にも警告にも同じ色を使う
- **改善**：状態ごとの色をセマンティックトークンとして明確に分ける

### 強調色の乱用

- **問題**：複数の重要要素が同じ強調色で、すべてが「主役」になっている
- **改善**：60-30-10 ルールに基づき、アクセントカラーの面積を制限する

### 背景とテキストのコントラスト不足

- **問題**：薄いグレー文字が背景と同化している
- **改善**：OKLCHの明度値でコントラスト比を計測・調整する

### アルファ透明度の多用

- **問題**：ホバー状態やボーダーなど、あらゆる場所で透明度に頼っている
- **改善**：パレットを見直し、必要な色を明示的にトークンとして定義する

## このreferenceの使い方

以下のコマンドスキルから参照される:

- `extract-ui` — トークン抽出・リファクタリング時のカラートークン設計に参照
- `boost-ui` — 視覚的インパクト強化時のカラー階層設計に参照
- `calm-ui` — 視覚的ノイズ軽減時のカラーバランス調整に参照
- トークン設計の詳細は `reference/design-tokens.md` を併せて参照する
