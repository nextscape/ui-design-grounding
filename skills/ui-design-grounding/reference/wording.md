## このドキュメントの役割
このドキュメントは、UI/UXデザインにおける
**ワーディング（マイクロコピー）の設計原則と判断基準**を提供する。

UI上のテキスト（ボタンラベル、エラーメッセージ、ガイダンス、空の状態等）を
設計する際の判断材料とする。

## ワーディングとは何か

ワーディング（マイクロコピー）とは、
**UI上の短いテキスト（ボタンラベル、エラーメッセージ、ガイダンス等）**である。

以下を目的とする：

- ユーザーの理解を助ける
- 操作を明確にする
- エラーから回復を支援する
- ユーザーとの信頼関係を築く

## マイクロコピーの設計原則

### 明確性（Clarity）

**判断基準：**
- メッセージが明確で理解しやすい
- 専門用語を避け、平易な言葉を使う
- 曖昧な表現を避ける
- 一つのメッセージで一つのことを伝える

**実践例：**
- 「エラーが発生しました」 → 「メールアドレスの形式が正しくありません」
- 「送信」 → 「変更を保存」
- 「無効な入力です」 → 「半角数字で入力してください」

### 簡潔性（Conciseness）

**判断基準：**
- 必要な情報のみを伝える
- 冗長な表現を避ける
- 短く、要点を伝える
- ただし、必要な情報を削ってまで短くしない

**実践例：**
- 「この操作を実行すると、データが削除されます。この操作は取り消すことができません。本当に実行しますか？」
  → 「このデータを削除しますか？この操作は取り消せません。」
- 「入力されたメールアドレスはすでに登録されています。別のメールアドレスをお試しください。」
  → 「このメールアドレスは登録済みです。別のアドレスをお試しください。」

### ユーザー視点（User-Centered）

**判断基準：**
- ユーザーの視点で書く
- システムの都合ではなく、ユーザーの利益を伝える
- ユーザーの行動を促す
- ユーザーを責めない

**実践例：**

システム視点（避ける）→ ユーザー視点（推奨）：
- 「システムエラーが発生しました」 → 「申し訳ございません。問題が発生しました。しばらくしてから再度お試しください。」
- 「データベース接続に失敗しました」 → 「接続できませんでした。インターネット接続を確認してください。」
- 「バリデーションエラーです」 → 「入力内容に誤りがあります。確認してください。」
- 「保存されました」 → 「変更を保存しました」

### 一貫性（Consistency）

**判断基準：**
- 用語が統一されている
- トーンが一貫している
- 同じ状況では同じ表現を使う
- プロダクト全体で統一ルールを持つ

**実践例：**
- 用語の統一：「保存」と「登録」を混在させない
- トーンの統一：丁寧語で統一、または常体で統一
- 表現の統一：同じエラーは同じメッセージ
- 操作の統一：同じ種類の操作には同じ動詞を使う

## ボイスとトーン

### ボイス（Voice）— 一貫したブランドの性格

ボイスはプロダクトの**性格**であり、常に一貫している。
ユーザーがどの画面を見ても「同じプロダクトだ」と感じられるようにする。

**ボイスの定義例：**
- 専門的だが親しみやすい
- 簡潔で率直
- 丁寧だが堅すぎない
- ユーザーを対等なパートナーとして扱う

### トーン（Tone）— 状況に応じた感情的な調整

トーンはボイスの上に乗る**感情的なニュアンス**であり、状況によって変化する。

**状況別のトーン：**

| 状況 | トーン | 例 |
|------|--------|-----|
| 成功・完了 | 祝福的、肯定的 | 「アカウントを作成しました。ようこそ！」 |
| エラー・失敗 | 共感的、支援的 | 「申し訳ございません。問題が発生しました。」 |
| 破壊的操作 | 真剣、明確 | 「このアカウントを完全に削除します。この操作は取り消せません。」 |
| オンボーディング | 歓迎的、ガイド的 | 「まずはプロフィールを設定しましょう。」 |
| 待機・ローディング | 安心感、進捗 | 「ファイルをアップロードしています...」 |
| 警告 | 注意喚起、具体的 | 「保存していない変更があります。」 |

**注意点：**
- エラーメッセージにユーモアを使わない（ユーザーは困っている状態であり、冗談は不適切）
- 破壊的操作で楽観的なトーンを使わない
- 成功メッセージで事務的すぎるトーンを使わない

## ボタンラベルの設計

### 基本原則：動詞 + 目的語

**「OK」「送信」「はい/いいえ」を使わない。**
操作の内容が具体的に分かるラベルにする。

**パターン：動詞 + 目的語**

| 避ける | 推奨 |
|--------|------|
| OK | 変更を保存 |
| 送信 | メッセージを送信 |
| Submit | アカウントを作成 |
| はい | 削除する |
| いいえ | キャンセル |
| 実行 | レポートを生成 |
| 確認 | 注文を確定する |

### 破壊的操作のラベル

破壊的な操作では**何を破壊するかを明記する**。

| 避ける | 推奨 |
|--------|------|
| 削除 | このプロジェクトを削除 |
| OK | アカウントを削除する |
| 実行する | 全データを消去する |

### ボタンの対（ペア）

確認ダイアログやモーダルでは、2つのボタンが対になる。
両方のラベルが対称的で、操作内容が明確であること。

| 避ける | 推奨 |
|--------|------|
| OK / キャンセル | 変更を保存 / 変更を破棄 |
| はい / いいえ | 削除する / キャンセル |
| 確認 / 戻る | 注文を確定する / 買い物を続ける |

## エラーメッセージの設計

### 3つの要素

すべてのエラーメッセージは以下の3つに答える：

1. **何が起きたか？**（What happened?）
2. **なぜ起きたか？**（Why?）
3. **どうすれば直せるか？**（How to fix?）

**実践例：**

```
何が：パスワードが条件を満たしていません。
なぜ：パスワードは8文字以上で、英数字を含む必要があります。
直し方：パスワードを修正して、もう一度お試しください。
```

→ 「パスワードは8文字以上で、英数字を含む必要があります。修正してもう一度お試しください。」

```
何が：ファイルをアップロードできませんでした。
なぜ：ファイルサイズが上限（10MB）を超えています。
直し方：10MB以下のファイルを選択してください。
```

→ 「ファイルサイズが上限（10MB）を超えています。10MB以下のファイルを選択してください。」

### エラーメッセージの禁止事項

- **ユーザーを責めない**：「入力が間違っています」→「入力内容を確認してください」
- **ユーモアを使わない**：「おっと！」「あらら」→ 使わない。ユーザーは困っている。
- **技術用語を使わない**：「Error 500」「NullPointerException」→ ユーザーが理解できる言葉に翻訳する
- **曖昧にしない**：「エラーが発生しました」→ 具体的な問題と解決策を示す

## 空の状態（Empty State）の設計

空の状態とは、コンテンツがまだ存在しない画面の状態。
初回利用時、検索結果なし、データ削除後などに表示される。

### 3つの要素

1. **状態を認識させる**：今何も表示されていない理由
2. **価値を伝える**：この画面で何ができるか
3. **行動を促す**：次に何をすべきか

**実践例：**

```
初回利用時：
「プロジェクトはまだありません。
 チームの作業を整理・管理できます。
 [最初のプロジェクトを作成]」

検索結果なし：
「"〇〇" に一致する結果はありませんでした。
 検索キーワードを変更するか、フィルターを調整してください。
 [フィルターをクリア]」

データ削除後：
「通知はありません。
 新しい通知があるとここに表示されます。」
```

**注意点：**
- 空の状態を放置しない（空白ページは不安を与える）
- イラストを使う場合は、ブランドのトーンに合わせる
- アクションボタンは1つに絞る（選択肢が多いと迷う）

## 確認ダイアログの文言

### 使用を控えるべき場面

確認ダイアログは操作の流れを中断する。**可能であれば Undo パターンを検討する。**

確認ダイアログが適切な場面：
- 取り消し不可能な操作
- 金銭が関わる操作
- 他のユーザーに影響する操作

### 文言の設計

**構成要素：**
1. **タイトル**：何を確認するか（動詞 + 目的語）
2. **説明文**：操作の結果と影響を具体的に説明
3. **ボタンラベル**：操作内容を明記（「OK」は使わない）

**実践例：**

```
タイトル：このプロジェクトを削除しますか？
説明文：プロジェクト「〇〇」とすべてのタスク・ファイルが完全に削除されます。
       この操作は取り消せません。
ボタン：[キャンセル] [プロジェクトを削除]
```

```
タイトル：変更を破棄しますか？
説明文：保存していない変更は失われます。
ボタン：[編集に戻る] [変更を破棄]
```

**避けるべきパターン：**
- 「本当に実行しますか？」（何を実行するか不明）
- 「OK / キャンセル」（どちらが何をするか不明）
- 「はい / いいえ」（文脈なしでは判断できない）

## アクセシビリティのためのライティング

### リンクテキスト

リンクテキストは**単独で意味が分かる**ようにする。
スクリーンリーダーはリンクだけを一覧表示する機能があり、
「こちら」「ここをクリック」では目的地が分からない。

| 避ける | 推奨 |
|--------|------|
| 詳しくはこちら | 料金プランの詳細を見る |
| ここをクリック | ドキュメントをダウンロード |
| リンク | 利用規約を確認する |
| 詳細 | アカウント設定を変更する |

### 画像の代替テキスト（alt属性）

**alt テキストは画像が伝える「情報」を記述する。画像の「見た目」を記述しない。**

| 画像の種類 | alt テキスト |
|-----------|-------------|
| 商品写真 | 「赤いランニングシューズ、サイド ビュー」（商品情報） |
| グラフ | 「2024年の売上推移。1月から12月にかけて30%増加」（データ情報） |
| アイコンボタン | 「検索」「メニューを開く」（機能情報） |
| 装飾画像 | `alt=""`（空にする。スクリーンリーダーが読み上げない） |
| ロゴ | 「〇〇株式会社」（社名） |

**注意点：**
- 「〇〇の画像」「〇〇の写真」という記述は冗長（スクリーンリーダーが既に「画像」と読み上げる）
- 装飾的な画像は `alt=""` にする（`alt` 属性自体は省略しない）
- 複雑な図表は `alt` で要約し、詳細は本文やキャプションで提供する

### フォームのラベル

- すべての入力フィールドに `<label>` を関連付ける
- プレースホルダーはラベルの代替にしない
- 必須項目は「必須」と明記する（`*` だけでなくテキストで）
- エラーメッセージは `aria-describedby` でフィールドに関連付ける

## 翻訳・国際化（i18n）を考慮したライティング

多言語展開を想定する場合、日本語のライティング段階から翻訳しやすさを意識する。

### テキスト膨張への対応

言語によってテキストの長さが大きく変わる。UIレイアウトは膨張に耐えられる設計にする。

| 言語 | 日本語比での長さ変化 |
|------|---------------------|
| ドイツ語 | 約 +30% |
| フランス語 | 約 +20% |
| フィンランド語 | 約 +30-40% |
| 中国語 | 約 -30% |
| 英語 | テキストによる |

**対策：**
- ボタンやラベルに固定幅を設定しない（`min-width` を使い、テキストに応じて伸縮させる）
- テキストの折り返しを考慮する
- レイアウトに余白を持たせる

### 翻訳しやすいライティングルール

**数値をテキストに埋め込まない：**
- 「3件の結果」→ テンプレート：`{count}件の結果`
- 文中の数値はプレースホルダー化する

**完全な文で書く：**
- 文の一部だけを変数にしない（語順が言語によって異なるため）
- 「{name}さんが{action}しました」→ 言語によっては語順が変わるため、文全体をテンプレートにする

**略語を避ける：**
- 「設定」を「設」と略さない
- 略語は翻訳できない場合がある

**論理プロパティを使用する：**
- `margin-left` / `margin-right` ではなく `margin-inline-start` / `margin-inline-end` を使用する
- RTL（右から左）言語に自動対応する

```css
/* 避ける：物理プロパティ */
.element {
  margin-left: 1rem;
  padding-right: 0.5rem;
  text-align: left;
}

/* 推奨：論理プロパティ */
.element {
  margin-inline-start: 1rem;
  padding-inline-end: 0.5rem;
  text-align: start;
}
```

## 用語辞書（用語統一ルール）

プロダクト全体で用語を統一する。**一つの概念に一つの用語**を対応させる。

### 用語辞書テンプレート

| 統一用語 | 使わない用語 | 用途・文脈 |
|----------|------------|-----------|
| 削除 | 除去、ゴミ箱に入れる、消去 | データやアイテムを取り除く操作 |
| 設定 | 環境設定、オプション、コンフィグ | アプリケーションの各種設定画面 |
| ログイン | サインイン、ログオン | 認証してアカウントにアクセスする操作 |
| ログアウト | サインアウト、ログオフ | 認証セッションを終了する操作 |
| 保存 | 登録、記録、格納 | データを永続化する操作 |
| 作成 | 追加、新規、生成 | 新しいリソースを作る操作 |
| 編集 | 変更、修正、更新 | 既存のリソースを変更する操作 |
| キャンセル | 取消、中止、やめる | 操作を中断して元の状態に戻る操作 |
| エラー | 障害、不具合、問題 | 操作が失敗した状態 |
| 検索 | 探す、サーチ、検索する | コンテンツを条件で絞り込む操作 |

### 用語辞書の運用ルール

- プロジェクト開始時に用語辞書を作成する
- 新しい用語が必要になったら辞書に追加する
- コードレビューで用語の統一を確認する
- UIテキスト・ドキュメント・コード内のコメントすべてで統一する
- 用語辞書はチーム全体がアクセスできる場所に配置する

## 判断に迷いやすいポイント

### 専門用語の使用

**判断基準：**
- 対象ユーザーの知識に合っているか
- 代替表現で誤解が減るか

**判断例：**
- 「認証」→ 一般ユーザー向けなら「ログイン確認」
- 「同期」→ 一般ユーザー向けなら「最新に更新」
- 「デプロイ」→ 開発者向けならそのまま使用可

### トーンと丁寧さ

**判断基準：**
- サービスの性格と一致しているか
- 緊急性が高い場面で冗長になっていないか
- 状況に合ったトーンか（ボイスとトーンのセクション参照）

**判断例：**
- 重要な警告：簡潔で明確な表現を優先
- 日常操作：安心感のある丁寧表現を許容
- エラー時：共感的だが具体的に

### メッセージの長さ

**判断基準：**
- 3つの要素（何が・なぜ・どうすれば）が含まれているか
- 不要な修飾語を削れるか
- 詳細は展開可能にできるか

**判断例：**
- エラーメッセージ：問題、原因、解決方法を簡潔に
- ガイダンス：要点を簡潔に、詳細はヘルプで展開可能に
- 成功メッセージ：1文で十分。過剰に喜ばない

### Undo vs 確認ダイアログの文言

**判断基準：**
1. 操作は技術的に取り消し可能か
2. 確認ダイアログでユーザーが本当に内容を読むか
3. 頻繁に行う操作か（頻繁なら確認ダイアログは障害になる）

**判断例：**
- メール削除 → Undo Toast：「メールを削除しました [元に戻す]」
- アカウント削除 → 確認ダイアログ：具体的な影響を説明

## よくある失敗パターン

- **「OK」「送信」「はい/いいえ」ボタン**
  - 例：確認ダイアログに「OK / キャンセル」
  - 改善：操作内容を明記する（「削除する / キャンセル」）

- **システム視点のメッセージ**
  - 例：「システムエラーが発生しました」「Error 500」
  - 改善：ユーザー視点で、問題と解決方法を明確に

- **曖昧なエラーメッセージ**
  - 例：「エラーが発生しました」「問題があります」
  - 改善：何が起きたか、なぜか、どう直すかの3つに答える

- **専門用語の多用**
  - 例：「バリデーションエラー」「タイムアウト」
  - 改善：平易な言葉で、ユーザーが理解できる表現に

- **一貫性の欠如**
  - 例：「保存」と「登録」を混在、「削除」と「除去」を混在
  - 改善：用語辞書を作成し、プロダクト全体で統一する

- **意味のないリンクテキスト**
  - 例：「こちら」「ここをクリック」「詳細」
  - 改善：リンク先の内容が分かるテキストにする（「料金プランの詳細を見る」）

- **エラー時のユーモア**
  - 例：「おっと！何かがうまくいかなかったようです」
  - 改善：共感的で具体的なメッセージにする。困っているユーザーに冗談は不要。

- **空の状態の放置**
  - 例：データがない画面に何も表示しない
  - 改善：状態の説明、価値の提示、アクションボタンを配置する

- **固定幅のテキスト領域**
  - 例：ボタンの幅を固定して翻訳時にテキストが溢れる
  - 改善：`min-width` と伸縮可能なレイアウトを使用する
