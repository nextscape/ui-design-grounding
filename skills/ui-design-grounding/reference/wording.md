## このドキュメントの役割
UI/UXデザインにおける**ワーディング（マイクロコピー）の設計原則と判断基準**を提供する。UI上のテキスト（ボタンラベル、エラーメッセージ、ガイダンス、空の状態等）を設計する際の判断材料とする。

## ワーディングとは何か
ワーディング（マイクロコピー）とは**UI上の短いテキスト**（ボタンラベル、エラーメッセージ、ガイダンス等）。目的は、理解を助ける／操作を明確にする／エラーからの回復を支援する／信頼関係を築く、こと。

## マイクロコピーの設計原則

### 明確性（Clarity）

**判断基準：** 明確で理解しやすい／専門用語を避け平易に／曖昧な表現を避ける／一つのメッセージで一つのことを伝える

**実践例：**
- 「エラーが発生しました」 → 「メールアドレスの形式が正しくありません」
- 「送信」 → 「変更を保存」
- 「無効な入力です」 → 「半角数字で入力してください」

### 簡潔性（Conciseness）

**判断基準：** 必要な情報のみを短く要点を伝える／冗長な表現を避ける／ただし必要な情報を削ってまで短くしない

**実践例：**
- 「この操作を実行すると、データが削除されます。この操作は取り消すことができません。本当に実行しますか？」
  → 「このデータを削除しますか？この操作は取り消せません。」

### ユーザー視点（User-Centered）

**判断基準：** ユーザーの視点で書く／システムの都合でなくユーザーの利益を伝える／行動を促す／責めない

**実践例（システム視点 → ユーザー視点）：**
- 「システムエラーが発生しました」 → 「申し訳ございません。問題が発生しました。しばらくしてから再度お試しください。」
- 「データベース接続に失敗しました」 → 「接続できませんでした。インターネット接続を確認してください。」
- 「バリデーションエラーです」 → 「入力内容に誤りがあります。確認してください。」

### 一貫性（Consistency）

**判断基準：** 用語が統一されている／トーンが一貫している／同じ状況では同じ表現／プロダクト全体で統一ルールを持つ

**実践例：**
- 用語：「保存」と「登録」を混在させない
- トーン：丁寧語か常体かを統一
- 表現：同じエラーは同じメッセージ／同じ種類の操作には同じ動詞

## ボイスとトーン

### ボイス（Voice）— 一貫したブランドの性格
ボイスはプロダクトの**性格**で、常に一貫している。どの画面でも「同じプロダクトだ」と感じられるようにする。
**定義例：** 専門的だが親しみやすい／簡潔で率直／丁寧だが堅すぎない／対等なパートナーとして扱う

### トーン（Tone）— 状況に応じた感情的な調整
トーンはボイスの上に乗る**感情的なニュアンス**で、状況によって変化する。

| 状況 | トーン | 例 |
|------|--------|-----|
| 成功・完了 | 祝福的、肯定的 | 「アカウントを作成しました。ようこそ！」 |
| エラー・失敗 | 共感的、支援的 | 「申し訳ございません。問題が発生しました。」 |
| 破壊的操作 | 真剣、明確 | 「このアカウントを完全に削除します。この操作は取り消せません。」 |
| オンボーディング | 歓迎的、ガイド的 | 「まずはプロフィールを設定しましょう。」 |
| 待機・ローディング | 安心感、進捗 | 「ファイルをアップロードしています...」 |
| 警告 | 注意喚起、具体的 | 「保存していない変更があります。」 |

**注意点：**
- エラーメッセージにユーモアを使わない（ユーザーは困っている）
- 破壊的操作で楽観的なトーンを使わない
- 成功メッセージで事務的すぎるトーンを使わない

## ボタンラベルの設計

### 基本原則：動詞 + 目的語
**「OK」「送信」「はい/いいえ」を使わない。** 操作の内容が具体的に分かるラベルにする。

| 避ける | 推奨 |
|--------|------|
| OK | 変更を保存 |
| 送信 | メッセージを送信 |
| Submit | アカウントを作成 |
| はい | 削除する |
| 実行 | レポートを生成 |
| 確認 | 注文を確定する |

### 破壊的操作のラベル
**何を破壊するかを明記する。**

| 避ける | 推奨 |
|--------|------|
| 削除 | このプロジェクトを削除 |
| OK | アカウントを削除する |
| 実行する | 全データを消去する |

### ボタンの対（ペア）
確認ダイアログやモーダルでは2つのボタンが対になる。両方が対称的で、操作内容が明確であること。

| 避ける | 推奨 |
|--------|------|
| OK / キャンセル | 変更を保存 / 変更を破棄 |
| はい / いいえ | 削除する / キャンセル |
| 確認 / 戻る | 注文を確定する / 買い物を続ける |

## エラーメッセージの設計

### 3つの要素
すべてのエラーメッセージは次に答える。
1. **何が起きたか？**（What happened?）
2. **なぜ起きたか？**（Why?）
3. **どうすれば直せるか？**（How to fix?）

**実践例：** 何が／なぜ／直し方 を1文にまとめる。
→ 「パスワードは8文字以上で、英数字を含む必要があります。修正してもう一度お試しください。」

### 禁止事項
- **ユーザーを責めない**：「入力が間違っています」→「入力内容を確認してください」
- **ユーモアを使わない**：「おっと！」「あらら」→ 使わない。ユーザーは困っている。
- **技術用語を使わない**：「Error 500」「NullPointerException」→ ユーザーが理解できる言葉に翻訳する
- **曖昧にしない**：「エラーが発生しました」→ 具体的な問題と解決策を示す

## 空の状態（Empty State）の設計
コンテンツがまだ存在しない画面の状態（初回利用時、検索結果なし、データ削除後など）。

### 3つの要素
1. **状態を認識させる**：今何も表示されていない理由
2. **価値を伝える**：この画面で何ができるか
3. **行動を促す**：次に何をすべきか

**実践例（初回利用時）：**
```
「プロジェクトはまだありません。
 チームの作業を整理・管理できます。
 [最初のプロジェクトを作成]」
```

**注意点：**
- 空の状態を放置しない（空白ページは不安を与える）
- イラストはブランドのトーンに合わせる
- アクションボタンは1つに絞る（選択肢が多いと迷う）

## 確認ダイアログの文言

### 使用を控えるべき場面
確認ダイアログは操作の流れを中断する。**可能であれば Undo パターンを検討する。**

適切な場面：取り消し不可能な操作／金銭が関わる操作／他のユーザーに影響する操作

### 文言の設計
**構成要素：**
1. **タイトル**：何を確認するか（動詞 + 目的語）
2. **説明文**：操作の結果と影響を具体的に
3. **ボタンラベル**：操作内容を明記（「OK」は使わない）

**実践例：**
```
タイトル：このプロジェクトを削除しますか？
説明文：プロジェクト「〇〇」とすべてのタスク・ファイルが完全に削除されます。
       この操作は取り消せません。
ボタン：[キャンセル] [プロジェクトを削除]
```

**避けるべきパターン：**
- 「本当に実行しますか？」（何を実行するか不明）
- 「OK / キャンセル」（どちらが何をするか不明）
- 「はい / いいえ」（文脈なしでは判断できない）

## アクセシビリティのためのライティング

### リンクテキスト
リンクテキストは**単独で意味が分かる**ようにする。スクリーンリーダーはリンクだけを一覧表示するため、「こちら」では目的地が分からない。

| 避ける | 推奨 |
|--------|------|
| 詳しくはこちら | 料金プランの詳細を見る |
| ここをクリック | ドキュメントをダウンロード |
| 詳細 | アカウント設定を変更する |

### 画像の代替テキスト（alt属性）
**alt テキストは画像が伝える「情報」を記述する。「見た目」を記述しない。**

| 画像の種類 | alt テキスト |
|-----------|-------------|
| 商品写真 | 「赤いランニングシューズ、サイド ビュー」（商品情報） |
| グラフ | 「2024年の売上推移。1月から12月にかけて30%増加」（データ情報） |
| アイコンボタン | 「検索」「メニューを開く」（機能情報） |
| 装飾画像 | `alt=""`（空にする。スクリーンリーダーが読み上げない） |
| ロゴ | 「〇〇株式会社」（社名） |

**注意点：**
- 「〇〇の画像」「〇〇の写真」は冗長（スクリーンリーダーが既に「画像」と読み上げる）
- 装飾画像は `alt=""` にする（`alt` 属性自体は省略しない）
- 複雑な図表は `alt` で要約し、詳細は本文やキャプションで提供する

### フォームのラベル
- すべての入力フィールドに `<label>` を関連付ける
- プレースホルダーはラベルの代替にしない
- 必須項目は「必須」とテキストで明記（`*` だけにしない）
- エラーメッセージは `aria-describedby` でフィールドに関連付ける

## 翻訳・国際化（i18n）を考慮したライティング
多言語展開を想定する場合、日本語の段階から翻訳しやすさを意識する。

### テキスト膨張への対応
言語によってテキスト長は大きく変わる。レイアウトは膨張に耐えられる設計にする。

| 言語 | 日本語比での長さ変化 |
|------|---------------------|
| ドイツ語 | 約 +30% |
| フランス語 | 約 +20% |
| フィンランド語 | 約 +30-40% |
| 中国語 | 約 -30% |
| 英語 | テキストによる |

**対策：** 固定幅を設定しない（`min-width` で伸縮させる）／テキストの折り返しを考慮する／レイアウトに余白を持たせる

### 翻訳しやすいライティングルール
- **数値をテキストに埋め込まない**：「3件の結果」→ テンプレート `{count}件の結果`
- **完全な文で書く**：文の一部だけを変数にしない。語順が言語で異なるため文全体をテンプレート化する（例：「{name}さんが{action}しました」）
- **略語を避ける**：「設定」を「設」と略さない（翻訳できない場合がある）
- **論理プロパティを使用する**：`margin-left`/`margin-right` でなく `margin-inline-start`/`margin-inline-end` を使い、RTL言語に自動対応する

```css
/* 避ける：物理プロパティ */
.element { margin-left: 1rem; padding-right: 0.5rem; text-align: left; }

/* 推奨：論理プロパティ */
.element { margin-inline-start: 1rem; padding-inline-end: 0.5rem; text-align: start; }
```

## 用語辞書（用語統一ルール）
プロダクト全体で用語を統一する。**一つの概念に一つの用語**を対応させる。

### 用語辞書テンプレート

| 統一用語 | 使わない用語 | 用途・文脈 |
|----------|------------|-----------|
| 削除 | 除去、ゴミ箱に入れる、消去 | データやアイテムを取り除く |
| 設定 | 環境設定、オプション、コンフィグ | 各種設定画面 |
| ログイン | サインイン、ログオン | 認証してアカウントにアクセス |
| ログアウト | サインアウト、ログオフ | 認証セッションを終了 |
| 保存 | 登録、記録、格納 | データを永続化 |
| 作成 | 追加、新規、生成 | 新しいリソースを作る |
| 編集 | 変更、修正、更新 | 既存のリソースを変更 |
| キャンセル | 取消、中止、やめる | 操作を中断して元に戻る |
| エラー | 障害、不具合、問題 | 操作が失敗した状態 |
| 検索 | 探す、サーチ | コンテンツを条件で絞り込む |

### 運用ルール
- プロジェクト開始時に辞書を作成し、新しい用語が必要になったら追加する
- コードレビューで用語の統一を確認する
- UIテキスト・ドキュメント・コード内コメントすべてで統一する
- 辞書はチーム全体がアクセスできる場所に配置する

## 判断に迷いやすいポイント

### 専門用語の使用
**判断基準：** 対象ユーザーの知識に合っているか／代替表現で誤解が減るか
**判断例：** 「認証」→ 一般向けなら「ログイン確認」／「同期」→「最新に更新」／「デプロイ」→ 開発者向けならそのまま使用可

### トーンと丁寧さ
**判断基準：** サービスの性格と一致しているか／緊急性が高い場面で冗長になっていないか／状況に合ったトーンか（ボイスとトーン参照）
**判断例：** 重要な警告は簡潔・明確を優先／日常操作は安心感のある丁寧表現を許容／エラー時は共感的だが具体的に

### メッセージの長さ
**判断基準：** 3つの要素（何が・なぜ・どうすれば）が含まれているか／不要な修飾語を削れるか／詳細は展開可能にできるか
**判断例：** エラーは問題・原因・解決方法を簡潔に／ガイダンスは要点を簡潔に詳細はヘルプで／成功は1文で十分

### Undo vs 確認ダイアログ
**判断基準：** ①技術的に取り消し可能か ②ユーザーが本当に内容を読むか ③頻繁に行う操作か（頻繁なら確認は障害になる）
**判断例：** メール削除 → Undo Toast「メールを削除しました [元に戻す]」／アカウント削除 → 確認ダイアログで具体的な影響を説明

## よくある失敗パターン

- **「OK」「送信」「はい/いいえ」ボタン**：確認ダイアログの「OK / キャンセル」など → 操作内容を明記（「削除する / キャンセル」）
- **システム視点のメッセージ**：「システムエラー」「Error 500」 → ユーザー視点で問題と解決方法を明確に
- **曖昧なエラー**：「エラーが発生しました」 → 何が・なぜ・どう直すかの3つに答える
- **専門用語の多用**：「バリデーションエラー」「タイムアウト」 → 平易でユーザーが理解できる表現に
- **一貫性の欠如**：「保存」と「登録」を混在 → 用語辞書を作成し全体で統一する
- **意味のないリンクテキスト**：「こちら」「詳細」 → リンク先の内容が分かるテキストに
- **エラー時のユーモア**：「おっと！」 → 共感的で具体的なメッセージに
- **空の状態の放置**：データがない画面に何も表示しない → 状態説明・価値提示・アクションボタンを配置
- **固定幅のテキスト領域**：翻訳時にテキストが溢れる → `min-width` と伸縮可能なレイアウトを使用

## このreferenceの使い方
以下のコマンドスキルから参照される:
- `clarify-ui` — ワーディング明確化時のマイクロコピー設計・エラーメッセージ設計に参照
- `design-ui` — UI設計時のワーディング・ボイス&トーン設計に参照
- `score-ui` — UI品質スコアリングのワーディング評価時に参照
- `guard-ui` — エッジケース堅牢化時のエラーメッセージ・空の状態設計に参照

ワーディング設計・UIレビューの判断材料として、また用語辞書テンプレート導入のベースとして使う。
