## このドキュメントの役割
このドキュメントは、UI/UXデザインにおける
**モーションデザインの判断基準と実践的な指針**を提供する。

アニメーションのデュレーション、イージング、性能最適化、アクセシビリティ対応について、
設計・実装時の判断軸を体系化する。

## モーションデザインとは何か

モーションデザインとは、
**UIの状態変化やフィードバックをアニメーションで伝え、ユーザーの理解と快適さを向上させること**である。

以下を目的とする：

- 操作結果の即座のフィードバック
- 状態変化の視覚的な連続性
- ユーザーの注意の適切な誘導
- インターフェースの空間的な関係性の伝達
- 知覚的なパフォーマンスの向上

## デュレーション体系

アニメーションのデュレーションは、変化の種類と規模に応じて段階的に設定する。

### デュレーションの基準値

| カテゴリ | デュレーション | 用途 |
|---------|-------------|------|
| 即座のフィードバック | 100-150ms | hover、active states、ボタン押下 |
| 状態変化 | 200-300ms | トグル、スイッチ、タブ切り替え |
| レイアウト変化 | 300-500ms | アコーディオン、パネルスライド |
| エントランスアニメーション | 500-800ms | ページ遷移、セクション入場 |

**判断基準：**
- これらはデフォルト値であり、コンテキストにより調整可能である
- 退出アニメーションのデュレーションは、入場の約75%に設定する
- 退出は入場より短くする理由：ユーザーは次のアクションに移りたいため、退出を待たせない
- 小さい要素ほど短いデュレーション、大きい要素ほど長いデュレーションが自然である
- デュレーションが長すぎると「遅い」と感じ、短すぎると変化に気づかない

## イージングカーブ

イージングカーブは、アニメーションの加速・減速パターンを決定する。
**用途に応じて適切なカーブを選択する。**

### イージングの使い分け

| イージング | 用途 | 理由 |
|-----------|------|------|
| ease-out | 入場（要素が到着） | 最初に速く動き、目的地で減速する。自然な到着感 |
| ease-in | 退出（要素が去る） | ゆっくり動き始め、加速して去る。自然な離脱感 |
| ease-in-out | トグル、状態切り替え | 両端で緩やかに変化し、中間で速い。位置の入れ替わりに適する |

**`ease` を使わない。** CSSデフォルトの `ease` は中途半端なカーブであり、意図が不明確になる。

### 推奨する指数関数カーブ

標準のイージングよりも指数関数カーブのほうが自然な動きを実現する。

```css
:root {
  --ease-out-quart: cubic-bezier(0.25, 1, 0.5, 1);
  --ease-out-quint: cubic-bezier(0.22, 1, 0.36, 1);
  --ease-out-expo: cubic-bezier(0.16, 1, 0.3, 1);
}
```

**判断基準：**
- 入場アニメーションには `--ease-out-quart` または `--ease-out-quint` を推奨する
- より劇的な減速が必要な場合は `--ease-out-expo` を使用する
- バウンスやエラスティックのイージングは使用しない。実際の物体はスムーズに減速するのであり、跳ね返らない。バウンス/エラスティックは古臭い印象を与える

## アニメーション性能ルール

### 最重要ルール：transform と opacity のみアニメーションする

**`transform` と `opacity` のみをアニメーションプロパティとして使用する。**
これが最も重要なルールである。

**理由：**
- `transform` と `opacity` はコンポジターレイヤーで処理され、レイアウトやペイントの再計算を引き起こさない
- その他のプロパティ（`width`, `height`, `padding`, `margin` 等）のアニメーションはレイアウト再計算を引き起こし、フレーム落ちの原因となる

### 禁止されるプロパティのアニメーション

以下のプロパティをアニメーションしてはならない：

- `width`, `height`
- `padding`, `margin`
- `top`, `left`, `right`, `bottom`（`position: absolute/fixed` の場合。代わりに `transform: translate()` を使用する）
- `border-width`
- `font-size`

### 高さアニメーションの代替手段

高さの変化（アコーディオン等）には `grid-template-rows` を使用する。

```css
.accordion-content {
  display: grid;
  grid-template-rows: 0fr;
  transition: grid-template-rows 300ms var(--ease-out-quart);
}

.accordion-content[data-open="true"] {
  grid-template-rows: 1fr;
}

.accordion-content > .inner {
  overflow: hidden;
}
```

### will-change の使用制限

- `will-change` の先行使用は禁止する
- ブラウザは自身で最適化を行うため、`will-change` を事前に設定すると逆にメモリを無駄に消費する
- 測定によりボトルネックが確認された場合のみ、限定的に使用する

### スクロールトリガーアニメーション

- Intersection Observer API でスクロールトリガーアニメーションを実装する
- `scroll` イベントリスナーの使用は避ける（パフォーマンスに悪影響）

```javascript
const observer = new IntersectionObserver(
  (entries) => {
    entries.forEach((entry) => {
      if (entry.isIntersecting) {
        entry.target.classList.add('visible');
        observer.unobserve(entry.target);
      }
    });
  },
  { threshold: 0.1 }
);
```

## スタガリング

リスト要素やカード群を順番にアニメーションさせるスタガリングパターン。

### 基本実装

```css
.stagger-item {
  opacity: 0;
  transform: translateY(16px);
  animation: stagger-in 300ms var(--ease-out-quart) forwards;
  animation-delay: calc(var(--i, 0) * 50ms);
}

@keyframes stagger-in {
  to {
    opacity: 1;
    transform: translateY(0);
  }
}
```

```html
<ul>
  <li class="stagger-item" style="--i: 0">アイテム1</li>
  <li class="stagger-item" style="--i: 1">アイテム2</li>
  <li class="stagger-item" style="--i: 2">アイテム3</li>
</ul>
```

**判断基準：**
- 各アイテム間のディレイは 30-80ms が適切である（50ms を推奨）
- 合計スタガー時間に上限を設定する。全体が長すぎると効果が薄れ、ユーザーを待たせる
- 合計スタガー時間は 300-500ms 以内に収める
- アイテム数が多い場合は、表示されている要素のみスタガリングし、残りは一括で表示する

## prefers-reduced-motion 対応

### 必須対応（オプションではない）

`prefers-reduced-motion` への対応は**必須**であり、オプションではない。

**対応が必要な理由：**
- 40歳以上の成人の約35%がモーションに敏感である
- 前庭障害を持つユーザーにとって、過度なアニメーションは身体的な不快感を引き起こす
- WCAG 2.1 の達成基準 2.3.3（インタラクションによるアニメーション）に関連する

### 実装パターン

```css
/* 装飾的アニメーションをクロスフェードに代替 */
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.2s !important;
  }

  /* クロスフェードは維持する（移動を伴わない opacity 変化） */
  .fade-transition {
    transition: opacity 0.2s ease;
  }
}
```

**判断基準：**
- 装飾的アニメーション（エントランス、パララックス、ホバーエフェクト等）は無効化またはクロスフェードに代替する
- 機能的インジケーター（ローディングスピナー、プログレスバー等）は維持する。処理中であることを伝えるフィードバックは無効化してはならない
- アニメーションを完全に削除するのではなく、クロスフェード（`opacity` のみのトランジション）で代替する

## 知覚的パフォーマンス

ユーザーが感じる速度は、実際の処理速度とは異なる。
モーションデザインで知覚的なパフォーマンスを向上させる。

### 80ms 閾値

- 操作から 80ms 以内にフィードバックがあれば、ユーザーは「即座」と感じる
- この閾値を超えると「待っている」感覚が生じ始める
- ボタンの `:active` 状態等、即座のフィードバックはこの閾値内に収める

### 先行開始（Preemptive Start）

ユーザーがアクションを起こす前にアニメーションの準備を開始する。

**例：**
- `mousedown` でアニメーション準備を開始し、`click` で本アニメーションを実行する
- `hover` でリソースのプリフェッチを開始する

### 早期完了（オプティミスティックUI）

処理が完了する前にUIを成功状態に更新する。

**適するケース：**
- いいね、ブックマーク等のリスクが低い操作
- テキストの保存

**適さないケース：**
- 決済処理
- データの削除
- 外部サービスへの送信

### 知覚時間の圧縮

- タスク終了に向けて `ease-in` を適用すると、知覚的な待ち時間が短く感じる
- プログレスバーが最後に加速するパターンは、実際の処理時間と無関係に体感速度を向上させる

## 判断に迷いやすいポイント

### アニメーションを付けるべきか、付けないべきか

**判断基準：**
1. そのアニメーションは状態変化を伝えているか（機能的か）
2. ユーザーの操作に対するフィードバックになっているか
3. 空間的な関係性の理解を助けているか

**判断例：**
- タブ切り替え時のコンテンツスライド → 付ける（空間的関係性の伝達）
- ページ全体のフェードイン → コンテキスト次第（初回訪問では効果的、ページ内遷移では不要な場合あり）
- ボタンのホバーエフェクト → 付ける（インタラクションフィードバック）
- ロゴの回転アニメーション → 付けない（装飾的、目的が不明確）

**トレードオフ：**
- ガイドとしてのアニメーション vs 注意散漫
- 判断：ユーザーのタスク達成を支援するなら付ける。タスクから注意を逸らすなら付けない

### デュレーションの微調整

**判断基準：**
1. 要素のサイズ（大きい要素ほど長いデュレーション）
2. 移動距離（距離が長いほど長いデュレーション）
3. 操作の頻度（頻繁な操作ほど短いデュレーション）

**判断例：**
- ドロップダウンの開閉（頻繁、小さい） → 200ms
- モーダルの表示（まれ、大きい） → 300-400ms
- ページ遷移（まれ、全体） → 500ms

**トレードオフ：**
- 知覚的パフォーマンス vs 実装複雑性
- 判断：高頻度の操作ほどパフォーマンス最適化の投資対効果が高い

### バウンス/エラスティック vs スムーズな減速

**判断基準：**
- バウンス/エラスティックは原則として使用しない
- 例外：ゲーム的なインターフェースや、意図的に遊び心を演出する場合のみ検討
- ビジネスアプリケーション、情報提供サイトでは使用しない

**トレードオフ：**
- デライト vs 抑制
- 判断：プロフェッショナルな印象を優先する場合はスムーズな減速。カジュアルな体験を優先する場合でもバウンスは慎重に

## よくある失敗パターン

- **バウンス/エラスティックイージングの使用**
  - 例：ボタンクリック時にバウンスアニメーションを付ける
  - 改善：`ease-out-quart` や `ease-out-quint` でスムーズに減速させる

- **レイアウトプロパティのアニメーション**
  - 例：`width` や `height` をトランジションで変化させる
  - 改善：`transform: scale()` や `grid-template-rows` で代替する

- **目的のないアニメーション**
  - 例：装飾のためだけにロゴを回転させる、背景をパルスさせる
  - 改善：すべてのアニメーションに機能的な目的（フィードバック、空間関係、状態変化の伝達）を持たせる

- **過剰なアニメーション**
  - 例：ページ上のすべての要素が独立してアニメーションする
  - 改善：注目すべき変化にのみアニメーションを適用し、全体の動きを抑制する

- **prefers-reduced-motion 未対応**
  - 例：モーション設定を無視してすべてのアニメーションを実行する
  - 改善：`@media (prefers-reduced-motion: reduce)` でクロスフェードに代替し、機能的インジケーターのみ維持する

- **CSSデフォルトの `ease` に依存**
  - 例：`transition: all 0.3s ease` のようにデフォルトイージングを使い回す
  - 改善：用途に応じた指数関数カーブをカスタムプロパティとして定義し、使い分ける

- **`will-change` の乱用**
  - 例：すべてのアニメーション要素に `will-change: transform` を設定する
  - 改善：`will-change` は使用せず、ブラウザの最適化に任せる。測定で問題が確認された場合のみ限定的に使用する

- **scroll イベントリスナーによるスクロールアニメーション**
  - 例：`window.addEventListener('scroll', ...)` で要素の表示を制御する
  - 改善：Intersection Observer API を使用する

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `animate-ui` — アニメーション実装時のデュレーション・イージング・性能ルールの判断に参照

- デュレーションとイージングの選定時にデフォルト値として参照する
