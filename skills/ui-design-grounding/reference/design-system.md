## このドキュメントの役割
UI/UXの設計・実装における**デザインシステムの設計と運用の判断基準と原則**を提供する。デザインシステムとは、UIコンポーネントとその使用ルールを再利用可能な形で体系化したもの。

## デザインシステムとは何か

**UIコンポーネント、デザイントークン、ガイドライン、パターンを体系的に整理し再利用可能にしたもの**。目的：

- UIの一貫性確保
- 開発・デザイン効率の向上
- 品質の標準化
- チーム間コミュニケーション改善
- 変更への対応力向上

## デザインシステムの構成要素

### デザイントークン（Design Tokens）

UIの見た目を「値」ではなく「意味」で管理する仕組み。トークンはデザインシステムの基盤であり、コンポーネントはトークンを使って構築される。詳細は `reference/design-tokens.md` を参照。

### コンポーネント（Components）

再利用可能なUI部品。**種類：**
- **原子**（Atoms）：ボタン、入力フィールド、アイコン等
- **分子**（Molecules）：検索フォーム、カード等
- **組織**（Organisms）：ヘッダー、フッター、サイドバー等
- **テンプレート**（Templates）：ページレイアウト等

### パターン（Patterns）

複数のコンポーネントを組み合わせた、よく使われるUIパターン。例：モーダルダイアログ、フォーム入力、一覧表示。

### ガイドライン（Guidelines）

コンポーネントやパターンの使用方法・判断基準。プロジェクト固有のガイドラインは `/init-design` で DESIGN.md として管理する。DESIGN.md は「リポジトリの視覚的アイデンティティの憲法」であり、本ドキュメントのデザインシステム理論を特定プロジェクトの具体値（トークン）と指針に落とし込んだ成果物。その**フォーマット仕様**は `design-md-spec.md` が定義し、`/init-design` のほか `/extract-ui`・`/audit-ui` 等も DESIGN.md を読み書きしうる。

## コンポーネント設計の原則

### 粒度の考え方

**判断基準：**
- **単一責任**：1コンポーネントは1つの責務を持つ
- **再利用性**：複数の文脈で使えるか
- **変更の影響範囲**：変更時の影響範囲が明確か

細かく分割するかまとめるかは、変更の単位と再利用性のバランスで判断する。例：ボタンは細かく分割（基本／アイコン／リンク）、フォームは適度にまとめる（入力フィールド・ラベル・エラーメッセージを1つに）。

### 責務の分離

**コンポーネントの責務：**
- **見た目（Presentation）**：スタイリング、レイアウト
- **状態管理（State）**：内部状態、プロパティ
- **動作（Behavior）**：イベントハンドリング、インタラクション

**判断基準：** 見た目と動作を分離できるか、状態管理をどこに置くか（コンポーネント内／親／グローバル）。例：単純なボタンは見た目と動作をコンポーネント内に、複雑なフォームは状態管理を親や状態管理ライブラリに。

### 再利用性の設計

**判断基準：**
- 複数の文脈で使えるか
- カスタマイズ可能か（props、スロット等）
- 過度な抽象化をしていないか

汎用性と使いやすさが衝突する場合は、80%のケースをカバーする汎用性を目指し、特殊ケースは別コンポーネントで対応する。

### バリアント（Variant）の設計

**判断基準：**
- 意味のある違いを表すか
- 組み合わせが複雑になりすぎていないか
- 将来の拡張を考慮しているか

例：ボタンは size（sm, md, lg）・variant（primary, secondary）・state（disabled, loading）、カードは elevation（flat, raised）・padding（sm, md, lg）。

## デザインシステムの範囲

### 含めるべきもの

- **頻繁に使われるコンポーネント**
- **一貫性が重要なコンポーネント**（ボタン、入力フィールド等）
- **複数の画面で共有されるパターン**
- **ブランド表現に関わる要素**（色、タイポグラフィ等）

### 含めない方がよいもの

- **一度しか使われない特殊なコンポーネント**
- **プロジェクト固有のビジネスロジック**
- **実験的なUI要素**（安定するまで含めない）

**判断基準：** 3回以上使われるならシステムに含める。ただし過度な抽象化は避ける。

## トークンとの関係

デザインシステムはデザイントークンを基盤に構築される。

**関係性：**
- トークン：値の集合（色、余白、フォント等）
- コンポーネント：トークンを使用して構築
- パターン：コンポーネントを組み合わせて構築

**判断基準：** コンポーネントは直接値を指定せずトークンを使用する。特殊な値が必要な場合のみコンポーネント固有のトークンを定義（`design-tokens.md` の Component Tokens を参照。DESIGN.md の `components` セクションは semantic を参照する適用仕様であり、これとは別物）。

> トークンの階層モデルと正規の役割語彙（Material 3 系）は `design-tokens.md` が単一所有者として定義する。本ドキュメントはその語彙を用いるのみで、階層や命名を独自に再定義しない。DESIGN.md での具体的な書式は `design-md-spec.md` を参照。

## 運用と更新の考え方

### 段階的な構築

完璧を目指さず必要最小限から始め、頻繁に使われるコンポーネントから優先的に整備し、使用しながら改善する。アプローチ：(1) 最小セット（ボタン・入力フィールド・カード等）を整備、(2) 使用しながら不足を発見、(3) 必要に応じて追加・改善。

### バージョン管理

**判断基準：** 破壊的変更はバージョンアップで管理し、後方互換を保つ期間を設け、非推奨（deprecated）のプロセスを明確にする。例：小さな改善は同バージョン内で更新、大きな変更は新バージョンとして提供し旧バージョンも一定期間維持。

### ドキュメント化

**含めるべき内容：** コンポーネントの目的と使用場面、props の説明、使用例（コード・視覚）、アクセシビリティの考慮事項、よくある間違い・注意点。

**判断基準：** 実装の詳細より使い方を重視し、「使う人」の視点で書く。

## 判断に迷いやすいポイント

### システムに含めるか、個別実装か

**判断基準：** (1) 使用頻度（3回以上ならシステムに）、(2) 一貫性の重要性、(3) 抽象化の複雑さ（過度な抽象化は避ける）。例：汎用的なボタンはシステムに含め、特殊なビジネスロジックを含むコンポーネントは個別実装。

### バリアントの粒度

**判断基準：** 意味のある違いをバリアントとして定義し、装飾的な違いは props で対応する。乱用すると設計が破綻するため必要最小限に絞る。例：ボタンは primary/secondary と size 程度、カードは elevation と padding 程度に限定。

### 破壊的変更の扱い

**判断基準：** 既存利用箇所への影響が大きいか、移行期間・互換性を確保できるか。破壊的変更はメジャーバージョンで告知し段階移行する。

## よくある失敗パターン

- **過度な抽象化** — あらゆるケースに対応しようとして複雑化。改善：80%のケースをカバーする設計に留める。
- **ドキュメントの不足** — 使い方が不明確。改善：使用例と注意点を明確に記す。
- **一貫性の欠如** — 同じ機能が異なる見た目・動作。改善：システムの範囲を明確にし使用を徹底。
- **更新プロセスの不明確さ** — 変更時の影響範囲が不明。改善：バージョン管理と非推奨プロセスを明確化。
- **実装とデザインの乖離** — デザインと実装が一致しない。改善：定期的なレビューと同期プロセス。

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `design-ui` — UI設計時のデザインシステム構成・コンポーネント設計に参照
- `implement-ui` — UI実装時のコンポーネント粒度・責務分離の判断に参照
- `extract-ui` — トークン・コンポーネント抽出・リファクタリング時に参照
- `init-design` — DESIGN.md 生成時のデザインシステム構成・含める/含めないの判断に参照
- コンポーネント設計時の判断基準として参照する
- デザインシステムの構築・運用計画の判断材料として使う

**関連リファレンス:**
- `design-tokens.md` — トークンの階層構造・命名・段階導入の詳細
- `design-md-spec.md` — DESIGN.md のフォーマット仕様（システム理論を成果物に落とす出力契約）
- `implementation.md` — コンポーネント粒度・責務分離の実装観点
- `color-system.md` — カラーパレット・セマンティックカラーのシステム設計
