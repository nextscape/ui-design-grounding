## このドキュメントの役割
このドキュメントは、UI/UXデザインおよび実装における
**アクセシビリティの判断基準と実践的な指針**を提供する。

特定のプロジェクトや技術スタックに依存しない、
汎用的なアクセシビリティ原則を整理する。

## アクセシビリティとは何か

アクセシビリティとは、
**多様な能力や状況にあるユーザーが、同じ情報にアクセスし、同じ機能を利用できること**である。

以下を目的とする：

- 障害のあるユーザーが利用できる
- 一時的な制約（片手操作、画面が眩しい環境等）に対応できる
- 技術的制約（古いブラウザ、低速回線等）に対応できる
- 結果として、すべてのユーザーの使いやすさが向上する

## アクセシビリティの基本原則（WCAG準拠）

WCAG（Web Content Accessibility Guidelines）の4つの原則：

### 知覚可能（Perceivable）
情報とUIコンポーネントは、ユーザーが知覚できる方法で提示されなければならない。

#### テキストの代替手段（alt属性）

画像のalt属性は、画像そのものの説明ではなく、**画像が伝えている情報**を記述する。

**ガイドライン：**
- 情報を持つ画像：画像が伝えている情報を簡潔に記述する
  - 良い例：`alt="売上が3月から6月にかけて150%増加"`（グラフの場合）
  - 悪い例：`alt="棒グラフ"`
- 装飾的な画像：`alt=""`（空のalt属性）を設定する。altを省略してはならない
- リンク内の画像：リンク先の内容を示すalt属性を設定する
- 複雑な画像（図表等）：`aria-describedby`で詳細な説明を提供する

**リンクテキストのガイドライン：**
- リンクテキストは単独で意味が分かるようにする
  - 良い例：`<a href="...">利用規約を読む</a>`
  - 悪い例：`<a href="...">こちら</a>`

#### 色だけに依存しない情報伝達

- 色以外の手段（アイコン、テキスト、パターン等）でも情報を伝える
- エラー表示：色だけでなく、アイコンやテキストも併用する

#### 色のコントラスト

WCAG AAレベルのコントラスト比基準：

| 対象 | 必要なコントラスト比 |
|------|---------------------|
| 通常テキスト（18pt未満、または14pt未満の太字） | 4.5:1 以上 |
| 大きなテキスト（18pt以上、または14pt以上の太字） | 3:1 以上 |
| UIコンポーネントやグラフィック | 3:1 以上 |
| プレースホルダーテキスト | 4.5:1 以上 |

**注意事項：**
- プレースホルダーテキストも通常テキストと同じ4.5:1の基準を満たす必要がある
- 装飾的なテキスト（ロゴ等）は例外となる場合がある
- ただし、情報伝達に必要な場合は基準を満たすこと

#### アクセシブルなフォントサイズ

テキストの拡大可能性を確保し、WCAG 1.4.4（テキストのサイズ変更）に準拠する。

**ガイドライン：**
- フォントサイズは `rem` または `em` を使用する。`px` を使用しない
- ボディテキストの最小サイズは `16px`（`1rem`）相当とする
- ビューポートのメタタグで `user-scalable=no` を設定してはならない
- `maximum-scale=1` の設定も避ける
- テキストが200%まで拡大された際にもコンテンツが利用可能であること

**実装例：**
```css
html {
  font-size: 100%; /* ブラウザのデフォルト（通常16px）を尊重 */
}

body {
  font-size: 1rem;
  line-height: 1.5;
}

h1 {
  font-size: 2rem;
}

small {
  font-size: 0.875rem; /* 14px相当。これより小さくしない */
}
```

```html
<!-- 正しい設定 -->
<meta name="viewport" content="width=device-width, initial-scale=1">

<!-- 避けるべき設定 -->
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no">
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">
```

#### モーションとアニメーション（prefers-reduced-motion）

**40歳以上の成人の約35%がモーションに敏感**であり、モーションの制御は優先度の高いアクセシビリティ要件である。

**ガイドライン：**
- `prefers-reduced-motion: reduce` を必ず実装する
- アニメーションを完全に削除するのではなく、**クロスフェードで代替**する
  - ユーザーにフィードバックが伝わらなくなることを防ぐ
- 機能的なアニメーション（ローディングスピナー、プログレスバー等）は維持する
- 装飾的なアニメーション、パララックス、自動再生の動画は無効化する

**実装例：**
```css
/* デフォルト：アニメーションあり */
.element {
  transition: transform 0.3s ease, opacity 0.3s ease;
}

/* モーション軽減時：クロスフェードで代替 */
@media (prefers-reduced-motion: reduce) {
  .element {
    transition: opacity 0.2s ease;
    transform: none !important;
    animation: none !important;
  }
}

/* 機能的なアニメーションは維持 */
@media (prefers-reduced-motion: reduce) {
  .loading-spinner {
    /* スピナーは維持する - 処理中であることを伝える重要なフィードバック */
    animation: spin 1s linear infinite;
  }
}
```

### 操作可能（Operable）
UIコンポーネントとナビゲーションは操作可能でなければならない。

#### キーボード操作の完全サポート

**基本操作パターン：**
- `Tab` / `Shift+Tab` でフォーカス移動
- `Enter` / `Space` で実行
- `Esc` でキャンセル・閉じる
- 矢印キーで選択肢を移動（メニュー、タブ、ラジオボタン等）

**キーボードナビゲーションパターン：**
- コンポーネントグループ間は `Tab` で移動する
- コンポーネントグループ内は矢印キーで移動する（ロービング・タブインデックス）
- ロービング・タブインデックス：グループ内の現在アクティブな要素のみ `tabindex="0"`、他は `tabindex="-1"` に設定する

**実装パターン例（タブコンポーネント）：**
```html
<div role="tablist">
  <button role="tab" tabindex="0" aria-selected="true">タブ1</button>
  <button role="tab" tabindex="-1" aria-selected="false">タブ2</button>
  <button role="tab" tabindex="-1" aria-selected="false">タブ3</button>
</div>
```
- `Tab` でタブリスト全体にフォーカスを移動
- 矢印キーでタブ間を移動
- `Tab` で次のコンポーネントグループへ移動

#### フォーカスリング

フォーカスインジケーターは、キーボード操作ユーザーにとって現在地を示す最も重要な視覚的手がかりである。

**ガイドライン：**
- `:focus` ではなく **`:focus-visible`** を使用する
  - `:focus` はマウスクリック時にも表示されてしまう
  - `:focus-visible` はキーボード操作時のみ表示される
- フォーカスリングの太さは **2-3px** とする
- `outline-offset` でフォーカスリングと要素の間にスペースを確保する
- フォーカスリングのコントラスト比は **3:1以上** とする
- `outline: none` を使用する場合は、必ず代替のフォーカススタイルを提供する

**実装例：**
```css
:focus-visible {
  outline: 2px solid var(--color-focus);
  outline-offset: 2px;
}

/* outline: none を使う場合は代替スタイルを必ず提供 */
.custom-button:focus-visible {
  outline: none;
  box-shadow: 0 0 0 3px var(--color-focus);
}
```

#### スキップリンク

ページの先頭に配置し、キーボードユーザーがナビゲーションを飛ばしてメインコンテンツに直接移動できるようにする。

**ガイドライン：**
- ページ内の最初のフォーカス可能な要素として配置する
- 通常は視覚的に非表示にし、フォーカス時に表示する
- リンク先は `#main-content`（メインコンテンツ領域のID）とする

**実装例：**
```html
<body>
  <a href="#main-content" class="skip-link">メインコンテンツへスキップ</a>
  <header><!-- ナビゲーション等 --></header>
  <main id="main-content">
    <!-- メインコンテンツ -->
  </main>
</body>
```

```css
.skip-link {
  position: absolute;
  top: -100%;
  left: 0;
  padding: 0.5rem 1rem;
  background: var(--color-background);
  color: var(--color-text);
  z-index: 1000;
  text-decoration: underline;
}

.skip-link:focus {
  top: 0;
}
```

#### タッチターゲット

モバイルユーザーが正確にタップできるよう、十分なタッチターゲットサイズを確保する。

**ガイドライン：**
- 最小タップ領域は **44px x 44px** とする
- 視覚的には24px程度のサイズでも、タップ領域は44pxを確保する
- 擬似要素を使用してタップ領域を拡張できる

**実装例：**
```css
/* 視覚的には小さいが、タップ領域は44pxを確保 */
.small-button {
  position: relative;
  width: 24px;
  height: 24px;
}

.small-button::after {
  content: '';
  position: absolute;
  top: 50%;
  left: 50%;
  transform: translate(-50%, -50%);
  width: 44px;
  height: 44px;
}
```

#### 十分な操作時間の提供

- タイムアウトがある場合は、ユーザーが延長・無効化できるようにする
- 自動更新するコンテンツは一時停止・停止できるようにする

#### 発作を引き起こすコンテンツの回避

- 1秒間に3回以上の点滅を避ける
- `prefers-reduced-motion` と組み合わせて制御する

### 理解可能（Understandable）
情報とUIの操作は理解可能でなければならない。

- 読みやすさと予測可能性
- 入力支援とエラー防止
- 一貫性のある操作パターン
- エラーメッセージの具体的な記述と解決方法の提示

### 堅牢（Robust）
コンテンツは、支援技術を含む様々なユーザーエージェントで解釈可能でなければならない。

- マークアップの妥当性
- セマンティックHTMLの使用（div/spanの乱用を避ける）
- ARIA属性の適切な使用（セマンティックHTMLで足りない場合のみ）

## 判断に迷いやすいポイント

### 色のコントラスト

**判断基準：**
- 通常テキスト（18pt未満、または14pt未満の太字）：コントラスト比 4.5:1 以上
- 大きなテキスト（18pt以上、または14pt以上の太字）：コントラスト比 3:1 以上
- UIコンポーネントやグラフィック：コントラスト比 3:1 以上
- プレースホルダーテキスト：コントラスト比 4.5:1 以上

**判断に迷うケース：**
- 装飾的なテキスト（ロゴ、アイコン等）は例外となる場合がある
- ただし、情報伝達に必要な場合は基準を満たす
- プレースホルダーテキストは薄い色にしがちだが、基準を満たす必要がある

**トレードオフ：**
- デザインの自由度 vs アクセシビリティ
- 判断：情報伝達が目的なら基準を満たす。装飾のみなら例外も可

### キーボード操作

**判断基準：**
- すべてのインタラクティブ要素がキーボードで操作可能
- フォーカス順序が論理的
- フォーカスインジケーターが視認可能

**判断に迷うケース：**
- モーダルダイアログのフォーカストラップ
- ドロップダウンメニューの操作
- カスタムコンポーネントのキーボード操作

**実装パターン：**
- Tab / Shift+Tab で移動
- Enter / Space で実行
- Esc でキャンセル・閉じる
- 矢印キーで選択肢を移動（メニュー等）
- ロービング・タブインデックスでグループ内ナビゲーション

### スクリーンリーダー対応

**判断基準：**
- セマンティックHTMLを優先使用
- ARIA属性は必要な場合のみ追加
- ランドマーク（header, nav, main, aside, footer）の適切な使用

**判断に迷うケース：**
- 装飾的な要素にaria-hiddenを付けるか
- 動的に変化するコンテンツのaria-live設定
- 複雑なUIコンポーネントのARIAロール選択

**実装パターン：**
- 見出し階層（h1-h6）の適切な使用
- リスト（ul, ol）の適切な使用
- フォームラベルの明確な関連付け（label要素、aria-labelledby）
- エラーメッセージのaria-describedbyでの関連付け

### フォーカス管理

**判断基準：**
- フォーカス可能な要素には視覚的なフォーカスインジケーター（`:focus-visible` を使用）
- フォーカス順序が論理的（DOM順序と視覚順序の一致）
- フォーカストラップの適切な実装（モーダル等）

**判断に迷うケース：**
- カスタムフォーカススタイルのデザイン
- スキップリンクの必要性
- 動的コンテンツ追加時のフォーカス移動

**実装パターン：**
- `:focus-visible` で代替のフォーカススタイルを提供
- モーダル表示時は背景要素にtabindex="-1"を設定し、フォーカスをモーダル内に閉じる
- コンテンツ更新時は、適切な要素にフォーカスを移動

## 実装時の判断基準とトレードオフ

### アクセシビリティ vs デザインの自由度

**判断軸：**
1. 情報伝達が目的か、装飾が目的か
2. 代替手段があるか（色だけでなく、アイコンやテキストでも伝わるか）
3. ユーザーの操作に影響するか

**判断例：**
- エラー表示：色だけでなく、アイコンやテキストも併用 → アクセシビリティ優先
- 装飾的なグラデーション背景：情報伝達に不要 → デザイン優先も可

### アクセシビリティ vs 実装コスト

**判断軸：**
1. 影響範囲（多くのユーザーが使う機能か）
2. 実装の複雑さ（既存パターンで対応できるか）
3. 段階的改善の可能性

**判断例：**
- 主要なフォーム：完全なアクセシビリティ対応を優先
- 内部ツールの補助機能：段階的改善も可（ただし最低限の対応は必須）

### アクセシビリティ vs パフォーマンス

**判断軸：**
1. アクセシビリティ機能がパフォーマンスに与える影響
2. 代替実装方法の有無

**判断例：**
- ARIA属性の追加：パフォーマンスへの影響はほぼなし → アクセシビリティ優先
- アニメーションのprefers-reduced-motion対応：パフォーマンス向上にも寄与 → 両立可能

## よくある失敗パターン

- **色だけに依存した情報伝達**
  - 例：エラーを赤色だけで示す
  - 改善：アイコンやテキストも併用

- **フォーカスインジケーターの削除**
  - 例：outline: none のみで代替スタイルなし
  - 改善：`:focus-visible` でカスタムフォーカススタイルを提供

- **セマンティックHTMLの不使用**
  - 例：div要素でボタンを作る
  - 改善：button要素を使用、または適切なARIAロールを設定

- **動的コンテンツの変更を通知しない**
  - 例：Ajaxで更新してもスクリーンリーダーに通知しない
  - 改善：aria-live属性や適切なフォーカス移動

- **キーボード操作の不完全な実装**
  - 例：カスタムコンポーネントがマウス操作のみ
  - 改善：キーボードイベントハンドラの実装、ロービング・タブインデックスの適用

- **pxベースのフォントサイズ指定**
  - 例：`font-size: 14px` でユーザーのブラウザ設定を無視
  - 改善：`rem` / `em` を使用し、ブラウザのデフォルト設定を尊重

- **user-scalable=noの設定**
  - 例：ビューポートでズームを無効化
  - 改善：`user-scalable=no` と `maximum-scale=1` を削除

- **prefers-reduced-motionの未対応**
  - 例：モーションに敏感なユーザーがアニメーションを制御できない
  - 改善：`prefers-reduced-motion: reduce` でクロスフェードに代替

- **プレースホルダーテキストのコントラスト不足**
  - 例：プレースホルダーが薄すぎて読めない
  - 改善：プレースホルダーテキストも4.5:1のコントラスト比を確保

## 段階的な改善アプローチ

すべてを一度に完璧にする必要はない。以下の優先順位で段階的に改善する。

### 優先度1（必須）
- キーボード操作の完全サポート
- 十分なコントラスト比（テキスト4.5:1、UI要素3:1、プレースホルダー4.5:1）
- セマンティックHTMLの基本使用
- `prefers-reduced-motion` 対応（クロスフェードでの代替実装）

### 優先度2（重要）
- ARIA属性の適切な使用
- フォーカス管理の改善（`:focus-visible` の使用）
- エラーメッセージの明確な関連付け（`aria-describedby`）
- アクセシブルなフォントサイズ（`rem`/`em` の使用、最小16px）
- スキップリンクの実装

### 優先度3（推奨）
- 詳細なaria-labelの追加
- 高度なARIAパターン（ロービング・タブインデックス、複合ウィジェット等）

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `audit-ui` — 技術品質監査のアクセシビリティ評価時に参照
- `guard-ui` — エッジケース堅牢化のアクセシビリティチェック時に参照
- `adapt-ui` — レスポンシブ適応時のアクセシビリティ確保に参照
- `implement-ui` — UI実装時のアクセシビリティ要件として参照
- `animate-ui` — アニメーション実装時の prefers-reduced-motion 対応に参照
- `typeset-ui` — タイポグラフィ設定時のアクセシブルなフォントサイズ・コントラスト確保に参照
- UIレビュー時のアクセシビリティチェックリストとして使う
