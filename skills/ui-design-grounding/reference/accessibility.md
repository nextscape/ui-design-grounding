## このドキュメントの役割
UI/UXデザイン・実装における**アクセシビリティの判断基準と実践指針**を、特定の技術スタックに依存しない汎用原則として整理する。

## アクセシビリティとは何か
**多様な能力や状況のユーザーが、同じ情報にアクセスし、同じ機能を利用できること**。

- 障害のあるユーザーが利用できる
- 一時的な制約（片手操作、眩しい環境等）に対応
- 技術的制約（古いブラウザ、低速回線等）に対応
- 結果としてすべてのユーザーの使いやすさが向上する

## アクセシビリティの基本原則（WCAG準拠）

WCAG（Web Content Accessibility Guidelines）の4原則。

### 知覚可能（Perceivable）
情報とUIは、ユーザーが知覚できる方法で提示する。

#### テキストの代替手段（alt属性）

alt属性は画像そのものではなく、**画像が伝えている情報**を記述する。

- 情報を持つ画像：伝えている情報を簡潔に記述
  - 良い例（グラフ）：`alt="売上が3月から6月にかけて150%増加"` / 悪い例：`alt="棒グラフ"`
- 装飾的な画像：`alt=""`（空のalt）を設定。altの省略は不可
- リンク内の画像：リンク先の内容を示すaltを設定
- 複雑な図表：`aria-describedby` で詳細説明を提供

リンクテキストは単独で意味が分かるようにする。
- 良い例：`<a href="...">利用規約を読む</a>` / 悪い例：`<a href="...">こちら</a>`

#### 色だけに依存しない情報伝達

- 色以外の手段（アイコン、テキスト、パターン等）でも情報を伝える
- エラー表示：色だけでなくアイコンやテキストも併用

#### 色のコントラスト

WCAG AAレベルのコントラスト比基準：

| 対象 | 必要なコントラスト比 |
|------|---------------------|
| 通常テキスト（18pt未満、または14pt未満の太字） | 4.5:1 以上 |
| 大きなテキスト（18pt以上、または14pt以上の太字） | 3:1 以上 |
| UIコンポーネントやグラフィック | 3:1 以上 |
| プレースホルダーテキスト | 4.5:1 以上 |

- プレースホルダーも通常テキストと同じ4.5:1を満たす必要がある
- 装飾的テキスト（ロゴ等）は例外となる場合があるが、情報伝達に必要なら基準を満たす

#### アクセシブルなフォントサイズ

テキストの拡大可能性を確保し、WCAG 1.4.4（テキストのサイズ変更）に準拠する。

- フォントサイズは `rem`/`em` を使用し、`px` を使わない
- ボディテキストの最小は `16px`（`1rem`）相当
- ビューポートで `user-scalable=no`・`maximum-scale=1` を設定しない
- テキスト200%拡大時もコンテンツが利用可能であること

```css
html { font-size: 100%; } /* ブラウザのデフォルト（通常16px）を尊重 */
body { font-size: 1rem; line-height: 1.5; }
h1 { font-size: 2rem; }
small { font-size: 0.875rem; } /* 14px相当。これより小さくしない */
```

```html
<!-- 正しい -->
<meta name="viewport" content="width=device-width, initial-scale=1">
<!-- 避ける -->
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no">
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">
```

#### モーションとアニメーション（prefers-reduced-motion）

モーションの制御は優先度の高いアクセシビリティ要件（モーション過敏のユーザーへの配慮）。`prefers-reduced-motion: reduce` の実装は**必須**で、装飾的アニメーションはクロスフェードで代替し、機能的アニメーション（スピナー等）は維持する。**理由・必須性・実装コード（@media 例）は `motion-design.md`（prefers-reduced-motion 対応）が所有する。**

### 操作可能（Operable）
UIとナビゲーションは操作可能でなければならない。

#### キーボード操作の完全サポート

基本操作パターン：
- `Tab` / `Shift+Tab` でフォーカス移動
- `Enter` / `Space` で実行
- `Esc` でキャンセル・閉じる
- 矢印キーで選択肢を移動（メニュー、タブ、ラジオボタン等）

ナビゲーションパターン：
- コンポーネントグループ間は `Tab`、グループ内は矢印キーで移動（ロービング・タブインデックス）
- ロービング・タブインデックス：グループ内のアクティブ要素のみ `tabindex="0"`、他は `tabindex="-1"`

```html
<div role="tablist">
  <button role="tab" tabindex="0" aria-selected="true">タブ1</button>
  <button role="tab" tabindex="-1" aria-selected="false">タブ2</button>
  <button role="tab" tabindex="-1" aria-selected="false">タブ3</button>
</div>
```
`Tab` でタブリストへ移動 → 矢印キーでタブ間移動 → `Tab` で次のグループへ。

#### フォーカスリング

フォーカスインジケーターはキーボードユーザーが現在地を知る最重要の視覚的手がかり。

- `:focus` ではなく **`:focus-visible`** を使う（キーボード操作時のみ表示）
- 太さ **2-3px**、`outline-offset` でスペース確保、コントラスト比 **3:1以上**
- `outline: none` を使う場合は必ず代替（`box-shadow` 等）を提供

> 設計基準の詳細・実装コード（`:focus-visible` リセット、暗色背景対応、box-shadow 代替）は `interaction.md`（フォーカスリングの設計）が所有する。

#### スキップリンク

キーボードユーザーがナビゲーションを飛ばしてメインコンテンツへ直接移動できるよう、ページ先頭に配置する。

- ページ内の最初のフォーカス可能要素として配置
- 通常は視覚的に非表示にし、フォーカス時に表示
- リンク先は `#main-content`（メインコンテンツ領域のID）

```html
<body>
  <a href="#main-content" class="skip-link">メインコンテンツへスキップ</a>
  <header><!-- ナビゲーション等 --></header>
  <main id="main-content"><!-- メインコンテンツ --></main>
</body>
```

```css
.skip-link {
  position: absolute; top: -100%; left: 0;
  padding: 0.5rem 1rem;
  background: var(--color-background);
  color: var(--color-text);
  z-index: 1000;
  text-decoration: underline;
}
.skip-link:focus { top: 0; }
```

#### タッチターゲット

モバイルで正確にタップできるよう十分なサイズを確保する。

- 最小タップ領域は **44px x 44px**
- 視覚的に24px程度でも、タップ領域は44pxを確保する
- 擬似要素でタップ領域を拡張できる

```css
/* 視覚的には小さいが、タップ領域は44pxを確保 */
.small-button { position: relative; width: 24px; height: 24px; }
.small-button::after {
  content: ''; position: absolute;
  top: 50%; left: 50%; transform: translate(-50%, -50%);
  width: 44px; height: 44px;
}
```

#### 十分な操作時間の提供

- タイムアウトはユーザーが延長・無効化できるようにする
- 自動更新コンテンツは一時停止・停止できるようにする

#### 発作を引き起こすコンテンツの回避

- 1秒間に3回以上の点滅を避ける
- `prefers-reduced-motion` と組み合わせて制御する

### 理解可能（Understandable）
情報とUIの操作は理解可能でなければならない。

- 読みやすさと予測可能性
- 入力支援とエラー防止
- 一貫性のある操作パターン
- エラーメッセージの具体的な記述と解決方法の提示

### 堅牢（Robust）
コンテンツは支援技術を含む様々なユーザーエージェントで解釈可能でなければならない。

- マークアップの妥当性
- セマンティックHTMLの使用（div/spanの乱用を避ける）
- ARIA属性は適切に使用（セマンティックHTMLで足りない場合のみ）

## 判断に迷いやすいポイント

### 色のコントラスト

判断基準（コントラスト比）：通常テキスト 4.5:1 以上 / 大きなテキスト 3:1 以上 / UI・グラフィック 3:1 以上 / プレースホルダー 4.5:1 以上。

- 迷うケース：装飾的テキスト（ロゴ、アイコン等）は例外となる場合があるが、情報伝達に必要なら基準を満たす。プレースホルダーは薄くしがちだが基準を満たす
- トレードオフ：デザインの自由度 vs アクセシビリティ → 情報伝達が目的なら基準を満たす、装飾のみなら例外も可

### キーボード操作

判断基準：すべてのインタラクティブ要素がキーボードで操作可能 / フォーカス順序が論理的 / フォーカスインジケーターが視認可能。

- 迷うケース：モーダルのフォーカストラップ、ドロップダウン操作、カスタムコンポーネント
- パターン：Tab/Shift+Tab で移動、Enter/Space で実行、Esc で閉じる、矢印キーで選択肢移動、ロービング・タブインデックスでグループ内ナビゲーション

### スクリーンリーダー対応

判断基準：セマンティックHTMLを優先 / ARIA属性は必要時のみ / ランドマーク（header, nav, main, aside, footer）を適切に使用。

- 迷うケース：装飾要素への aria-hidden、動的コンテンツの aria-live、複雑なコンポーネントのARIAロール選択
- パターン：見出し階層（h1-h6）・リスト（ul, ol）の適切な使用、フォームラベルの関連付け（label, aria-labelledby）、エラーの aria-describedby 関連付け

### フォーカス管理

判断基準：視覚的なフォーカスインジケーター（`:focus-visible`）/ フォーカス順序が論理的（DOM順序と視覚順序の一致）/ フォーカストラップの適切な実装（モーダル等）。

- 迷うケース：カスタムフォーカススタイル、スキップリンクの必要性、動的コンテンツ追加時のフォーカス移動
- パターン：`:focus-visible` で代替スタイル提供、モーダル表示時は背景要素を tabindex="-1" にしフォーカスをモーダル内に閉じる、コンテンツ更新時は適切な要素へフォーカス移動

## 実装時の判断基準とトレードオフ

### アクセシビリティ vs デザインの自由度
判断軸：①情報伝達が目的か装飾が目的か ②代替手段があるか ③ユーザー操作に影響するか。
- エラー表示：色だけでなくアイコン・テキスト併用 → アクセシビリティ優先
- 装飾的グラデーション背景：情報伝達に不要 → デザイン優先も可

### アクセシビリティ vs 実装コスト
判断軸：①影響範囲 ②実装の複雑さ ③段階的改善の可能性。
- 主要なフォーム：完全対応を優先
- 内部ツールの補助機能：段階的改善も可（最低限の対応は必須）

### アクセシビリティ vs パフォーマンス
判断軸：①パフォーマンスへの影響 ②代替実装の有無。
- ARIA属性の追加：影響ほぼなし → アクセシビリティ優先
- アニメーションの prefers-reduced-motion 対応：パフォーマンス向上にも寄与 → 両立可能

## よくある失敗パターン

- **色だけに依存した情報伝達**：エラーを赤色だけで示す → アイコン・テキストも併用
- **フォーカスインジケーターの削除**：outline: none のみで代替なし → `:focus-visible` でカスタムスタイル提供
- **セマンティックHTMLの不使用**：divでボタンを作る → button要素、または適切なARIAロール
- **動的コンテンツの変更を通知しない**：Ajax更新をスクリーンリーダーに伝えない → aria-live や適切なフォーカス移動
- **キーボード操作の不完全な実装**：カスタムコンポーネントがマウスのみ → キーボードイベント、ロービング・タブインデックス
- **pxベースのフォントサイズ**：`font-size: 14px` がブラウザ設定を無視 → `rem`/`em` を使用
- **user-scalable=noの設定**：ズーム無効化 → `user-scalable=no`・`maximum-scale=1` を削除
- **prefers-reduced-motionの未対応**：モーション過敏ユーザーが制御できない → `prefers-reduced-motion: reduce` でクロスフェード代替
- **プレースホルダーのコントラスト不足**：薄すぎて読めない → 4.5:1 を確保

## 段階的な改善アプローチ

すべてを一度に完璧にする必要はない。以下の優先順位で改善する。

### 優先度1（必須）
- キーボード操作の完全サポート
- 十分なコントラスト比（テキスト4.5:1、UI要素3:1、プレースホルダー4.5:1）
- セマンティックHTMLの基本使用
- `prefers-reduced-motion` 対応（クロスフェードでの代替）

### 優先度2（重要）
- ARIA属性の適切な使用
- フォーカス管理の改善（`:focus-visible`）
- エラーメッセージの明確な関連付け（`aria-describedby`）
- アクセシブルなフォントサイズ（`rem`/`em`、最小16px）
- スキップリンクの実装

### 優先度3（推奨）
- 詳細な aria-label の追加
- 高度なARIAパターン（ロービング・タブインデックス、複合ウィジェット等）
