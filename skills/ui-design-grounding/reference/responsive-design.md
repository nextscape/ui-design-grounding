## このドキュメントの役割
このドキュメントは、UI/UXデザインにおける
**レスポンシブデザインの判断基準と実践的な指針**を提供する。

画面サイズ、入力方式、デバイス特性に応じたUI適応の設計原則を体系化する。
特定のフレームワークに依存しない、汎用的なレスポンシブ設計の判断軸を提供する。

## レスポンシブデザインとは何か

レスポンシブデザインとは、
**デバイスや画面サイズに関わらず、最適な表示と操作体験を提供するための設計手法**である。

以下を目的とする：

- あらゆる画面サイズでのコンテンツの可読性と操作性
- デバイスの入力方式（タッチ、マウス、キーボード）への適応
- ネットワーク条件やデバイス性能への配慮
- コンテンツの優先順位に基づいた段階的な情報開示

## モバイルファースト

### min-width クエリを使用する

**モバイルファーストとは、基本スタイルをモバイル向けに記述し、メディアクエリで拡張すること**である。

```css
/* 基本スタイル = モバイル向け */
.container {
  padding: 1rem;
  display: flex;
  flex-direction: column;
  gap: 1rem;
}

/* タブレット以上で拡張 */
@media (min-width: 768px) {
  .container {
    padding: 2rem;
    flex-direction: row;
  }
}

/* デスクトップ以上でさらに拡張 */
@media (min-width: 1024px) {
  .container {
    max-width: 1200px;
    margin-inline: auto;
  }
}
```

**判断基準：**
- `min-width` クエリを使用する。`max-width` クエリ（デスクトップファースト）は使用しない
- デスクトップファーストだと、モバイルに不要なスタイルをロードした上で上書きすることになり、無駄が生じる
- 基本スタイルはモバイル向けに記述し、大きい画面に向けてメディアクエリで拡張する
- これにより、CSSの記述量が最小化され、モバイルでの読み込みパフォーマンスが向上する

## コンテンツ駆動ブレイクポイント

### デバイスサイズではなくコンテンツで決める

**ブレイクポイントは特定のデバイスサイズに合わせるのではなく、コンテンツが壊れる地点で設定する。**

**設定方法：**
1. 最も狭い画面幅（320px）から表示を確認する
2. 画面幅を徐々に広げていく
3. コンテンツのレイアウトが崩れた地点（テキストの折り返しが不自然、余白が広すぎる等）でブレイクポイントを設定する
4. 繰り返す

**判断基準：**
- 通常3つのブレイクポイントで十分である：約640px、約768px、約1024px
- デバイス名（iPhone、iPad等）でブレイクポイントを定義しない。デバイスの画面サイズは年々変化する
- ブレイクポイントの値は、コンテンツに合わせて調整してよい（例：680px、820px 等の中間値も可）

### フルードスケーリング

ブレイクポイント間で段階的ではなく滑らかにスケーリングする場合、`clamp()` を使用する。

```css
.heading {
  /* 最小: 1.5rem、推奨: 4vw、最大: 3rem */
  font-size: clamp(1.5rem, 4vw, 3rem);
}

.container {
  /* 最小: 1rem、推奨: 5vw、最大: 4rem */
  padding-inline: clamp(1rem, 5vw, 4rem);
}
```

**判断基準：**
- フォントサイズ、パディング、ギャップ等のスペーシングに `clamp()` を活用する
- `clamp()` を使用するとブレイクポイントの数を減らせる
- ただし、レイアウトの大きな変更（1カラム → 2カラム等）にはメディアクエリが適する

## 入力方式検出

### ポインターとホバーの検出

デバイスの入力方式に応じてUIを適応させるために、メディアクエリで入力特性を検出する。

```css
/* マウス/トラックパッド（精密なポインター） */
@media (pointer: fine) {
  .button {
    padding: 0.5rem 1rem;
  }
}

/* タッチ（粗いポインター） */
@media (pointer: coarse) {
  .button {
    padding: 0.75rem 1.25rem;
    min-height: 44px;
  }
}

/* ホバー可能なデバイス */
@media (hover: hover) {
  .card:hover {
    box-shadow: var(--shadow-md);
  }
}

/* ホバー不可能なデバイス */
@media (hover: none) {
  /* hover に依存しない代替UIを提供 */
}
```

**判断基準：**
- `pointer: fine` はマウス/トラックパッド（精密なポインティング）を示す
- `pointer: coarse` はタッチ操作（粗いポインティング）を示す
- `hover: hover` はホバー可能なデバイスを示す
- `hover: none` はホバー不可能なデバイス（タッチデバイス）を示す
- **hover に機能を依存させない。** ツールチップの中に重要な情報を入れてはならない。タッチデバイスではアクセスできない
- 入力タイプに基づいてパディング・タッチターゲットサイズを調整する

## セーフエリア

### ノッチ・丸角・ダイナミックアイランド対応

現代のモバイルデバイスにはノッチ、丸角、ダイナミックアイランド等の物理的な画面形状がある。
コンテンツがこれらの領域に隠れないよう、セーフエリアを考慮する。

```css
/* ビューポートをデバイス全体に拡張 */
/* <meta name="viewport" content="viewport-fit=cover"> が必要 */

.fixed-bottom-bar {
  position: fixed;
  bottom: 0;
  left: 0;
  right: 0;
  padding-bottom: env(safe-area-inset-bottom);
  padding-left: env(safe-area-inset-left);
  padding-right: env(safe-area-inset-right);
}

.page-content {
  padding-top: env(safe-area-inset-top);
}
```

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

**判断基準：**
- `env(safe-area-inset-top)`, `env(safe-area-inset-bottom)`, `env(safe-area-inset-left)`, `env(safe-area-inset-right)` を使用する
- `viewport-fit=cover` をメタタグに設定しないと `env()` の値が 0 になる
- 固定ボトムバー（ナビゲーション、CTA等）では特に `safe-area-inset-bottom` が重要
- 横向き表示では `safe-area-inset-left` と `safe-area-inset-right` も考慮する

## レスポンシブ画像

### srcset と sizes による最適化

デバイスの画面サイズと解像度に応じて、適切なサイズの画像を配信する。

```html
<img
  src="image-800.jpg"
  srcset="
    image-400.jpg 400w,
    image-800.jpg 800w,
    image-1200.jpg 1200w,
    image-1600.jpg 1600w
  "
  sizes="
    (min-width: 1024px) 50vw,
    (min-width: 768px) 75vw,
    100vw
  "
  alt="説明テキスト"
  loading="lazy"
/>
```

### picture 要素によるアートディレクション

画面サイズに応じて画像の構図（画角）自体を変える場合は `<picture>` 要素を使用する。

```html
<picture>
  <source media="(min-width: 1024px)" srcset="hero-wide.jpg" />
  <source media="(min-width: 768px)" srcset="hero-medium.jpg" />
  <img src="hero-narrow.jpg" alt="説明テキスト" />
</picture>
```

### 遅延読み込み

```html
<!-- ビューポート外の画像を遅延読み込み -->
<img src="image.jpg" alt="説明テキスト" loading="lazy" />

<!-- ファーストビューの画像は遅延読み込みしない -->
<img src="hero.jpg" alt="説明テキスト" loading="eager" />
```

**判断基準：**
- `srcset` + `sizes` で画面サイズに応じた画像を配信する
- 構図を変える場合のみ `<picture>` 要素を使用する（単なるリサイズなら `srcset` で十分）
- `loading="lazy"` でビューポート外の画像を遅延読み込みする
- ファーストビューの画像（ヒーロー画像等）には `loading="lazy"` を設定しない

## レイアウト適応パターン

### ナビゲーション

画面サイズに応じてナビゲーションの形態を変化させる。

| 画面サイズ | パターン |
|-----------|---------|
| モバイル | ハンバーガーメニュー |
| タブレット | コンパクトナビゲーション（アイコン + 省略ラベル） |
| デスクトップ | フルナビゲーションバー |

**判断基準：**
- ナビゲーション項目が5個以下であれば、モバイルでもボトムバーやタブバーで表示を検討する
- ハンバーガーメニューは発見性が低い。可能であれば主要な項目はボトムバーに常時表示する

### テーブル

**モバイルでテーブルを横スクロールさせるのは最後の手段とする。**

| 画面サイズ | パターン |
|-----------|---------|
| モバイル | カード形式に変換、または重要列のみ表示 |
| タブレット | 横スクロール付きテーブル |
| デスクトップ | フルテーブル |

### 段階的開示

情報量が多い場合、モバイルでは `<details>` / `<summary>` で折りたたむ。

```html
<details>
  <summary>詳細情報を表示</summary>
  <div class="details-content">
    <!-- 折りたたまれたコンテンツ -->
  </div>
</details>
```

### サイドバー

| 画面サイズ | パターン |
|-----------|---------|
| モバイル | ドロワー（オーバーレイ）または非表示 |
| タブレット | 折りたたみ式サイドバー |
| デスクトップ | 常時表示サイドバー |

## テスト

### DevTools のエミュレーションだけでは不十分

ブラウザの DevTools によるデバイスエミュレーションは便利だが、以下の点で実機テストの代替にはならない：

- タッチ操作の精度と感触
- 実際のネットワーク速度
- デバイス固有のブラウザ挙動（SafariのViewport挙動、Chromeのアドレスバー表示/非表示等）
- セーフエリアの実際の影響
- パフォーマンス（低スペックデバイスでの動作）

### 必須のテスト項目

**実機テスト：**
- iPhone（Safari）：iOS固有のViewport挙動、100vh問題、セーフエリア
- Android（Chrome）：多様な画面サイズ、アドレスバーの動的変化
- タブレット：iPad（Safari）、Androidタブレット

**画面方向：**
- 縦向き（Portrait）と横向き（Landscape）の両方をテストする
- 方向転換時のレイアウト崩れを確認する

**ネットワーク：**
- 低速ネットワークシミュレーション（3G相当）でのページ読み込みを確認する
- 画像の遅延読み込みが正しく動作しているか確認する

**判断基準：**
- 最低限、iPhone（Safari）とAndroid（Chrome）の実機テストを実施する
- タブレットテストは、タブレットユーザーが想定される場合に実施する
- 横向きテストは、動画やダッシュボード等の横幅が重要なコンテンツで必須

## 判断に迷いやすいポイント

### レスポンシブ vs アダプティブ

**判断基準：**
1. コンテンツが連続的にスケーリング可能か
2. デバイスごとに根本的に異なるUIが必要か
3. 開発・保守のリソースはどの程度か

**判断例：**
- ブログ、コーポレートサイト → レスポンシブ（単一のHTML/CSS、フルードスケーリング）
- 複雑なダッシュボード → アダプティブ要素を含むレスポンシブ（特定のブレイクポイントでレイアウトを大きく変更）
- モバイルアプリとデスクトップアプリ → アダプティブ（根本的に異なるUI）

**トレードオフ：**
- レスポンシブ対応の複雑さ vs 保守性
- 判断：単一のコードベースで管理可能であればレスポンシブを優先する。デバイスごとのUI差異が大きい場合はアダプティブを検討する

### コンポーネントレベル vs ページレベルのレスポンシブ

**判断基準：**
1. コンポーネントが異なるコンテキストで再利用されるか
2. コンポーネント自身が自分のレイアウトを制御すべきか

**判断例：**
- カードコンポーネント → コンポーネントレベル（Container Queries で自身のサイズに応じて適応）
- ページ全体のレイアウト → ページレベル（メディアクエリで画面サイズに応じて適応）

```css
/* Container Queries によるコンポーネントレベルのレスポンシブ */
.card-container {
  container-type: inline-size;
}

@container (min-width: 400px) {
  .card {
    flex-direction: row;
  }
}
```

**トレードオフ：**
- コンポーネントレベル vs ページレベル
- 判断：再利用されるコンポーネントは Container Queries でコンポーネントレベルの適応を検討する。ページ固有のレイアウトはメディアクエリで十分

### モバイルでの機能の扱い

**判断基準：**
1. その機能はモバイルユーザーにも必要か
2. 機能を適応（形を変える）できるか、切り捨てるしかないか
3. モバイルでの操作性は確保できるか

**判断例：**
- 複雑なフィルター → アコーディオンやモーダルに適応する（切り捨てない）
- データテーブル → カード形式に変換する（切り捨てない）
- 高度な設定画面 → モバイルでもアクセス可能にする（ただし段階的開示で情報量を制御する）

**トレードオフ：**
- アダプティブ vs レスポンシブ
- 判断：モバイルで重要な機能を非表示にしてはならない。適応（形を変える）すべきであり、切り捨てではない

### hover 依存の代替手段

**判断基準：**
- その情報は hover なしでもアクセス可能か
- タッチデバイスでの代替手段はあるか
- 情報の重要度はどの程度か

**判断例：**
- ツールチップ → タッチではタップで表示、またはラベルを常時表示
- テーブル行のアクションボタン → 常時表示、またはコンテキストメニューを提供
- プレビュー → クリック/タップで表示、またはインライン表示

## よくある失敗パターン

- **デスクトップファースト（max-width クエリ）**
  - 例：デスクトップ向けスタイルを基本とし、`max-width` で上書きする
  - 改善：モバイルファーストで `min-width` クエリを使用する

- **デバイス検出（User-Agent）による分岐**
  - 例：User-Agent 文字列でiPhoneかAndroidかを判定してスタイルを切り替える
  - 改善：メディアクエリによる機能検出（`pointer`, `hover`, `min-width` 等）を使用する。デバイスは常に新しいものが登場するため、User-Agent ベースの検出は保守不能になる

- **モバイルで重要機能を非表示にする**
  - 例：デスクトップでは表示されるフィルターや設定をモバイルでは `display: none` にする
  - 改善：機能を適応させる（形を変える）。アコーディオン、モーダル、ドロワー等で提供する

- **タブレット・横向きの無視**
  - 例：モバイルとデスクトップのみを考慮し、タブレットや横向き表示を未テスト
  - 改善：中間のブレイクポイントを設定し、タブレットでの表示と横向き表示をテストする

- **hover 依存の機能**
  - 例：テーブル行にホバーしないとアクションボタンが表示されない
  - 改善：`@media (hover: none)` でタッチデバイス向けの代替UIを提供する。重要なアクションは常時表示する

- **固定幅のレイアウト**
  - 例：`width: 1200px` のようにピクセル単位の固定幅を設定する
  - 改善：`max-width` と `width: 100%` を組み合わせる。または `clamp()` でフルードスケーリングを適用する

- **100vh の使用（モバイル）**
  - 例：`height: 100vh` でフルスクリーンレイアウトを実装するが、モバイルブラウザのアドレスバーを考慮していない
  - 改善：`height: 100dvh`（dynamic viewport height）を使用する。または `min-height: 100vh` にする

- **セーフエリア未考慮**
  - 例：固定ボトムバーがノッチやホームインジケーターと重なる
  - 改善：`env(safe-area-inset-bottom)` 等を適用する

- **画像の未最適化**
  - 例：すべてのデバイスで同じ高解像度画像を配信する
  - 改善：`srcset` + `sizes` で画面サイズに応じた画像を配信し、`loading="lazy"` で遅延読み込みする

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `adapt-ui` — レスポンシブ適応時のブレイクポイント・レイアウト適応パターンの判断に参照
- `audit-ui` — 技術品質監査のレスポンシブ対応評価時に参照
- `design-ui` — UI設計時のブレイクポイント・モバイルファースト設計に参照
- `implement-ui` — UI実装時のレスポンシブCSS実装に参照
- `optimize-ui` — パフォーマンス最適化時のレスポンシブ画像・遅延読み込みに参照
- `guard-ui` — エッジケース堅牢化時のデバイス・入力方式対応に参照
- モバイルファーストの方針とブレイクポイント設計の根拠として参照する
