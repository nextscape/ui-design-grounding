## このドキュメントの役割
UI/UXにおける**レスポンシブデザインの判断基準と実践指針**を提供する。画面サイズ・入力方式・デバイス特性に応じたUI適応の設計原則を、特定フレームワークに依存しない汎用的な判断軸として体系化する。

## レスポンシブデザインとは何か

**デバイスや画面サイズに関わらず、最適な表示と操作体験を提供する設計手法**。目的は以下：

- あらゆる画面サイズでのコンテンツの可読性と操作性
- 入力方式（タッチ、マウス、キーボード）への適応
- ネットワーク条件・デバイス性能への配慮
- コンテンツの優先順位に基づく段階的な情報開示

## モバイルファースト

### min-width クエリを使用する

**基本スタイルをモバイル向けに記述し、メディアクエリで拡張する**。

```css
/* 基本スタイル = モバイル向け */
.container {
  padding: 1rem;
  display: flex;
  flex-direction: column;
  gap: 1rem;
}

/* タブレット以上で拡張 */
@media (min-width: 768px) {
  .container { padding: 2rem; flex-direction: row; }
}

/* デスクトップ以上でさらに拡張 */
@media (min-width: 1024px) {
  .container { max-width: 1200px; margin-inline: auto; }
}
```

**判断基準：**
- `min-width` クエリを使う。`max-width`（デスクトップファースト）は使わない
- デスクトップファーストはモバイルに不要なスタイルをロードして上書きするため無駄が生じる
- 基本はモバイル向けに記述し、大きい画面へメディアクエリで拡張する
- CSS記述量が最小化され、モバイルの読み込みパフォーマンスが向上する

## コンテンツ駆動ブレイクポイント

### デバイスサイズではなくコンテンツで決める

**ブレイクポイントは特定デバイスサイズに合わせず、コンテンツが壊れる地点で設定する。**

**設定方法：** 最も狭い幅（320px）から表示を確認し、徐々に広げ、レイアウトが崩れた地点（テキストの折り返しが不自然、余白が広すぎる等）でブレイクポイントを置く。これを繰り返す。

**判断基準：**
- 通常3つで十分：約640px、約768px、約1024px
- デバイス名（iPhone、iPad等）で定義しない。画面サイズは年々変化する
- 値はコンテンツに合わせ調整してよい（例：680px、820px 等の中間値も可）

### フルードスケーリング

段階的でなく滑らかにスケーリングする場合は `clamp()` を使う。

```css
/* 最小, 推奨, 最大 */
.heading { font-size: clamp(1.5rem, 4vw, 3rem); }
.container { padding-inline: clamp(1rem, 5vw, 4rem); }
```

**判断基準：**
- フォントサイズ・パディング・ギャップ等のスペーシングに `clamp()` を活用する
- `clamp()` でブレイクポイント数を減らせる
- ただしレイアウトの大きな変更（1カラム→2カラム等）にはメディアクエリが適する

## 入力方式検出

### ポインターとホバーの検出

入力方式に応じてUIを適応させるため、メディアクエリで入力特性を検出する。

```css
@media (pointer: fine) {   /* マウス/トラックパッド */
  .button { padding: 0.5rem 1rem; }
}
@media (pointer: coarse) { /* タッチ */
  .button { padding: 0.75rem 1.25rem; min-height: 44px; }
}
@media (hover: hover) {    /* ホバー可能 */
  .card:hover { box-shadow: var(--shadow-md); }
}
@media (hover: none) {     /* ホバー不可 */
  /* hover に依存しない代替UIを提供 */
}
```

**判断基準：**
- `pointer: fine` = マウス/トラックパッド（精密）、`pointer: coarse` = タッチ（粗い）
- `hover: hover` = ホバー可能、`hover: none` = ホバー不可（タッチデバイス）
- **hover に機能を依存させない。** ツールチップに重要情報を入れない。タッチデバイスでアクセスできない
- 入力タイプに基づきパディング・タッチターゲットサイズを調整する

## セーフエリア

### ノッチ・丸角・ダイナミックアイランド対応

現代のモバイルデバイスにはノッチ・丸角・ダイナミックアイランド等の物理形状がある。コンテンツがこれらに隠れないようセーフエリアを考慮する。

```css
/* <meta ... viewport-fit=cover> が必要 */
.fixed-bottom-bar {
  position: fixed; bottom: 0; left: 0; right: 0;
  padding-bottom: env(safe-area-inset-bottom);
  padding-left: env(safe-area-inset-left);
  padding-right: env(safe-area-inset-right);
}
.page-content { padding-top: env(safe-area-inset-top); }
```

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

**判断基準：**
- `env(safe-area-inset-top / -bottom / -left / -right)` を使用する
- `viewport-fit=cover` をメタタグに設定しないと `env()` の値が 0 になる
- 固定ボトムバー（ナビ、CTA等）では特に `safe-area-inset-bottom` が重要
- 横向きでは `safe-area-inset-left` と `safe-area-inset-right` も考慮する

## レスポンシブ画像

### srcset と sizes による最適化

画面サイズと解像度に応じて適切なサイズの画像を配信する。

```html
<img
  src="image-800.jpg"
  srcset="image-400.jpg 400w, image-800.jpg 800w,
          image-1200.jpg 1200w, image-1600.jpg 1600w"
  sizes="(min-width: 1024px) 50vw, (min-width: 768px) 75vw, 100vw"
  alt="説明テキスト" loading="lazy" />
```

### picture 要素によるアートディレクション

画面サイズに応じて画像の構図（画角）自体を変える場合は `<picture>` を使う。

```html
<picture>
  <source media="(min-width: 1024px)" srcset="hero-wide.jpg" />
  <source media="(min-width: 768px)" srcset="hero-medium.jpg" />
  <img src="hero-narrow.jpg" alt="説明テキスト" />
</picture>
```

### 遅延読み込み

ビューポート外は `loading="lazy"`、ファーストビュー画像（ヒーロー等）は `loading="eager"`（lazy にしない）。

**判断基準：**
- `srcset` + `sizes` で画面サイズに応じた画像を配信する
- 構図を変える場合のみ `<picture>` を使う（単なるリサイズなら `srcset` で十分）
- `loading="lazy"` でビューポート外を遅延読み込み。ファーストビュー画像には設定しない

## レイアウト適応パターン

### ナビゲーション

| 画面サイズ | パターン |
|-----------|---------|
| モバイル | ハンバーガーメニュー |
| タブレット | コンパクトナビ（アイコン + 省略ラベル） |
| デスクトップ | フルナビゲーションバー |

**判断基準：**
- 項目が5個以下なら、モバイルでもボトムバー/タブバー表示を検討する
- ハンバーガーメニューは発見性が低い。可能なら主要項目はボトムバーに常時表示する

### テーブル

**モバイルでの横スクロールは最後の手段とする。**

| 画面サイズ | パターン |
|-----------|---------|
| モバイル | カード形式に変換、または重要列のみ表示 |
| タブレット | 横スクロール付きテーブル |
| デスクトップ | フルテーブル |

### 段階的開示

情報量が多い場合、モバイルでは `<details>` / `<summary>` で折りたたむ。

```html
<details>
  <summary>詳細情報を表示</summary>
  <div class="details-content"><!-- 折りたたみコンテンツ --></div>
</details>
```

### サイドバー

| 画面サイズ | パターン |
|-----------|---------|
| モバイル | ドロワー（オーバーレイ）または非表示 |
| タブレット | 折りたたみ式サイドバー |
| デスクトップ | 常時表示サイドバー |

## テスト

### DevTools のエミュレーションだけでは不十分

DevTools のデバイスエミュレーションは便利だが、以下は実機テストの代替にならない：

- タッチ操作の精度と感触
- 実際のネットワーク速度
- デバイス固有のブラウザ挙動（SafariのViewport挙動、Chromeのアドレスバー表示/非表示等）
- セーフエリアの実際の影響
- 低スペックデバイスでのパフォーマンス

### 必須のテスト項目

- **実機**：iPhone（Safari）= iOS固有のViewport挙動・100vh問題・セーフエリア／Android（Chrome）= 多様な画面サイズ・アドレスバーの動的変化／タブレット = iPad（Safari）・Androidタブレット
- **画面方向**：縦（Portrait）・横（Landscape）の両方をテストし、方向転換時のレイアウト崩れを確認する
- **ネットワーク**：低速シミュレーション（3G相当）でのページ読み込みと、画像遅延読み込みの動作を確認する

**判断基準：**
- 最低限、iPhone（Safari）とAndroid（Chrome）の実機テストを実施する
- タブレットテストはタブレットユーザーが想定される場合に実施する
- 横向きテストは動画・ダッシュボード等、横幅が重要なコンテンツで必須

## 判断に迷いやすいポイント

### レスポンシブ vs アダプティブ

**判断基準：** コンテンツが連続的にスケーリング可能か／デバイスごとに根本的に異なるUIが必要か／開発・保守リソースの程度。

**判断例：**
- ブログ、コーポレートサイト → レスポンシブ（単一HTML/CSS、フルードスケーリング）
- 複雑なダッシュボード → アダプティブ要素を含むレスポンシブ（特定ブレイクポイントでレイアウトを大きく変更）
- モバイルアプリとデスクトップアプリ → アダプティブ（根本的に異なるUI）

**トレードオフ：** 単一コードベースで管理可能ならレスポンシブを優先。デバイス間のUI差異が大きければアダプティブを検討する。

### コンポーネントレベル vs ページレベルのレスポンシブ

**判断基準：** コンポーネントが異なるコンテキストで再利用されるか／自身でレイアウトを制御すべきか。

**判断例：**
- カードコンポーネント → コンポーネントレベル（Container Queries で自身のサイズに応じて適応）
- ページ全体のレイアウト → ページレベル（メディアクエリで画面サイズに応じて適応）

```css
/* Container Queries によるコンポーネントレベルのレスポンシブ */
.card-container { container-type: inline-size; }
@container (min-width: 400px) {
  .card { flex-direction: row; }
}
```

**トレードオフ：** 再利用されるコンポーネントは Container Queries でコンポーネントレベルの適応を検討。ページ固有のレイアウトはメディアクエリで十分。

### モバイルでの機能の扱い

**判断基準：** モバイルユーザーにも必要か／適応（形を変える）できるか・切り捨てるしかないか／モバイルでの操作性を確保できるか。

**判断例：**
- 複雑なフィルター → アコーディオンやモーダルに適応する（切り捨てない）
- データテーブル → カード形式に変換する（切り捨てない）
- 高度な設定画面 → モバイルでもアクセス可能にする（段階的開示で情報量を制御）

**トレードオフ：** モバイルで重要機能を非表示にしてはならない。適応（形を変える）すべきで、切り捨てではない。

### hover 依存の代替手段

**判断基準：** hover なしでもアクセス可能か／タッチデバイスでの代替手段はあるか／情報の重要度。

**判断例：**
- ツールチップ → タッチではタップで表示、またはラベルを常時表示
- テーブル行のアクションボタン → 常時表示、またはコンテキストメニューを提供
- プレビュー → クリック/タップで表示、またはインライン表示

## よくある失敗パターン

- **デスクトップファースト（max-width）** — 改善：モバイルファーストで `min-width` を使う
- **デバイス検出（User-Agent）による分岐** — 改善：メディアクエリによる機能検出（`pointer`, `hover`, `min-width` 等）を使う。User-Agent ベースは新デバイス登場で保守不能になる
- **モバイルで重要機能を非表示にする**（`display: none`）— 改善：アコーディオン・モーダル・ドロワー等で形を変えて提供する
- **タブレット・横向きの無視** — 改善：中間のブレイクポイントを設定し、タブレット・横向きをテストする
- **hover 依存の機能**（行ホバーでアクション表示等）— 改善：`@media (hover: none)` でタッチ向け代替UIを提供。重要なアクションは常時表示する
- **固定幅のレイアウト**（`width: 1200px` 等）— 改善：`max-width` + `width: 100%`、または `clamp()` でフルードスケーリングする
- **100vh の使用（モバイル）** — アドレスバー未考慮。改善：`height: 100dvh`（dynamic viewport height）または `min-height: 100vh` にする
- **セーフエリア未考慮**（固定ボトムバーがノッチ/ホームインジケーターと重なる）— 改善：`env(safe-area-inset-bottom)` 等を適用する
- **画像の未最適化**（全デバイス同一の高解像度）— 改善：`srcset` + `sizes` で配信し、`loading="lazy"` で遅延読み込みする
