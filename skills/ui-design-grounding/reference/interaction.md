## このドキュメントの役割
このドキュメントは、UI/UXデザインにおける
**インタラクション設計の原則とパターン**を提供する。

ユーザーとシステムの間の相互作用を設計する際の判断基準とする。
8つのインタラクティブ状態を軸に、各状態の設計基準と実装ガイダンスを体系化する。

## インタラクション設計とは何か

インタラクション設計とは、
**ユーザーがシステムと対話する方法を設計すること**である。

以下を目的とする：

- 操作の予測可能性
- 操作結果の明確なフィードバック
- エラーの防止とリカバリ
- 操作の効率性と快適さ
- すべての入力方法（マウス、キーボード、タッチ）への対応

## 8つのインタラクティブ状態

すべてのインタラクティブ要素は、以下の8状態を持ちうる。
各状態は**視覚的に区別可能**でなければならない。

---

### 1. Default（基本状態）

要素の**安静時の状態**。ユーザーが何も操作していないときの見た目。

**設計基準：**
- 操作可能であることが視覚的に明確である
- 周囲の要素と適切なコントラストを持つ
- クリッカブルな要素はクリッカブルに見える（ボタンらしい見た目、リンクらしい色と下線）
- 要素の優先度が視覚的に伝わる（Primary / Secondary / Tertiary の区別）

**実装ガイダンス：**
- ボタン：背景色、border、border-radius、padding を明確に設定する
- リンク：色と下線で識別可能にする。色だけに頼らない（色覚多様性への配慮）
- `cursor: pointer` をクリッカブルな要素に設定する

---

### 2. Hover（カーソルオーバー）

マウスカーソルが要素の上にある状態。**タッチデバイスにはHoverは存在しない。**

**設計基準：**
- Default状態との視覚的な差異が明確である
- 操作可能であることを強化する
- 変化は控えめだが認識可能（背景色の明度変化、影の追加など）
- Hover だけに依存する情報を配置しない（タッチデバイスでアクセスできなくなる）

**実装ガイダンス：**
- 背景色：明度を 5-10% 変化させる
- `transition` で 150-200ms の滑らかな変化を付ける
- タッチデバイスでは Hover 効果を無効化する（`@media (hover: hover)` を使用）

```css
@media (hover: hover) {
  .button:hover {
    background-color: var(--color-primary-hover);
  }
}
```

---

### 3. Focus（キーボードナビゲーション）

キーボードの Tab キーで要素にフォーカスが当たった状態。
**Hover と Focus は別の状態であり、それぞれ独立して設計する。**

**設計基準：**
- フォーカスインジケーター（フォーカスリング）が必ず表示される
- Hover とは異なる視覚表現にする
- すべてのインタラクティブ要素でフォーカスが可能である
- フォーカス順序が論理的である（DOM順序と視覚的順序が一致する）

**実装ガイダンス：**
- `:focus-visible` を使用する（`:focus` ではなく）
- マウスクリック時にフォーカスリングを表示しない（`:focus-visible` が自動的に処理する）
- フォーカスリングの詳細は後述「フォーカスリングの設計」セクションを参照

```css
.button:focus-visible {
  outline: 2px solid var(--color-focus-ring);
  outline-offset: 2px;
}
```

---

### 4. Active（クリック・押下中）

要素がクリック・タップされている最中の状態。押下感のフィードバックを与える。

**設計基準：**
- クリック/タップの瞬間に即座に（100ms以内）視覚的変化がある
- 「押している」感覚が伝わる（わずかな縮小、色の深化、影の消失など）
- Default → Hover → Active の変化が段階的で自然である

**実装ガイダンス：**
- `transform: scale(0.97)` や `translateY(1px)` で押下感を表現する
- 背景色をさらに深くする
- `box-shadow` を縮小して「沈む」感覚を出す
- `:active` 疑似クラスを使用する

```css
.button:active {
  transform: scale(0.97);
  box-shadow: var(--shadow-sm);
}
```

---

### 5. Disabled（無効状態）

操作ができない状態。条件が満たされていない、権限がないなど。

**設計基準：**
- 操作不可であることが視覚的に明確（低コントラスト、グレーアウト）
- なぜ無効なのかが分かる（Tooltip や補足テキストで理由を伝える）
- Disabled要素は可能な限り避ける（非表示にするか、操作可能にして理由を説明する方が良い場合がある）
- Disabled 要素にも Tooltip は表示可能にする（`pointer-events: none` だと Tooltip が出ない問題に注意）

**実装ガイダンス：**
- `opacity: 0.4-0.5` で視覚的に無効化する
- `cursor: not-allowed` を設定する
- `aria-disabled="true"` を使用する（`disabled` 属性だとフォーカスが当たらなくなる場合がある）
- Tooltip で無効理由を説明する場合は `pointer-events` の制御に注意する

```html
<button aria-disabled="true" title="すべての必須項目を入力してください">
  保存する
</button>
```

---

### 6. Loading（処理中）

操作を受け付けた後、結果を待っている状態。

**設計基準：**
- 操作が受け付けられたことが即座に分かる
- 処理中であることが継続的に伝わる（アニメーション）
- 二重送信を防止する
- 処理時間の見通しが伝わる（可能な場合はプログレス表示）

**実装ガイダンス：**
- ボタンを即座に Disabled にしてスピナーを表示する
- ボタンの幅を固定してレイアウトシフトを防ぐ
- `aria-busy="true"` を設定する
- 処理時間が短い（< 1秒）場合はスピナーを遅延表示する（チラつき防止）
- ローディングパターンの詳細は後述セクションを参照

```html
<button disabled aria-busy="true">
  <span class="spinner" aria-hidden="true"></span>
  保存中...
</button>
```

---

### 7. Error（エラー状態）

操作が失敗した、または入力に問題がある状態。

**設計基準：**
- エラーであることが色・アイコン・テキストの組み合わせで伝わる（色だけに頼らない）
- エラーの原因が具体的に分かる
- エラーの解決方法が分かる
- 該当する入力フィールドがハイライトされる
- エラーメッセージはフィールドの近くに表示される

**実装ガイダンス：**
- フィールドの `border-color` を赤系（エラーカラー）に変更する
- エラーメッセージをフィールドの下に配置する
- `aria-describedby` でエラーメッセージとフィールドを関連付ける
- `aria-invalid="true"` を設定する
- アイコン + テキストの組み合わせで伝える

```html
<input
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>
<p id="email-error" role="alert">
  メールアドレスの形式が正しくありません。@を含む形式で入力してください。
</p>
```

---

### 8. Success（成功状態）

操作が正常に完了した状態。

**設計基準：**
- 成功したことが即座に分かる
- 何が成功したのか具体的に伝える（「保存しました」ではなく「変更を保存しました」）
- 次のアクションが明確である
- 成功メッセージは自動的に消える（5-8秒後、またはユーザーが閉じる）
- 重要な成功通知はユーザーの操作で閉じるまで残す

**実装ガイダンス：**
- Toast / Snackbar で非侵入的に通知する
- チェックマークアイコンで視覚的に補強する
- `role="status"` でスクリーンリーダーに通知する
- 自動消去のタイマーを設定する

```html
<div role="status" class="toast toast--success">
  変更を保存しました
</div>
```

## フォーカスリングの設計

キーボードナビゲーションの要。**絶対に `outline: none` だけで削除してはならない。**

**設計基準：**
- `:focus-visible` を使用する（`:focus` ではない）
- マウスクリック時にはフォーカスリングを表示せず、キーボード操作時のみ表示する
- 太さ：2-3px
- 要素からのオフセット：2px 以上（要素と重ならないようにする）
- 背景とのコントラスト比：3:1 以上
- フォーカスリングの色はブランドカラーまたは高視認性の色（青系が一般的）

**推奨パターン：**

```css
/* リセット：ブラウザデフォルトのフォーカスを上書き */
:focus {
  outline: none;
}

/* キーボードフォーカス時のみリングを表示 */
:focus-visible {
  outline: 2px solid var(--color-focus-ring, #2563eb);
  outline-offset: 2px;
}

/* 暗い背景上のフォーカスリング */
.dark-bg :focus-visible {
  outline-color: #fff;
  outline-offset: 2px;
}
```

**注意点：**
- `:focus` を `:focus-visible` に置き換えるだけで、マウスクリック時の不要なリングが消える
- Safari は `:focus-visible` のサポートが遅れた経緯があるが、現在は主要ブラウザすべてでサポート済み
- カスタムコンポーネントでは `tabindex="0"` を適切に設定する

## フォーム設計

**設計基準：**

### プレースホルダーはラベルではない

- プレースホルダーはラベルの代替にしてはならない
- ラベルは常に表示する（入力フィールドの上または左）
- プレースホルダーは入力例やヒントとして補助的に使う
- プレースホルダーのコントラストは低いため、重要な情報を載せない

```html
<!-- 正しい -->
<label for="email">メールアドレス</label>
<input id="email" type="email" placeholder="example@mail.com" />

<!-- 誤り：プレースホルダーをラベル代わりにしている -->
<input type="email" placeholder="メールアドレス" />
```

### バリデーションのタイミング

- **推奨：blur 時（フィールドからフォーカスが外れたとき）にバリデーションする**
- キーストロークごとのバリデーションは避ける（入力中にエラーが出て邪魔になる）
- 送信時のバリデーションは許容されるが、blur 時のほうがフィードバックが早い
- 一度エラーが表示された後は、リアルタイムで修正確認する（ユーザーが修正したらすぐにエラーを消す）

### エラーの配置

- エラーメッセージはフィールドの**下**に配置する
- `aria-describedby` でフィールドとエラーメッセージを関連付ける
- `aria-invalid="true"` でフィールドをエラー状態としてマークする
- エラーメッセージには `role="alert"` を設定する（動的に表示される場合）

## ローディングパターン

### スケルトンスクリーン vs スピナー

**スケルトンスクリーン（推奨）：**
- ページ全体やセクションの読み込みに使用する
- コンテンツのレイアウトが事前に分かっている場合に最適
- 体感速度が向上する（構造が見えることで「もうすぐ」と感じる）

**スピナー：**
- 個別のアクション（ボタンクリック後など）に使用する
- コンテンツのレイアウトが事前に分からない場合に使用する
- 表示が 1 秒未満の場合はスピナーを遅延表示する（チラつき防止）

### オプティミスティック更新

リスクが低い操作では**オプティミスティック更新（楽観的更新）**を検討する。

**オプティミスティック更新が適するケース：**
- いいね、ブックマーク、既読マーク
- テキストの編集・保存
- 設定のトグル

**適さないケース：**
- 決済処理
- データの削除
- 外部サービスへの送信

**仕組み：**
1. ユーザーが操作する
2. UIを即座に成功状態に更新する（サーバー応答を待たない）
3. バックグラウンドでサーバーに送信する
4. 失敗した場合のみ、UIを元に戻してエラーを通知する

## Popover API とオーバーレイ設計

### Popover API の活用

Tooltip、ドロップダウンメニュー、非モーダルなオーバーレイには **Popover API** を使用する。

**Popover API の利点：**
- Light dismiss（外側のクリックや Escape キーで自動的に閉じる）
- 適切なスタッキング（z-index の競合が発生しない、トップレイヤーに描画される）
- JavaScript なしで基本的な開閉が可能
- アクセシビリティのセマンティクスが組み込まれている

```html
<!-- Popover の基本パターン -->
<button popovertarget="menu">メニューを開く</button>
<div id="menu" popover>
  <ul>
    <li><a href="/settings">設定</a></li>
    <li><a href="/profile">プロフィール</a></li>
  </ul>
</div>
```

### モーダルには `<dialog>` 要素を使用する

- モーダルダイアログには `<dialog>` 要素と `showModal()` メソッドを使用する
- `<dialog>` は自動的に `inert` の効果を持つ（背景要素が操作不能になる）
- フォーカストラップが自動的に機能する
- Escape キーで閉じる動作が組み込まれている

```html
<dialog id="confirm-dialog">
  <h2>確認</h2>
  <p>この操作を実行しますか？</p>
  <form method="dialog">
    <button value="cancel">キャンセル</button>
    <button value="confirm">実行する</button>
  </form>
</dialog>
```

```javascript
// モーダルとして開く
document.getElementById('confirm-dialog').showModal();
```

### `inert` 属性

モーダルの背景コンテンツには `inert` 属性を検討する。
`<dialog>` 要素が `showModal()` で開かれた場合は自動的に処理されるが、
カスタムモーダルを実装する場合は明示的に設定する。

```html
<main inert>
  <!-- モーダル表示中はメインコンテンツを操作不能にする -->
</main>
<div class="custom-modal" role="dialog" aria-modal="true">
  ...
</div>
```

## ドロップダウンの配置問題

**最も頻出するバグ：`position: absolute` のドロップダウンが `overflow: hidden` の親要素にクリップされる。**

### 問題の原因

`position: absolute` の要素は最も近い `position: relative` な祖先を基準に配置される。
その祖先やさらに上位の要素に `overflow: hidden` / `overflow: auto` / `overflow: scroll` が設定されていると、
ドロップダウンがクリップされて見切れる。

### 解決策（優先度順）

**1. CSS Anchor Positioning（Chrome 125+）**

最新のCSS仕様。ブラウザが自動的にアンカー要素に対して配置する。

```css
.trigger {
  anchor-name: --dropdown-trigger;
}
.dropdown {
  position: fixed;
  position-anchor: --dropdown-trigger;
  top: anchor(bottom);
  left: anchor(left);
}
```

**2. Popover API + Anchor の組み合わせ**

Popover API のトップレイヤー描画と組み合わせる。

```html
<button popovertarget="dropdown" style="anchor-name: --btn">開く</button>
<div id="dropdown" popover style="position-anchor: --btn; top: anchor(bottom);">
  ...
</div>
```

**3. Portal / Teleport パターン（React, Vue 等）**

DOM ツリーの最上位（`<body>` 直下）にドロップダウンをレンダリングする。
`overflow: hidden` の影響を受けない。

- React：`createPortal`
- Vue：`<Teleport to="body">`

**4. `position: fixed` フォールバック**

ビューポート基準で配置する。`overflow: hidden` の影響を受けない。
ただしスクロール時の位置追従に JavaScript が必要。

```css
.dropdown {
  position: fixed;
  /* JavaScript でトリガー要素の位置を計算して設定する */
}
```

## 破壊的操作の設計

### 取り消し（Undo） vs 確認ダイアログ

**取り消し（Undo）のほうが優れたUXを提供する。**
ただし実装コストは確認ダイアログよりも高い。

| 観点 | Undo | 確認ダイアログ |
|------|------|--------------|
| UX | 操作の流れを中断しない | 操作の流れを中断する |
| 安全性 | 高い（実際に戻せる） | 低い（習慣的に「OK」を押す） |
| 実装コスト | 高い（ソフトデリートや遅延実行が必要） | 低い（ダイアログを出すだけ） |
| 適用場面 | メール削除、投稿削除、ファイル移動 | アカウント削除、課金操作 |

**Undo パターンの実装：**
1. ユーザーが削除を実行する
2. UIから即座に要素を非表示にする（実際にはまだ削除しない）
3. Undo 可能な Toast を表示する（5-10秒間）
4. Toast が消えた後（またはユーザーが明示的に確認した後）に実際に削除する
5. Undo がクリックされた場合は元に戻す

**確認ダイアログが適切なケース：**
- 取り消し不可能な操作（アカウント削除、公開投稿の完全削除）
- 金銭が関わる操作
- 影響範囲が大きい操作（チーム全体の設定変更など）

**確認ダイアログの設計原則：**
- 具体的に何が起こるかを説明する
- ボタンラベルに操作内容を明記する（「OK」ではなく「削除する」）
- 破壊的なボタンは目立つ警告色にする
- キャンセルをデフォルト（右側、または視覚的に控えめ）にする

## キーボードナビゲーション

### Roving Tabindex

**コンポーネントグループ内の移動には Roving Tabindex パターンを使用する。**

- Tab キー：コンポーネント間を移動する
- 矢印キー：コンポーネント内の要素間を移動する

**例：タブリスト**
- Tab でタブリストに入る
- 左右矢印キーでタブを切り替える
- Tab でタブリストから次の要素に移動する

```html
<div role="tablist">
  <button role="tab" tabindex="0" aria-selected="true">タブ1</button>
  <button role="tab" tabindex="-1">タブ2</button>
  <button role="tab" tabindex="-1">タブ3</button>
</div>
```

**実装の原則：**
- アクティブな要素のみ `tabindex="0"`、それ以外は `tabindex="-1"` にする
- 矢印キーで移動したら `tabindex` を更新して `focus()` を呼ぶ
- ツールバー、タブ、メニュー、ラジオグループなどに適用する

### スキップリンク

ページ上部に**スキップリンク**を配置する。キーボードユーザーがナビゲーションを飛ばしてメインコンテンツに直接移動できるようにする。

```html
<a href="#main-content" class="skip-link">
  メインコンテンツへスキップ
</a>
```

```css
.skip-link {
  position: absolute;
  top: -100%;
  left: 0;
}
.skip-link:focus {
  top: 0;
  z-index: 9999;
  background: var(--color-bg);
  padding: 0.5rem 1rem;
}
```

## ジェスチャーの発見可能性

**ジェスチャー操作には必ず可視的なフォールバックを提供する。**

- スワイプで削除 → 削除ボタンも配置する
- ピンチでズーム → ズームボタンも配置する
- ドラッグ&ドロップで並べ替え → 並べ替えボタンやメニューも配置する
- 長押しでコンテキストメニュー → 右クリックやボタンでも開けるようにする

ジェスチャーは**ショートカット**であり、**唯一の操作手段**にしてはならない。
キーボードユーザーや支援技術のユーザーがアクセスできない。

## アニメーションとインタラクション

アニメーションの詳細な設計（イージング、デュレーション、トランジションの種類など）は
motion-design のリファレンスを参照すること。

ここではインタラクションフィードバックに関連する原則のみを記載する。

**インタラクションフィードバックとしてのアニメーション：**
- 状態変化（Hover、Active、Focus）のトランジションは 150-200ms
- 要素の出現・消失は 200-300ms
- `prefers-reduced-motion` に対応する：装飾的なアニメーションは無効化し、機能的なアニメーションは簡略化する

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

## 判断に迷いやすいポイント

### Disabled にすべきか、非表示にすべきか

**判断基準：**
1. ユーザーがその機能の存在を知る必要があるか
2. 条件を満たせば操作可能になることを伝えたいか
3. なぜ操作できないかを説明できるか

**判断例：**
- 権限不足で使えない機能 → Disabled + Tooltip で理由を説明
- 現在のコンテキストで存在しない機能 → 非表示
- フォームの必須項目が未入力 → Disabled + 補足テキスト

### 確認ダイアログ vs Undo

**判断基準：**
1. 操作は技術的に取り消し可能か
2. 操作の影響範囲はどの程度か
3. ユーザーの操作フローを中断してでも確認すべきか

**判断例：**
- メール削除 → Undo（日常的な操作、取り消し可能）
- アカウント削除 → 確認ダイアログ（不可逆、影響大）
- 投稿の下書き削除 → Undo（日常的な操作）
- 公開投稿の削除 → 確認ダイアログ（影響が外部に及ぶ）

### Hover 情報の代替手段

**判断基準：**
- その情報はタッチデバイスでも必要か
- 常時表示でも視覚的に問題ないか
- Hover 以外のトリガー（クリック、フォーカス）で表示できるか

**判断例：**
- ツールチップ → タッチではタップで表示、またはラベルを常時表示
- プレビュー → クリックで表示、またはインライン表示
- 追加情報 → アコーディオンやモーダルで提供

### オプティミスティック更新の適用範囲

**判断基準：**
1. 失敗時にロールバックしてもユーザーが混乱しないか
2. 操作のリスクが低いか（データ損失や金銭的影響がないか）
3. 失敗頻度が十分に低いか

**判断例：**
- いいねボタン → オプティミスティック更新（低リスク、失敗時もロールバック容易）
- 商品購入 → 通常のローディング表示（高リスク）
- コメント投稿 → オプティミスティック更新 or ローディング（プロダクトの方針次第）

## よくある失敗パターン

- **`outline: none` でフォーカスリングを削除**
  - 例：見た目を整えるために `outline: none` を設定し、代替を提供しない
  - 改善：`:focus-visible` で適切なフォーカスリングを設計する

- **Hover のみに依存する情報**
  - 例：Hover しないと操作ボタンが見えないテーブル行
  - 改善：常時表示するか、タッチでも発見可能な代替手段を提供する

- **プレースホルダーをラベル代わりにする**
  - 例：入力フィールドにプレースホルダーだけでラベルがない
  - 改善：ラベルを常に表示し、プレースホルダーは補助的な例示にとどめる

- **キーストロークごとのバリデーション**
  - 例：1文字入力するたびにエラーが表示される
  - 改善：blur 時にバリデーションし、エラー表示後はリアルタイムで修正確認する

- **`overflow: hidden` によるドロップダウンの見切れ**
  - 例：テーブルセル内のドロップダウンが親要素にクリップされる
  - 改善：Portal パターン、Popover API、または `position: fixed` を使用する

- **z-index の競合**
  - 例：z-index の値を場当たり的に増やして管理不能になる
  - 改善：Popover API やトップレイヤーを活用し、z-index のスケールをデザイントークンで管理する

- **フィードバックの欠如**
  - 例：ボタンをクリックしても反応がない、処理中か分からない
  - 改善：即座の視覚的フィードバック、Loading 状態の表示

- **確認ダイアログの乱用**
  - 例：すべての操作に「本当に実行しますか？」を表示する
  - 改善：日常的な操作は Undo で対応し、確認ダイアログは高リスク操作に限定する

- **ジェスチャーのみの操作**
  - 例：スワイプでしか削除できない
  - 改善：可視的なボタンやメニューでの代替操作を提供する

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `score-ui` — UI品質スコアリングのインタラクション評価時に参照
- `guard-ui` — エッジケース堅牢化時のインタラクション状態・エラーハンドリング設計に参照
- `adapt-ui` — レスポンシブ適応時の入力方式対応・タッチ対応に参照
- `animate-ui` — アニメーション実装時のインタラクションフィードバック設計に参照
- `polish-ui` — UI修正適用時のインタラクション改善に参照
- インタラクション設計時の判断基準として参照する
- UIレビュー時のインタラクション評価の判断材料として使う
- 8つのインタラクティブ状態をチェックリストとして、各状態の設計漏れを確認する
