## このドキュメントの役割
**インタラクション設計の原則とパターン**を提供し、ユーザーとシステムの相互作用を設計する際の判断基準とする。8つのインタラクティブ状態を軸に、各状態の設計基準と実装ガイダンスを体系化する。

## インタラクション設計とは何か
**ユーザーがシステムと対話する方法を設計すること**。目的：

- 操作の予測可能性
- 操作結果の明確なフィードバック
- エラーの防止とリカバリ
- 操作の効率性と快適さ
- 全入力方法（マウス・キーボード・タッチ）への対応

## 8つのインタラクティブ状態

すべてのインタラクティブ要素は以下8状態を持ちうる。各状態は**視覚的に区別可能**でなければならない。

---

### 1. Default（基本状態）

要素の**安静時の状態**。

**設計基準：**
- 操作可能であることが視覚的に明確で、周囲と適切なコントラストを持つ
- クリッカブルな要素はそう見える（ボタンらしい見た目、リンクらしい色と下線）
- 優先度が視覚的に伝わる（Primary / Secondary / Tertiary の区別）

**実装ガイダンス：**
- ボタン：背景色・border・border-radius・padding を明確に設定
- リンク：色と下線で識別（色だけに頼らない＝色覚多様性への配慮）
- クリッカブル要素に `cursor: pointer`

---

### 2. Hover（カーソルオーバー）

マウスカーソルが要素上にある状態。**タッチデバイスにはHoverは存在しない。**

**設計基準：**
- Default との視覚差が明確で、操作可能であることを強化する
- 変化は控えめだが認識可能（背景色の明度変化、影の追加）
- Hover だけに依存する情報を置かない（タッチでアクセス不能になる）

**実装ガイダンス：**
- 背景色：明度を 5-10% 変化
- `transition` で 150-200ms の滑らかな変化
- タッチデバイスでは無効化（`@media (hover: hover)`）

```css
@media (hover: hover) {
  .button:hover {
    background-color: var(--color-primary-hover);
  }
}
```

---

### 3. Focus（キーボードナビゲーション）

Tab キーでフォーカスが当たった状態。**Hover と Focus は別の状態であり、独立して設計する。**

**設計基準：**
- フォーカスインジケーター（フォーカスリング）が必ず表示される
- Hover とは異なる視覚表現にする
- すべてのインタラクティブ要素でフォーカス可能
- フォーカス順序が論理的（DOM順序と視覚的順序が一致）

**実装ガイダンス：**
- `:focus-visible` を使う（`:focus` ではない）。マウスクリック時はリングを出さない
- 実装コード・設計基準は後述「フォーカスリングの設計」を参照

---

### 4. Active（クリック・押下中）

クリック・タップされている最中の状態。押下感のフィードバックを与える。

**設計基準：**
- クリック/タップ時に即座に（100ms以内）視覚変化がある
- 「押している」感覚が伝わる（わずかな縮小、色の深化、影の消失）
- Default → Hover → Active の変化が段階的で自然

**実装ガイダンス：**
- `transform: scale(0.97)` や `translateY(1px)` で押下感
- 背景色を深く、`box-shadow` を縮小して「沈む」感覚
- `:active` 疑似クラスを使用

```css
.button:active {
  transform: scale(0.97);
  box-shadow: var(--shadow-sm);
}
```

---

### 5. Disabled（無効状態）

操作ができない状態（条件未達、権限なしなど）。

**設計基準：**
- 操作不可が視覚的に明確（低コントラスト、グレーアウト）
- なぜ無効かが分かる（Tooltip や補足テキストで理由を伝える）
- Disabled は可能な限り避ける（非表示にするか、操作可能にして理由を説明する方が良い場合がある）
- Disabled 要素にも Tooltip は表示可能にする（`pointer-events: none` だと Tooltip が出ない問題に注意）

**実装ガイダンス：**
- `opacity: 0.4-0.5`、`cursor: not-allowed`
- `aria-disabled="true"` を使用（`disabled` 属性だとフォーカスが当たらなくなる場合がある）
- Tooltip で理由を説明する場合は `pointer-events` の制御に注意

```html
<button aria-disabled="true" title="すべての必須項目を入力してください">
  保存する
</button>
```

---

### 6. Loading（処理中）

操作を受け付けた後、結果を待っている状態。

**設計基準：**
- 操作が受け付けられたことが即座に分かる
- 処理中であることが継続的に伝わる（アニメーション）
- 二重送信を防止する
- 処理時間の見通しが伝わる（可能ならプログレス表示）

**実装ガイダンス：**
- ボタンを即座に Disabled にしてスピナー表示
- ボタン幅を固定してレイアウトシフトを防ぐ
- `aria-busy="true"`
- 短い処理（< 1秒）はスピナーを遅延表示（チラつき防止）
- 詳細は後述「ローディングパターン」を参照

```html
<button disabled aria-busy="true">
  <span class="spinner" aria-hidden="true"></span>
  保存中...
</button>
```

---

### 7. Error（エラー状態）

操作が失敗した、または入力に問題がある状態。

**設計基準：**
- エラーが色・アイコン・テキストの組み合わせで伝わる（色だけに頼らない）
- 原因が具体的に分かり、解決方法も分かる
- 該当フィールドがハイライトされる
- エラーメッセージはフィールドの近くに表示

**実装ガイダンス：**
- フィールドの `border-color` をエラーカラー（赤系）に変更
- エラーメッセージをフィールドの下に配置
- `aria-describedby` でメッセージとフィールドを関連付け、`aria-invalid="true"` を設定
- アイコン + テキストの組み合わせで伝える

```html
<input
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>
<p id="email-error" role="alert">
  メールアドレスの形式が正しくありません。@を含む形式で入力してください。
</p>
```

---

### 8. Success（成功状態）

操作が正常に完了した状態。

**設計基準：**
- 成功が即座に分かる
- 何が成功したのか具体的に伝える（「保存しました」ではなく「変更を保存しました」）
- 次のアクションが明確
- 成功メッセージは自動的に消える（5-8秒後、またはユーザーが閉じる）。重要な通知は操作で閉じるまで残す

**実装ガイダンス：**
- Toast / Snackbar で非侵入的に通知
- チェックマークアイコンで補強
- `role="status"` でスクリーンリーダーに通知
- 自動消去のタイマーを設定

```html
<div role="status" class="toast toast--success">
  変更を保存しました
</div>
```

---

## フォーカスリングの設計

キーボードナビゲーションの要。**絶対に `outline: none` だけで削除してはならない。**

**設計基準：**
- `:focus-visible` を使用（`:focus` ではない）。マウスクリック時は出さず、キーボード操作時のみ表示
- 太さ：2-3px
- 要素からのオフセット：2px 以上（要素と重ならない）
- 背景とのコントラスト比：3:1 以上
- 色はブランドカラーまたは高視認性の色（青系が一般的）

**推奨パターン：**

```css
/* リセット：ブラウザデフォルトを上書き */
:focus {
  outline: none;
}

/* キーボードフォーカス時のみリングを表示 */
:focus-visible {
  outline: 2px solid var(--color-focus-ring, #2563eb);
  outline-offset: 2px;
}

/* 暗い背景上のフォーカスリング */
.dark-bg :focus-visible {
  outline-color: #fff;
  outline-offset: 2px;
}
```

**注意点：**
- `:focus` を `:focus-visible` に置き換えるだけで、マウスクリック時の不要なリングが消える
- Safari は対応が遅れた経緯があるが、現在は主要ブラウザすべてでサポート済み
- カスタムコンポーネントでは `tabindex="0"` を適切に設定する

## フォーム設計

### プレースホルダーはラベルではない

- プレースホルダーをラベルの代替にしない。ラベルは常に表示する（フィールドの上または左）
- プレースホルダーは入力例やヒントとして補助的に使う
- コントラストが低いため、重要な情報を載せない

```html
<!-- 正しい -->
<label for="email">メールアドレス</label>
<input id="email" type="email" placeholder="example@mail.com" />

<!-- 誤り：プレースホルダーをラベル代わりにしている -->
<input type="email" placeholder="メールアドレス" />
```

### バリデーションのタイミング

- **推奨：blur 時（フォーカスが外れたとき）にバリデーション**
- キーストロークごとのバリデーションは避ける（入力中にエラーが出て邪魔になる）
- 送信時のバリデーションは許容されるが、blur 時のほうがフィードバックが早い
- 一度エラーが表示された後はリアルタイムで修正確認する（修正したらすぐエラーを消す）

### エラーの配置

- エラーメッセージはフィールドの**下**に配置
- `aria-describedby` でフィールドとメッセージを関連付け
- `aria-invalid="true"` でエラー状態としてマーク
- 動的に表示される場合はメッセージに `role="alert"` を設定

## ローディングパターン

### スケルトンスクリーン vs スピナー

**スケルトンスクリーン（推奨）：**
- ページ全体やセクションの読み込みに使用
- レイアウトが事前に分かっている場合に最適
- 体感速度が向上する（構造が見えて「もうすぐ」と感じる）

**スピナー：**
- 個別アクション（ボタンクリック後など）に使用
- レイアウトが事前に分からない場合に使用
- 表示が 1 秒未満なら遅延表示（チラつき防止）

### オプティミスティック更新

リスクが低い操作では**オプティミスティック更新（楽観的更新）**を検討する。

**適するケース：** いいね、ブックマーク、既読マーク、テキストの編集・保存、設定のトグル
**適さないケース：** 決済処理、データの削除、外部サービスへの送信

**仕組み：**
1. ユーザーが操作する
2. UIを即座に成功状態に更新（サーバー応答を待たない）
3. バックグラウンドでサーバーに送信
4. 失敗時のみ、UIを元に戻してエラーを通知

## Popover API とオーバーレイ設計

### Popover API の活用

Tooltip、ドロップダウンメニュー、非モーダルなオーバーレイには **Popover API** を使う。

**利点：**
- Light dismiss（外側クリックや Escape で自動的に閉じる）
- 適切なスタッキング（トップレイヤーに描画、z-index 競合が起きない）
- JavaScript なしで基本的な開閉が可能
- アクセシビリティのセマンティクスが組み込まれている

```html
<button popovertarget="menu">メニューを開く</button>
<div id="menu" popover>
  <ul>
    <li><a href="/settings">設定</a></li>
    <li><a href="/profile">プロフィール</a></li>
  </ul>
</div>
```

### モーダルには `<dialog>` 要素を使用する

- モーダルダイアログには `<dialog>` 要素と `showModal()` を使う
- `<dialog>` は自動的に `inert` の効果を持つ（背景要素が操作不能になる）
- フォーカストラップが自動的に機能し、Escape で閉じる動作が組み込まれている

```html
<dialog id="confirm-dialog">
  <h2>確認</h2>
  <p>この操作を実行しますか？</p>
  <form method="dialog">
    <button value="cancel">キャンセル</button>
    <button value="confirm">実行する</button>
  </form>
</dialog>
```

```javascript
document.getElementById('confirm-dialog').showModal();
```

### `inert` 属性

モーダルの背景コンテンツには `inert` 属性を検討する。`<dialog>` を `showModal()` で開いた場合は自動処理されるが、カスタムモーダルでは明示的に設定する。

```html
<main inert>
  <!-- モーダル表示中はメインコンテンツを操作不能にする -->
</main>
<div class="custom-modal" role="dialog" aria-modal="true">
  ...
</div>
```

## ドロップダウンの配置問題

**最頻出バグ：`position: absolute` のドロップダウンが `overflow: hidden` の親要素にクリップされる。**

### 問題の原因

`position: absolute` の要素は最も近い `position: relative` な祖先を基準に配置される。その祖先や上位に `overflow: hidden` / `auto` / `scroll` があると、ドロップダウンがクリップされて見切れる。

### 解決策（優先度順）

**1. CSS Anchor Positioning（Chrome 125+）**

最新仕様。ブラウザが自動的にアンカー要素に対して配置する。

```css
.trigger {
  anchor-name: --dropdown-trigger;
}
.dropdown {
  position: fixed;
  position-anchor: --dropdown-trigger;
  top: anchor(bottom);
  left: anchor(left);
}
```

**2. Popover API + Anchor の組み合わせ**

Popover API のトップレイヤー描画と組み合わせる。

```html
<button popovertarget="dropdown" style="anchor-name: --btn">開く</button>
<div id="dropdown" popover style="position-anchor: --btn; top: anchor(bottom);">
  ...
</div>
```

**3. Portal / Teleport パターン（React, Vue 等）**

DOM ツリー最上位（`<body>` 直下）にレンダリングし、`overflow: hidden` の影響を受けない。
- React：`createPortal` / Vue：`<Teleport to="body">`

**4. `position: fixed` フォールバック**

ビューポート基準で配置。`overflow: hidden` の影響を受けないが、スクロール時の位置追従に JavaScript が必要。

```css
.dropdown {
  position: fixed;
  /* JavaScript でトリガー要素の位置を計算して設定する */
}
```

## 破壊的操作の設計

### 取り消し（Undo） vs 確認ダイアログ

**取り消し（Undo）のほうが優れたUXを提供する。** ただし実装コストは高い。

| 観点 | Undo | 確認ダイアログ |
|------|------|--------------|
| UX | 操作の流れを中断しない | 操作の流れを中断する |
| 安全性 | 高い（実際に戻せる） | 低い（習慣的に「OK」を押す） |
| 実装コスト | 高い（ソフトデリートや遅延実行が必要） | 低い（ダイアログを出すだけ） |
| 適用場面 | メール削除、投稿削除、ファイル移動 | アカウント削除、課金操作 |

**Undo パターンの実装：**
1. ユーザーが削除を実行
2. UIから即座に要素を非表示（実際にはまだ削除しない）
3. Undo 可能な Toast を表示（5-10秒間）
4. Toast が消えた後（または明示的確認後）に実際に削除
5. Undo がクリックされたら元に戻す

**確認ダイアログが適切なケース：** 取り消し不可能な操作（アカウント削除、公開投稿の完全削除）、金銭が関わる操作、影響範囲が大きい操作（チーム全体の設定変更など）

**確認ダイアログの設計原則：**
- 具体的に何が起こるかを説明する
- ボタンラベルに操作内容を明記（「OK」ではなく「削除する」）
- 破壊的なボタンは目立つ警告色に
- キャンセルをデフォルト（右側、または視覚的に控えめ）にする

## キーボードナビゲーション

### Roving Tabindex

**コンポーネントグループ内の移動には Roving Tabindex を使う。**
- Tab：コンポーネント間を移動 / 矢印キー：コンポーネント内の要素間を移動

**例：タブリスト** — Tab でタブリストに入り、左右矢印でタブを切り替え、Tab で次の要素へ移動。

```html
<div role="tablist">
  <button role="tab" tabindex="0" aria-selected="true">タブ1</button>
  <button role="tab" tabindex="-1">タブ2</button>
  <button role="tab" tabindex="-1">タブ3</button>
</div>
```

**実装の原則：**
- アクティブな要素のみ `tabindex="0"`、それ以外は `tabindex="-1"`
- 矢印キーで移動したら `tabindex` を更新して `focus()` を呼ぶ
- ツールバー、タブ、メニュー、ラジオグループなどに適用

### スキップリンク

ページ上部に**スキップリンク**を配置し、キーボードユーザーがナビゲーションを飛ばしてメインコンテンツに直接移動できるようにする。

```html
<a href="#main-content" class="skip-link">
  メインコンテンツへスキップ
</a>
```

```css
.skip-link {
  position: absolute;
  top: -100%;
  left: 0;
}
.skip-link:focus {
  top: 0;
  z-index: 9999;
  background: var(--color-bg);
  padding: 0.5rem 1rem;
}
```

## ジェスチャーの発見可能性

**ジェスチャー操作には必ず可視的なフォールバックを提供する。**

- スワイプで削除 → 削除ボタンも配置
- ピンチでズーム → ズームボタンも配置
- ドラッグ&ドロップで並べ替え → 並べ替えボタンやメニューも配置
- 長押しでコンテキストメニュー → 右クリックやボタンでも開けるように

ジェスチャーは**ショートカット**であり、**唯一の操作手段**にしてはならない（キーボードユーザーや支援技術のユーザーがアクセスできなくなる）。

## アニメーションとインタラクション

アニメーションの詳細な設計（イージング、デュレーション、トランジションの種類など）は motion-design のリファレンスを参照。ここではインタラクションフィードバックに関連する原則のみを記載する。

- 状態変化（Hover、Active、Focus）のトランジションは 150-200ms
- 要素の出現・消失は 200-300ms
- `prefers-reduced-motion` に対応：装飾的アニメーションは無効化、機能的アニメーションは簡略化（実装コードは `motion-design.md` が所有）

## 判断に迷いやすいポイント

### Disabled にすべきか、非表示にすべきか

**判断基準：** ①ユーザーがその機能の存在を知る必要があるか ②条件を満たせば操作可能になることを伝えたいか ③なぜ操作できないか説明できるか

**判断例：**
- 権限不足で使えない機能 → Disabled + Tooltip で理由を説明
- 現在のコンテキストで存在しない機能 → 非表示
- フォームの必須項目が未入力 → Disabled + 補足テキスト

### 確認ダイアログ vs Undo

**判断基準：** ①操作は技術的に取り消し可能か ②影響範囲はどの程度か ③操作フローを中断してでも確認すべきか

**判断例：**
- メール削除 → Undo（日常的、取り消し可能）
- アカウント削除 → 確認ダイアログ（不可逆、影響大）
- 投稿の下書き削除 → Undo（日常的）
- 公開投稿の削除 → 確認ダイアログ（影響が外部に及ぶ）

### Hover 情報の代替手段

**判断基準：** その情報はタッチでも必要か／常時表示でも視覚的に問題ないか／Hover 以外のトリガー（クリック、フォーカス）で表示できるか

**判断例：**
- ツールチップ → タッチではタップで表示、またはラベルを常時表示
- プレビュー → クリックで表示、またはインライン表示
- 追加情報 → アコーディオンやモーダルで提供

### オプティミスティック更新の適用範囲

**判断基準：** ①失敗時にロールバックしてもユーザーが混乱しないか ②リスクが低いか（データ損失や金銭的影響がないか） ③失敗頻度が十分に低いか

**判断例：**
- いいねボタン → オプティミスティック更新（低リスク、ロールバック容易）
- 商品購入 → 通常のローディング表示（高リスク）
- コメント投稿 → オプティミスティック更新 or ローディング（プロダクト方針次第）

## よくある失敗パターン

- **`outline: none` でフォーカスリングを削除**：代替を提供しない → `:focus-visible` で適切なフォーカスリングを設計
- **Hover のみに依存する情報**：Hover しないと操作ボタンが見えない行 → 常時表示するか、タッチでも発見可能な代替手段を提供
- **プレースホルダーをラベル代わりにする** → ラベルを常に表示し、プレースホルダーは補助的な例示にとどめる
- **キーストロークごとのバリデーション** → blur 時にバリデーションし、エラー表示後はリアルタイムで修正確認
- **`overflow: hidden` によるドロップダウンの見切れ** → Portal パターン、Popover API、または `position: fixed` を使用
- **z-index の競合**：場当たり的に値を増やして管理不能になる → Popover API やトップレイヤーを活用し、z-index のスケールをデザイントークンで管理
- **フィードバックの欠如**：クリックしても反応がなく処理中か分からない → 即座の視覚フィードバック、Loading 状態の表示
- **確認ダイアログの乱用**：すべての操作に「本当に実行しますか？」 → 日常的操作は Undo、確認ダイアログは高リスク操作に限定
- **ジェスチャーのみの操作**：スワイプでしか削除できない → 可視的なボタンやメニューでの代替を提供
