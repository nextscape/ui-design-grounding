## ベースグリッドシステム

### 4pt 基本単位

スペーシングの基本単位は **4px**。8px ではなく 4px とするのは、`12px` や `20px` などの中間値が実務で頻繁に必要になるため。

### スペーシングスケール

| トークン名 | 値 | 用途 |
|---|---|---|
| `spacing.2xs` | 4px | インラインアイコンとテキストの間隔 |
| `spacing.xs` | 8px | 密接な関連要素間（ラベルと入力欄） |
| `spacing.sm` | 12px | コンポーネント内の要素間 |
| `spacing.md` | 16px | カード内のパディング、フォーム要素間 |
| `spacing.lg` | 24px | セクション内の要素グループ間 |
| `spacing.xl` | 32px | セクション間の余白 |
| `spacing.2xl` | 48px | 大きなセクション間の余白 |
| `spacing.3xl` | 64px | ページ主要セクション間 |
| `spacing.4xl` | 96px | ヒーローセクション、ページヘッダー |

### セマンティックトークン命名

直接値ではなくセマンティックトークンで管理する。

```css
:root {
  /* プリミティブトークン（スケール段階＝トークン名と一致） */
  --spacing-2xs: 0.25rem;  /* 4px */
  --spacing-xs:  0.5rem;   /* 8px */
  --spacing-sm:  0.75rem;  /* 12px */
  --spacing-md:  1rem;     /* 16px */
  --spacing-lg:  1.5rem;   /* 24px */
  --spacing-xl:  2rem;     /* 32px */
  --spacing-2xl: 3rem;     /* 48px */
  --spacing-3xl: 4rem;     /* 64px */
  --spacing-4xl: 6rem;     /* 96px */

  /* セマンティックトークン */
  --spacing-inline-xs: var(--spacing-2xs);
  --spacing-stack-sm:  var(--spacing-sm);
  --spacing-inset-md:  var(--spacing-md);
  --spacing-section:   var(--spacing-2xl);
}
```

### gap > margins

要素間スペーシングは `margin` より `gap` を優先する。コンテナが間隔を制御するため子要素が余白の責務を持たず、margin collapsing を回避でき、`:first-child`/`:last-child` の余白処理も不要になる。

```css
/* 推奨 */
.stack { display: flex; flex-direction: column; gap: var(--spacing-md); }
/* 非推奨 */
.stack > * + * { margin-top: 1rem; }
```

### 判断基準

- すべてのスペーシング値が 4px の倍数であること
- スペーシングトークンが定義され、直接値の使用が限定されていること
- 要素間スペーシングに `gap` が優先使用されていること

## インタラクティブ小コントロールの最小サイズ

ピル・バッジ・チップなどテキストラベル付きの小さなインタラクティブ要素には、タッチターゲットとは別に視認性・操作性のための最小サイズがある。

### コンテナの最小高さの基準

- **WCAG 2.5.8 (AA)**: ターゲットサイズ最小 **24×24 CSS px**（隣接ターゲットと非重複の場合）
- **WCAG 2.5.5 (AAA)**: ターゲットサイズ **44×44 CSS px**

視覚的に小さく描画する場合もタップ領域は疑似要素等で確保する（「タッチターゲット」参照）。

### コントロールグループの間隔

ピルやチップが並ぶグループの `gap` が狭すぎると境界が曖昧になり誤タップを招く。

- **Material Design 3**: チップグループの gap は **8dp**
- **WCAG 2.5.8**: 各ターゲットの中心に24px径の円を置いたとき、隣接ターゲットと重ならないこと

同一要素内のアイコンとテキストの間隔はこれより狭くてよい（4px 程度）。

### 判断基準

- DESIGN.md に小コントロールの最小サイズ・間隔が定義されていればそれに従う
- 未定義の場合は上記デザインシステム基準を参照して判断する
- 小コントロールのタップ領域が WCAG 2.5.8 (24px) を下回らないこと

## 自己調整グリッド

### auto-fit による自己調整

固定カラム数ではなく、利用可能な幅に自動で適応するグリッドを構築する。

```css
.grid-auto {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: var(--spacing-lg);
}
```

**`auto-fit` vs `auto-fill`：** `auto-fit` はアイテムが残りスペースを埋める（少数時に伸張）、`auto-fill` は空カラムを維持する。ほとんどのケースで `auto-fit` が適切。

### 名前付きグリッドエリア

複雑なレイアウトは名前付きグリッドエリアで宣言的に記述する。

```css
.page-layout {
  display: grid;
  grid-template-areas:
    "header  header"
    "sidebar main"
    "footer  footer";
  grid-template-columns: 280px 1fr;
  gap: var(--spacing-lg);
}
.header  { grid-area: header; }
.sidebar { grid-area: sidebar; }
.main    { grid-area: main; }
.footer  { grid-area: footer; }
```

### Flexbox vs Grid の使い分け

| 判断軸 | Flexbox | Grid |
|---|---|---|
| 次元 | **1次元**（行 or 列） | **2次元**（行 and 列） |
| 適した用途 | ナビゲーション、ボタングループ、インライン要素 | ページレイアウト、カードグリッド、フォーム |
| サイズ制御 | コンテンツに基づく | コンテナに基づく |
| アラインメント | 主軸・交差軸 | 行・列ともに精密な制御 |

### 判断基準

- レスポンシブにメディアクエリではなく `auto-fit` が活用されていること
- 1次元の配置に Grid を過剰使用していないこと
- 2次元のレイアウトに Flexbox を無理に使っていないこと

## 視覚階層の多次元化

視覚階層とは要素の重要度を視覚的に伝える構造であり、効果的な階層は**複数の次元を同時に使用する**。

### 階層を作る次元

| 次元 | 手法 | 効果 |
|---|---|---|
| サイズ | フォントサイズ、要素の大きさ | 大きいものが先に目に入る |
| ウェイト | フォントウェイト、線の太さ | 太い要素が強調される |
| 色 | コントラスト、彩度 | 高コントラスト・高彩度が注目を集める |
| 位置 | 上部、左上（F字パターン） | 先に読まれる位置に重要情報を配置 |
| ホワイトスペース | 周囲の余白 | 余白が多い要素は孤立して目立つ |

### サイズ比率のルール

重要な要素と周囲の要素のサイズ比は **3:1 以上** を確保する。

- 見出し `2rem` / 本文 `1rem` → 2:1（ギリギリ。ウェイトか色で補強）
- 見出し `3rem` / 本文 `1rem` → 3:1（サイズだけで明確に区別できる）

### 複数次元の同時使用

最良の視覚階層は **2〜3次元** を同時に使う。良い例＝「大きいサイズ + 太いウェイト + 上部配置」（サイズ×ウェイト×位置の3次元）。悪い例＝「色だけ変えて強調」（単一次元では弱い）。

### 判断基準

- 最重要要素が 2次元以上で強調されていること
- 単一次元（色だけ、サイズだけ）のみで階層を作ろうとしていないこと
- サイズ比 3:1 以上が確保されているか、不足分を他の次元で補っていること

## スクイントテスト

画面を**目を細めてぼやかして見る**ことで視覚階層とグルーピングが機能しているか検証する手法。画面（またはスクリーンショット）をぼかし、以下を確認する。

### チェックポイント

| 確認項目 | 合格基準 |
|---|---|
| 最重要要素が識別できるか | ぼやけた状態でも最初に目に入る要素がある |
| 2番目に重要な要素は | 最重要要素の次に目に入る要素が明確にある |
| グルーピングは明確か | 関連する要素がまとまりとして認識できる |

### 判断基準

- すべてが同じ重みに見える場合、階層設計に問題がある
- グルーピングが不明確な場合、スペーシングまたはコンテナの設計に問題がある
- 3つ以上の要素が同時に「最重要」に見える場合、強調の乱用である

## コンテナクエリ

### コンポーネントレベルのレスポンシブ

メディアクエリはビューポート幅に応答するが、コンテナクエリは配置先**コンテナの幅**に応答する。

```css
.card-container {
  container-type: inline-size;
  container-name: card;
}
@container card (min-width: 400px) {
  .card { display: grid; grid-template-columns: 200px 1fr; }
}
@container card (max-width: 399px) {
  .card { display: flex; flex-direction: column; }
}
```

### 活用場面

- カードが配置先（メインカラム、サイドバー、モーダル内）によってレイアウトを自動変更する
- ナビゲーションがコンテナ幅に応じてアイコンのみ/テキスト付きを切り替える

### 判断基準

- 同じコンポーネントが異なる幅のコンテナに配置される場合、コンテナクエリの導入を検討する
- ビューポート幅ではなくコンテナ幅に応答すべきかで使い分ける
- ブラウザサポート要件を確認する（モダンブラウザはすべて対応済み）

## オプティカル調整

### 視覚的中央 vs 数学的中央

人間の目は数学的中央を「中央」と認識せず、視覚的に正しい位置はわずかに上・左にずれる。

- ボタン内テキストが上に見える → `padding-bottom` をわずかに増やす
- 丸いコンテナ内のアイコンが下寄りに見える → わずかに上にオフセット

### テキストの視覚的インデント

`margin-left: 0` のテキストはフォントのサイドベアリング（文字左側の空白）により視覚的にインデントして見える場合がある。

```css
.heading-aligned { margin-left: -0.05em; /* サイドベアリング補正 */ }
```

### 再生アイコンの調整

三角形の再生アイコンは円形コンテナの数学的中央だと左寄りに見えるため、右へわずかにシフトする。

```css
.play-button svg { transform: translateX(1px); /* 視覚的中央に補正 */ }
```

### 同一行内のフォーム要素混在

`<select>`, `<input>`, ラジオボタンの `<div>` などが同じ行に並ぶと、ブラウザのデフォルトスタイルで高さやベースラインがずれる。

**対策:** コンテナの交差軸揃えで垂直中央に配置／全要素に同じ `padding` と `line-height` を明示／ネイティブ `<select>` は `appearance: none` + 明示的な高さ指定で制御。

### 判断基準

- 数学的中央配置で「ずれて見える」場合はオプティカル調整を検討する
- 調整値は小さく（1〜2px 程度）、フォントやアイコンに依存する
- すべてを調整する必要はなく、違和感がある場合のみ対応する
- 異なるフォーム要素が同一行で混在する場合、高さとベースラインの明示的統一が必要

## タッチターゲット

すべてのインタラクティブ要素のタップ領域は **44px × 44px** 以上を確保する（WCAG 2.5.5 AAA。AA は 24px = 2.5.8）。見た目が小さい要素（例: 24px のアイコンボタン）は擬似要素でタップ領域だけ 44px に拡張する。**最小値の根拠・擬似要素の実装コード・隣接ターゲット非重複の扱いは `accessibility.md`（タップ領域）が所有する。**

### 判断基準

- すべてのインタラクティブ要素のタップ領域が 44px 以上であること
- タップ領域同士が重ならないこと
- 視覚的サイズを小さくする場合は、疑似要素でタップ領域を補うこと

## カードの適切な使用

### カードが必要な場合

- **明確なアフォーダンス**：クリック可能な単位であることを示す
- **グリッド比較**：複数の選択肢を並べて比較する場面
- **明確なインタラクション境界**：ドラッグ＆ドロップや選択の対象であることを示す

### カードが不要な場合

- スペーシングとアラインメントだけで十分にグルーピングできる
- 背景やボーダーなしでも情報の関連性が伝わる
- リスト表示で行ごとの区切り線で十分な場面

### カードのネストは禁止

カード内にカードを配置してはならない。視覚的階層が崩壊し、インタラクション境界が曖昧になり、影やボーダーが重なってノイズが増える。

**改善策：** 内側の要素はセクション分け（余白や区切り線）で表現する／情報構造を見直しネストが不要な設計にする。

### 判断基準

- カードの使用に明確な理由（アフォーダンス、比較、インタラクション境界）があること
- スペーシングとアラインメントで代替できないか検討されていること
- カードのネストが存在しないこと

## 深度とエレベーション

### セマンティック z-index 階層

z-index はマジックナンバーではなくセマンティックな階層で定義する。

```css
:root {
  --z-base: 0;
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-modal: 300;
  --z-toast: 400;
}
```

| 階層 | 値 | 用途 |
|---|---|---|
| `base` | 0 | 通常のコンテンツ |
| `dropdown` | 100 | ドロップダウンメニュー、ポップオーバー |
| `sticky` | 200 | スティッキーヘッダー、フローティングボタン |
| `modal` | 300 | モーダルダイアログ、オーバーレイ |
| `toast` | 400 | トースト通知、スナックバー |

### シャドウの設計

シャドウは**微細（subtle）**にする。過剰なシャドウはUIを重たくする。

```css
/* 推奨：微細なシャドウ */
--shadow-sm: 0 1px 2px oklch(0% 0 0 / 0.05);
--shadow-md: 0 4px 6px oklch(0% 0 0 / 0.07);
--shadow-lg: 0 10px 15px oklch(0% 0 0 / 0.1);
/* 非推奨：過剰なシャドウ */
--shadow-heavy: 0 10px 30px rgba(0, 0, 0, 0.3);
```

### ダークモードでの深度表現

ダークモードはシャドウが見えにくいため、**面の明度を上げる**（`surface` → `surface-container` → `surface-container-high`）ことで深度を表現する。具体的な明度ラダーと OKLCH 値は `color-system.md`（ダークモード設計）が所有する。

### 判断基準

- z-index がセマンティックトークンで管理されていること
- シャドウの透明度が 0.1 以下を基準にしていること
- ダークモードで影だけに依存した深度表現になっていないこと

## 判断に迷いやすいポイント

### 厳密グリッド vs 有機的レイアウト

**トレードオフ：** 秩序と予測可能性 vs 自然さと独自性

1. アプリUI・管理画面 → 厳密グリッド（ユーザーは効率を求める）
2. マーケティング・ブランドサイト → 有機的レイアウトで個性を出せる
3. 混在させる場合はセクション単位で使い分ける

### カード vs オープンレイアウト

**トレードオフ：** 明確な境界 vs 開放感

1. 要素がクリック可能な単位か → カード
2. スペーシングとアラインメントで十分グルーピングできるか → オープンレイアウト
3. 「なんとなくカードで囲む」は判断の放棄

**判断例：** 商品一覧（クリックして詳細遷移）→ カード／ダッシュボードの統計セクション→余白とアラインメントで足りる場合が多い／設定画面のフォームグループ→セクション見出し + 余白で十分。

### 数学的 vs 光学的スペーシング

**トレードオフ：** 実装の一貫性 vs 視覚的な正確さ

1. グリッドやスペーシングトークンは数学的に正確に保つ
2. 個別要素（アイコン、テキスト）の配置は光学的に調整する
3. 全体構造は数学的、ディテールは光学的、が実用的

## よくある失敗パターン

### すべてをカードで包む

- **問題**：区切りをすべてカードの枠線やシャドウで表現し、画面がカードだらけで階層感が失われる
- **改善**：スペーシングとアラインメントで足りないか検討する。カードは明確なアフォーダンスが必要な場合に限定する

### カードのネスト

- **問題**：カード内にカードを配置し、視覚的階層が崩壊しインタラクション境界が曖昧になる
- **改善**：内部の情報構造はセクション分け（余白・区切り線）で表現する

### 同一カードグリッドの繰り返し

- **問題**：ページ全体が同じサイズ・構造のカードグリッドで埋まり単調になる
- **改善**：サイズやレイアウトにバリエーションを持たせる（重要なカードを大きく、フィーチャーカードを差し込む等）

### 全中央揃え

- **問題**：すべてを中央揃えにする。特に複数行テキストの中央揃えは読みにくい
- **改善**：テキストは**左揃え**を基本に、中央揃えは見出しや短いキャッチコピーに限定する。非対称レイアウト（左揃え + 右側余白）の方がデザインされた印象を与える

### 均一スペーシング（リズムなし）

- **問題**：すべての要素間に同じ余白を適用し、グルーピングや優先度が伝わらない
- **改善**：関連する要素間は狭く、無関係な要素間は広く。スペーシングスケールでリズムを作る

### 固定幅レイアウト

- **問題**：コンテナやカードが固定幅（`width: 300px`）でレスポンシブに対応しない
- **改善**：`minmax()`, `auto-fit`, パーセンテージ, `clamp()` で可変幅にする。固定幅はアイコンやアバターなど本質的に固定サイズの要素のみに限定する

### コンテナ幅の不統一による整列ずれ

- **問題**：ヘッダーが `max-width` + 中央寄せで幅制限される一方、直下のコンテンツは全幅で配置され、左端が揃わない
- **改善**：同一ページ内で視覚的に連続する要素は同じコンテナ幅を使うか、レイアウトモードに応じてヘッダーの幅も切り替える

### 均一スペーシングと内部パディングの混在

- **問題**：均一な `margin-top`/`gap` を設定したコンテナ内で、子要素ごとの内部パディングやボーダーの有無が異なり、視覚的な余白が不均一になる
- **改善**：セクション区切りパターンを統一する（全セクションを同じ `padding` + `border` 構造にする）か、コンテナの間隔を十分大きくして内部パディングの差を吸収する

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `arrange-ui` — レイアウト調整時のグリッド・スペーシング・視覚階層の判断に参照
- `design-ui` — UI設計時のグリッド・余白設計に参照
