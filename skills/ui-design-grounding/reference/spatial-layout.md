## ベースグリッドシステム

### 4pt 基本単位

スペーシングの基本単位は **4px** とする。8px ではなく 4px を採用する理由は、
`12px` や `20px` のような中間値が実務で頻繁に必要になるためである。

### スペーシングスケール

| トークン名 | 値 | 用途 |
|---|---|---|
| `space.2xs` | 4px | インラインアイコンとテキストの間隔 |
| `space.xs` | 8px | 密接な関連要素間（ラベルと入力欄） |
| `space.sm` | 12px | コンポーネント内の要素間 |
| `space.md` | 16px | カード内のパディング、フォーム要素間 |
| `space.lg` | 24px | セクション内の要素グループ間 |
| `space.xl` | 32px | セクション間の余白 |
| `space.2xl` | 48px | 大きなセクション間の余白 |
| `space.3xl` | 64px | ページ主要セクション間 |
| `space.4xl` | 96px | ヒーローセクション、ページヘッダー |

### セマンティックトークン命名

スペーシング値を直接使用するのではなく、セマンティックトークンで管理する。

```css
:root {
  /* プリミティブトークン */
  --space-4: 0.25rem;   /* 4px */
  --space-8: 0.5rem;    /* 8px */
  --space-12: 0.75rem;  /* 12px */
  --space-16: 1rem;     /* 16px */
  --space-24: 1.5rem;   /* 24px */
  --space-32: 2rem;     /* 32px */
  --space-48: 3rem;     /* 48px */
  --space-64: 4rem;     /* 64px */
  --space-96: 6rem;     /* 96px */

  /* セマンティックトークン */
  --space-inline-xs: var(--space-4);
  --space-stack-sm: var(--space-12);
  --space-inset-md: var(--space-16);
  --space-section: var(--space-48);
}
```

### gap > margins

要素間のスペーシングには `margin` ではなく `gap` を優先使用する。

**理由：**
- `gap` はコンテナが間隔を制御するため、子要素が余白の責務を持たない
- マージンの相殺（margin collapsing）による予期しない挙動を回避できる
- 最初・最後の要素の余白処理（`:first-child`, `:last-child`）が不要になる

```css
/* 推奨 */
.stack {
  display: flex;
  flex-direction: column;
  gap: var(--space-16);
}

/* 非推奨 */
.stack > * + * {
  margin-top: 1rem;
}
```

### 判断基準

- すべてのスペーシング値が 4px の倍数であること
- スペーシングトークンが定義され、直接値の使用が限定されていること
- 要素間スペーシングに `gap` が優先使用されていること

## 自己調整グリッド

### auto-fit による自己調整

固定のカラム数ではなく、コンテンツが利用可能な幅に自動で適応するグリッドを構築する。

```css
.grid-auto {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: var(--space-24);
}
```

**`auto-fit` vs `auto-fill`：**
- `auto-fit`：残りのスペースをアイテムが埋める（アイテム数が少ない場合に伸張する）
- `auto-fill`：空のカラムをそのまま維持する

ほとんどのケースでは `auto-fit` が適切である。

### 名前付きグリッドエリア

複雑なレイアウトでは名前付きグリッドエリアを使用し、レイアウト構造を宣言的に記述する。

```css
.page-layout {
  display: grid;
  grid-template-areas:
    "header  header"
    "sidebar main"
    "footer  footer";
  grid-template-columns: 280px 1fr;
  gap: var(--space-24);
}

.header  { grid-area: header; }
.sidebar { grid-area: sidebar; }
.main    { grid-area: main; }
.footer  { grid-area: footer; }
```

### Flexbox vs Grid の使い分け

| 判断軸 | Flexbox | Grid |
|---|---|---|
| 次元 | **1次元**（行 or 列） | **2次元**（行 and 列） |
| 適した用途 | ナビゲーション、ボタングループ、インライン要素 | ページレイアウト、カードグリッド、フォーム |
| サイズ制御 | コンテンツに基づく | コンテナに基づく |
| アラインメント | 主軸・交差軸 | 行・列ともに精密な制御 |

### 判断基準

- レスポンシブ対応にメディアクエリではなく `auto-fit` が活用されていること
- 1次元の配置に Grid を過剰使用していないこと
- 2次元のレイアウトに Flexbox を無理に使っていないこと

## 視覚階層の多次元化

視覚階層（ビジュアルヒエラルキー）とは、要素の重要度を視覚的に伝える構造である。
効果的な階層は**複数の次元を同時に使用する**。

### 階層を作る次元

| 次元 | 手法 | 効果 |
|---|---|---|
| サイズ | フォントサイズ、要素の大きさ | 大きいものが先に目に入る |
| ウェイト | フォントウェイト、線の太さ | 太い要素が強調される |
| 色 | コントラスト、彩度 | 高コントラスト・高彩度が注目を集める |
| 位置 | 上部、左上（F字パターン） | 先に読まれる位置に重要情報を配置 |
| ホワイトスペース | 周囲の余白 | 余白が多い要素は孤立して目立つ |

### サイズ比率のルール

重要な要素と周囲の要素のサイズ比は **3:1 以上** を確保する。

- 見出し `2rem` に対して本文 `1rem` → 比率 2:1（ギリギリ。ウェイトか色で補強する）
- 見出し `3rem` に対して本文 `1rem` → 比率 3:1（サイズだけで明確に区別できる）

### 複数次元の同時使用

最良の視覚階層は **2〜3次元** を同時に使用する。

```
良い例：
  見出し = 大きいサイズ + 太いウェイト + 上部配置
  → サイズ × ウェイト × 位置 の3次元

悪い例：
  見出し = 色だけ変えて強調
  → 単一次元では弱い
```

### 判断基準

- 最重要要素が 2次元以上で強調されていること
- 単一次元（色だけ、サイズだけ）のみで階層を作ろうとしていないこと
- サイズ比 3:1 以上が確保されているか、不足分を他の次元で補っていること

## スクイントテスト

スクイントテストとは、画面を**目を細めてぼやかして見る**ことで、
視覚階層とグルーピングが機能しているかを検証する手法である。

### テスト方法

1. 画面を表示し、目を細めてぼやかす（またはスクリーンショットをぼかす）
2. 以下の3点を確認する

### チェックポイント

| 確認項目 | 合格基準 |
|---|---|
| 最重要要素が識別できるか | ぼやけた状態でも最初に目に入る要素がある |
| 2番目に重要な要素は | 最重要要素の次に目に入る要素が明確にある |
| グルーピングは明確か | 関連する要素がまとまりとして認識できる |

### 判断基準

- すべてが同じ重みに見える場合、階層設計に問題がある
- グルーピングが不明確な場合、スペーシングまたはコンテナの設計に問題がある
- 3つ以上の要素が同時に「最重要」に見える場合、強調の乱用である

## コンテナクエリ

### コンポーネントレベルのレスポンシブ

従来のメディアクエリはビューポート幅に応答するが、
コンテナクエリはコンポーネントが配置された**コンテナの幅**に応答する。

```css
/* コンテナの定義 */
.card-container {
  container-type: inline-size;
  container-name: card;
}

/* コンテナ幅に応じたスタイル変更 */
@container card (min-width: 400px) {
  .card {
    display: grid;
    grid-template-columns: 200px 1fr;
  }
}

@container card (max-width: 399px) {
  .card {
    display: flex;
    flex-direction: column;
  }
}
```

### 活用場面

- カードコンポーネントが、配置先（メインカラム、サイドバー、モーダル内）によって自動的にレイアウトを変更する
- ナビゲーションコンポーネントが、コンテナ幅に応じてアイコンのみ/テキスト付きを切り替える

### 判断基準

- 同じコンポーネントが異なる幅のコンテナに配置される場合、コンテナクエリの導入を検討する
- ビューポート幅ではなくコンテナ幅に応答すべきかどうかで使い分ける
- ブラウザサポート要件を確認する（モダンブラウザはすべて対応済み）

## オプティカル調整

### 視覚的中央 vs 数学的中央

人間の目は数学的な中央を「中央」とは認識しない。
視覚的に正しい位置は、数学的中央よりもわずかに上・左にずれる。

**典型的な調整：**
- ボタン内のテキストは、数学的中央よりもわずかに上に見えることがある → `padding-bottom` をわずかに増やす
- 丸いコンテナ内のアイコンは、数学的中央に配置すると下寄りに見える → わずかに上にオフセットする

### テキストの視覚的インデント

`margin-left: 0` のテキストは、フォントのサイドベアリング（文字の左側の空白）により
視覚的にはインデントして見える場合がある。

```css
/* テキストの視覚的アラインメント調整 */
.heading-aligned {
  margin-left: -0.05em; /* フォントのサイドベアリングを補正 */
}
```

### 再生アイコンの調整

三角形の再生アイコンは、円形コンテナの数学的中央に配置すると左寄りに見える。
視覚的中央に合わせるため、右方向にわずかにシフトする。

```css
.play-button svg {
  transform: translateX(1px); /* 視覚的中央に補正 */
}
```

### 判断基準

- 数学的な中央配置で「ずれて見える」場合は、オプティカル調整を検討する
- 調整値は小さく（1〜2px 程度）、フォントやアイコンに依存する
- すべてを調整する必要はない。違和感がある場合のみ対応する

## タッチターゲット

### 44px 最小タップ領域

タッチデバイスでの操作性を確保するため、
すべてのインタラクティブ要素のタップ領域は **44px x 44px** 以上を確保する。

### 視覚サイズとタップ領域の分離

見た目は 24px でも、疑似要素でタップ領域を 44px に拡張する。

```css
.icon-button {
  position: relative;
  width: 24px;
  height: 24px;
  /* 視覚的には24px */
}

.icon-button::after {
  content: '';
  position: absolute;
  top: 50%;
  left: 50%;
  transform: translate(-50%, -50%);
  width: 44px;
  height: 44px;
  /* タップ領域は44px */
}
```

### 判断基準

- すべてのインタラクティブ要素のタップ領域が 44px 以上であること
- タップ領域同士が重ならないこと
- 視覚的サイズを小さくする場合は、疑似要素でタップ領域を補うこと

## カードの適切な使用

### カードが必要な場合

- **明確なアフォーダンス**が必要：クリック可能な単位であることを示す
- **グリッド比較**：複数の選択肢を並べて比較する場面
- **明確なインタラクション境界**：ドラッグ＆ドロップや選択の対象であることを示す

### カードが不要な場合

- **スペーシングとアラインメントだけで十分**にグルーピングできる
- 背景やボーダーなしでも情報の関連性が伝わる
- リスト表示で行ごとの区切り線で十分な場面

### カードのネストは禁止

カードの中にカードを配置してはならない。

**理由：**
- 視覚的な階層が崩壊する
- インタラクション境界が曖昧になる
- 影やボーダーが重なり、視覚的なノイズが増える

**改善策：**
- 内側の要素はセクション分け（余白や区切り線）で表現する
- 情報構造を見直し、ネストが不要な設計にする

### 判断基準

- カードの使用に明確な理由（アフォーダンス、比較、インタラクション境界）があること
- スペーシングとアラインメントで代替できないか検討されていること
- カードのネストが存在しないこと

## 深度とエレベーション

### セマンティック z-index 階層

z-index をマジックナンバーで管理するのではなく、セマンティックな階層で定義する。

```css
:root {
  --z-base: 0;
  --z-dropdown: 100;
  --z-sticky: 200;
  --z-modal: 300;
  --z-toast: 400;
}
```

**各階層の用途：**

| 階層 | 値 | 用途 |
|---|---|---|
| `base` | 0 | 通常のコンテンツ |
| `dropdown` | 100 | ドロップダウンメニュー、ポップオーバー |
| `sticky` | 200 | スティッキーヘッダー、フローティングボタン |
| `modal` | 300 | モーダルダイアログ、オーバーレイ |
| `toast` | 400 | トースト通知、スナックバー |

### シャドウの設計

シャドウは**微細（subtle）**にする。過剰なシャドウはUIを重たくする。

```css
/* 推奨：微細なシャドウ */
--shadow-sm: 0 1px 2px oklch(0% 0 0 / 0.05);
--shadow-md: 0 4px 6px oklch(0% 0 0 / 0.07);
--shadow-lg: 0 10px 15px oklch(0% 0 0 / 0.1);

/* 非推奨：過剰なシャドウ */
--shadow-heavy: 0 10px 30px rgba(0, 0, 0, 0.3);
```

### ダークモードでの深度表現

ダークモードではシャドウが見えにくいため、
**面の明度を上げることで深度を表現する**。

```css
/* ダークモードの深度表現 */
--surface-base:     oklch(15% 0.01 250);  /* 最背面 */
--surface-elevated: oklch(20% 0.01 250);  /* 浮いた面 */
--surface-overlay:  oklch(25% 0.01 250);  /* モーダル・ドロワー */
```

### 判断基準

- z-index がセマンティックトークンで管理されていること
- シャドウの透明度が 0.1 以下を基準にしていること
- ダークモードで影だけに依存した深度表現になっていないこと

## 判断に迷いやすいポイント

### 厳密グリッド vs 有機的レイアウト

**トレードオフ：** 秩序と予測可能性 vs 自然さと独自性

**判断軸：**
1. アプリUI・管理画面 → 厳密グリッドが適切（ユーザーは効率を求める）
2. マーケティング・ブランドサイト → 有機的レイアウトで個性を出せる
3. 両者を混在させる場合は、セクション単位で使い分ける

### カード vs オープンレイアウト

**トレードオフ：** 明確な境界 vs 開放感

**判断軸：**
1. 要素がクリック可能な単位か → カードが適切
2. スペーシングとアラインメントで十分にグルーピングできるか → オープンレイアウトが適切
3. 「なんとなくカードで囲む」は判断の放棄である

**判断例：**
- 商品一覧（クリックして詳細へ遷移）→ カード
- ダッシュボードの統計セクション → 余白とアラインメントで十分な場合が多い
- 設定画面のフォームグループ → セクション見出し + 余白で十分

### 数学的 vs 光学的スペーシング

**トレードオフ：** 実装の一貫性 vs 視覚的な正確さ

**判断軸：**
1. グリッドやスペーシングトークンは数学的に正確に保つ
2. 個別の要素（アイコン、テキスト）の配置は光学的に調整する
3. 全体構造は数学的、ディテールは光学的、という使い分けが実用的である

## よくある失敗パターン

### すべてをカードで包む

- **問題**：情報の区切りをすべてカードの枠線やシャドウで表現する。画面がカードだらけになり、階層感が失われる
- **改善**：スペーシングとアラインメントで十分にグルーピングできるか検討する。カードは明確なアフォーダンスが必要な場合に限定する

### カードのネスト

- **問題**：カード内にカードを配置する。視覚的な階層が崩壊し、インタラクション境界が曖昧になる
- **改善**：内部の情報構造はセクション分け（余白・区切り線）で表現する

### 同一カードグリッドの繰り返し

- **問題**：ページ全体が同じサイズ・同じ構造のカードグリッドで埋められ、単調になる
- **改善**：カードのサイズやレイアウトにバリエーションを持たせる。重要なカードを大きくする、フィーチャーカードを差し込むなど

### 全中央揃え

- **問題**：すべてのテキストとコンテンツを中央揃えにする。特に複数行のテキストの中央揃えは読みにくい
- **改善**：テキストは**左揃え**を基本とする。中央揃えは見出しや短いキャッチコピーに限定する。非対称レイアウト（左揃え + 右側余白）の方がデザインされた印象を与える

### 均一スペーシング（リズムなし）

- **問題**：すべての要素間に同じ余白が適用され、情報のグルーピングや優先度が伝わらない
- **改善**：関連する要素間は狭く、無関係な要素間は広くする。スペーシングスケールを活用してリズムを作る

### 固定幅レイアウト

- **問題**：コンテナやカードが固定幅（`width: 300px`）で定義され、レスポンシブに対応しない
- **改善**：`minmax()`, `auto-fit`, パーセンテージ、`clamp()` を使用して可変幅にする。固定幅はアイコンやアバターなど本質的に固定サイズの要素のみに限定する

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `arrange-ui` — レイアウト調整時のグリッド・スペーシング・視覚階層の判断に参照
- `design-ui` — UI設計時のグリッド・余白設計に参照
- `implement-ui` — UI実装時のCSS レイアウト実装に参照
- `boost-ui` — 視覚的インパクト強化時の視覚階層・深度設計に参照
- `calm-ui` — 視覚的ノイズ軽減時のスペーシング・カード使用判断に参照
- `adapt-ui` — レスポンシブ適応時のコンテナクエリ・自己調整グリッドに参照
- `extract-ui` — トークン抽出時のスペーシングトークン設計に参照
- `typeset-ui` — タイポグラフィ設定時の垂直リズム・視覚階層との関連で参照
- タイポグラフィとの関連は `reference/typography.md` を併せて参照する
- デザイントークンの詳細は `reference/design-tokens.md` を併せて参照する
