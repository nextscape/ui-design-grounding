# DESIGN.md ゲート

コマンドスキルが、プロジェクトの **DESIGN.md（視覚的アイデンティティの憲法）を必ず通る** ようにするための共通プロトコル。

対象のコマンドスキル（下記の**適用区分表**に挙げたもの。DESIGN.md を生成・抽出する側＝`init-design` / `scan-ui` / `extract-ui` は除く）はこのファイルを MANDATORY PREPARATION で参照し、手順の冒頭で **前段ゲート**、（値を動かすスキルは）修正完了後に **後段ゲート** を実施する。これにより「DESIGN.md があるのに参照せず実装してしまう」「修正で値を変えたのに DESIGN.md が取り残される」という双方向の乖離を防ぐ。

ゲートの持ち方は層で変わる。**第1層（考える/作る/直す/評価）は前段ゲートのみ**を持つ（修正は第2層へ委譲し、値の最終確定・乖離検出は委譲先が担う）。**値を実際に動かす実働層（第2層・配色・仕上げ）は前段＋後段ゲート**を持つ。

---

## 前段ゲート（基準の読み込み）— 手順の最初に必ず実施

1. プロジェクトルート（およびその近傍）に **DESIGN.md が存在するか** を確認する。

2. **存在する場合**:
   - front matter のデザイントークン（`colors` / `typography` / `rounded` / `spacing` / `components` — 正規キーは `design-md-spec.md` を参照）と、本文の設計指針・規約（影・モーション・ブレイクポイント・用語など、front matter ではなく散文/任意セクションで定義される観点を含む）を読み込む。
   - これらを **リファレンス（`reference/`）よりも優先する、プロジェクト固有の基準（source of truth）** として扱う。リファレンスは DESIGN.md が沈黙している領域の補完として使う。
   - 以降の診断・修正は「**DESIGN.md に定義された値・規約に照らして**」行う。
   - 既存トークンで表現できる変更は、**新しい値を持ち込まず既存トークンを使う**。

3. **存在しない、または対象領域が未定義の場合**:
   - リファレンスを基準として作業を進める。
   - 「基準が未整備である」ことを明示し、`/init-design`（外部サイトから逆算するなら `/scan-ui`）での整備を提案する。
   - 基準なしに「問題なし」と断定しない。

---

## 後段ゲート（乖離の検出と誘導）— 修正完了後に必ず実施

> 第1層（`design` / `implement` / `refine` / `audit` / `score`）は値の最終確定を第2層へ委譲する（または実装を変更しない）ため、後段ゲートは不要（前段のみ）。後段は値を動かす実働層（第2層・`recolor-ui` / `polish-ui`）が担う。

**S0. 最小自己波及チェック（実働層）**: 乖離検出の前に、今回の修正が**自分の観点の外側**を壊していないかを最小限で確認する。典型例: タイポ変更 → 行長・垂直リズム／色変更 → コントラスト・on-color ペア／余白変更 → 視覚階層。壊している場合は、その観点も直すか、第1層オーケストレーター（`refine` / `implement`）経由ならその**横断波及判定**に委ねる。直接呼びの場合はこの自己チェックが安全網になる。

以下は DESIGN.md との乖離検出と誘導:

1. 今回の修正が、DESIGN.md に定義された **トークン水準・規約**（色・タイポグラフィ・余白・角丸・影・モーション・ブレイクポイント・用語など）を **変更したか** を判定する。

2. **変更した場合**:
   - 「**DESIGN.md と実装の間に乖離が生じた**」ことを明示し、どのトークン／規約が **どの値から どの値へ** 変わったかを列挙する。
   - 反映先へ誘導する:
     - **色**（パレット・コントラスト・on-color）→ `/recolor-ui`
     - **それ以外**（タイポ・余白・角丸・影・モーション・ブレイクポイント・用語など）→ `/init-design`
   - **このスキルは DESIGN.md を自動では書き換えない。** 憲法の更新は人間の承認のもと、上記スキルで行う。

3. **DESIGN.md が存在しない場合**:
   - 今回確定した値が再利用価値を持つなら、`/init-design` での基準化を提案する（任意）。

---

## スキル別の適用区分

| 区分 | スキル | 前段 | 後段 |
|------|--------|:---:|:---:|
| 第1層・考える | `design-ui` | ✓ | —（構造設計。DESIGN.md を制約として読むが書かない） |
| 第1層・作る | `implement-ui` | ✓ | —（観点横断で第2層へ委譲。値の最終確定・乖離検出は委譲先が担う） |
| 第1層・直す | `refine-ui` | ✓ | —（観点ベースで診断し第2層へ委譲。後段は委譲先が担う） |
| 第1層・評価 | `audit-ui` `score-ui` `legibility-ui` | ✓ | —（実装を変更しない） |
| 第1層・基準化 | `init-design` `scan-ui` | — | —（DESIGN.md そのものを生成・更新する側） |
| 第2層・実働 | `boost-ui` `calm-ui` `typeset-ui` `animate-ui` `arrange-ui` `slim-ui` `clarify-ui` `guard-ui` `adapt-ui` `optimize-ui` | ✓ | ✓ |
| 配色（実働） | `recolor-ui` | ✓ | ✓（色は本スキル自身で DESIGN.md を更新） |
| 仕上げ（実働） | `polish-ui` | ✓ | ✓ |
| 抽出 | `extract-ui` | — | —（コード→コンポーネント/トークン抽出。DESIGN.md は生成側） |

> **後段（乖離検出）は値を実際に動かす実働層（第2層・`recolor-ui` / `polish-ui`）にのみ置く。** 第1層オーケストレーター（`design` / `implement` / `refine`）は前段のみを持ち、修正は第2層へ委譲するため後段は委譲先が担う（二重の乖離検出を避ける）。`recolor-ui` は色について前段（読込）・後段（更新）を本スキル内で完結させる。`polish-ui` は最終仕上げで値を動かしうるため、後段で乖離を検出して誘導する（自動書き換えはしない）。
