**タイポグラフィの判断基準と実践的な指針**を提供する。

文脈と制約に応じた判断ができるように基準を整理する。

## 垂直リズム

垂直リズムとは、テキストと余白の垂直方向の間隔をベースライン単位で統一し、
画面全体にリズム感と秩序を生み出す設計手法である。

### ベースライン単位の考え方

`line-height` をすべての垂直余白の基本単位とする。

**例：**
- body text の `line-height: 24px` を基本単位とする
- セクション間余白：`24px` の倍数（24px, 48px, 72px, 96px）
- 要素間余白：`24px` または `12px`（半分の値も許容）

```css
:root {
  --baseline: 1.5rem; /* 24px（body 16px × 1.5） */
}

h2 {
  margin-top: calc(var(--baseline) * 3);  /* 72px */
  margin-bottom: var(--baseline);          /* 24px */
}

p {
  margin-bottom: var(--baseline);          /* 24px */
}
```

### 判断基準

- すべての垂直方向の余白がベースライン単位の倍数であること
- 見出し上の余白は見出し下の余白より大きくする（グルーピング原則）
- 関連する要素間は狭く、無関係な要素間は広くする
- ベースライン単位の半分（`0.5 × baseline`）は許容するが、それ以下の端数は避ける

## モジュラースケール

タイプスケールとは、見出し・本文・補助テキストなどのフォントサイズを
数学的な比率で段階化したものである。

### 5段階に制限する

サイズの段階は **5段階** に制限する。それ以上は視覚的な差異が識別しにくくなる。

| トークン名 | 用途 | 比率 1.25 (Major Third) | 比率 1.333 (Perfect Fourth) | 比率 1.5 (Perfect Fifth) |
|---|---|---|---|---|
| `text-xs` | 補助テキスト、キャプション | 0.8rem (12.8px) | 0.75rem (12px) | 0.667rem (10.7px) |
| `text-sm` | セカンダリテキスト | 0.9rem (14.4px) | 0.875rem (14px) | 0.833rem (13.3px) |
| `text-base` | 本文テキスト | 1rem (16px) | 1rem (16px) | 1rem (16px) |
| `text-lg` | セクション見出し | 1.25rem (20px) | 1.333rem (21.3px) | 1.5rem (24px) |
| `text-xl+` | ページ見出し、ヒーロー | 1.563rem (25px) | 1.777rem (28.4px) | 2.25rem (36px) |

### 比率の選び方

- **1.25 (Major Third)**：コンパクトなUI、アプリ画面向き。差が小さく落ち着いた印象
- **1.333 (Perfect Fourth)**：汎用的。アプリにもコンテンツにも使える
- **1.5 (Perfect Fifth)**：コンテンツ主体のページ向き。見出しと本文の差が大きい

### 判断基準

- 隣接するサイズの差が **視覚的に明確に識別できる**こと
- サイズ差が小さすぎる段階が2つ以上あれば、スケールを減らすか比率を変更する
- 6段階以上が必要と感じたら、サイズではなくウェイトや色で階層を表現することを検討する

## 可読性

### 行長の制限

行が長すぎると視線の移動距離が増え、次の行の先頭に戻る際に行を見失いやすくなる。

**基本ルール：**
```css
p, .prose {
  max-width: 65ch; /* 約65文字幅 */
}
```

- `65ch` はアルファベット基準の推奨値である
- 日本語テキストでは `40ch`〜`50ch` が適切な場合もある
- カード内やサイドバーなど狭い領域では自然に制限されるため、追加指定は不要

### 行長と行間の関係

行長と行間は**逆相関**の関係にある。

| 行長 | 推奨 line-height |
|---|---|
| 短い（~45ch） | 1.4〜1.5 |
| 中程度（45ch〜65ch） | 1.5〜1.6 |
| 長い（65ch〜） | 1.6〜1.8 |

**理由：** 行が長いほど、次の行頭に戻る際の視線移動が大きくなる。行間を広げることで行の識別がしやすくなる。

### ダーク背景での調整

ダーク背景では明るいテキストが膨張して見えるため（ハレーション効果）、
`line-height` を **+0.05〜0.1** 広げると可読性が向上する。

```css
/* ライトモード */
body {
  line-height: 1.5;
}

/* ダークモード */
@media (prefers-color-scheme: dark) {
  body {
    line-height: 1.6;
  }
}
```

### 判断基準

- 本文テキストの行長が `65ch` を超えていないこと
- 行長に応じた `line-height` が設定されていること
- ダークモードで `line-height` の調整を検討していること

## フォント選定

### 使い古されたフォントの回避

以下のフォントは広く使われすぎており、視覚的な個性や差別化に貢献しない。

**避けるべきフォント：**
- Inter
- Roboto
- Arial
- Open Sans
- システムデフォルト（差別化が不要な場合は許容）

**代替候補（サンセリフ）：**
- Instrument Sans
- Plus Jakarta Sans
- Outfit
- Onest
- Figtree

**代替候補（セリフ）：**
- Fraunces
- Newsreader

### システムフォント vs カスタムフォント

**システムフォントの利点：**
- フォント読み込みゼロ（パフォーマンス最良）
- レイアウトシフトなし
- OSのネイティブな見た目に馴染む

**カスタムフォントの利点：**
- ブランドの視覚的アイデンティティを確立できる
- プラットフォーム間で一貫した見た目を実現できる

### フォントペアリング

**良いペアリングの原則：**
- **コントラストを複数の軸で作る**：セリフ + サンセリフ、ジオメトリック + ヒューマニスト、コンデンス + ワイド
- 1つのファミリー内のウェイト違いだけで十分な場合が多い

**禁止パターン：**
- **似ているが同一でないフォント**のペアリング
  - 例：Inter + Roboto（どちらもネオグロテスク）
  - コントラストが生まれず、「間違えた」ように見える
- 3つ以上のフォントファミリーの同時使用

### 判断基準

- フォント選定の根拠が「デフォルトだから」ではないこと
- ペアリングに明確なコントラスト軸があること
- 使用フォントファミリー数が2以下であること
- ブランドの差別化が不要なプロジェクト（内部ツール等）ではシステムフォントが最適

## Webフォント性能

### font-display 戦略

```css
@font-face {
  font-family: 'BrandFont';
  src: url('/fonts/brand.woff2') format('woff2');
  font-display: swap; /* テキストを即座に表示し、フォント読み込み後に差し替え */
}
```

- `swap`：テキストをフォールバックで即座に表示する。もっとも一般的な選択
- `optional`：高速接続でのみカスタムフォントを適用する。性能重視の場合に使用

### メトリクスマッチング

フォールバックフォントとカスタムフォントのメトリクスを揃えることで、
フォント読み込み時のレイアウトシフトを最小化する。

```css
@font-face {
  font-family: 'BrandFont-Fallback';
  src: local('Arial');
  size-adjust: 100.5%;
  ascent-override: 95%;
  descent-override: 22%;
  line-gap-override: 0%;
}

body {
  font-family: 'BrandFont', 'BrandFont-Fallback', sans-serif;
}
```

**各プロパティの役割：**
- `size-adjust`：フォールバックの文字幅をカスタムフォントに合わせる
- `ascent-override`：アセンダー（文字上部）の高さを合わせる
- `descent-override`：ディセンダー（文字下部）の高さを合わせる
- `line-gap-override`：行間ギャップを合わせる

### 判断基準

- `font-display` が指定されていること（未指定の場合、ブラウザによってはFOITが発生する）
- レイアウトシフトが最小化されていること
- フォントファイルは `woff2` 形式であること

## Fluid Type vs Fixed Scale

### 使い分けの原則

| ページの性質 | 推奨アプローチ | 理由 |
|---|---|---|
| マーケティング・LP・コンテンツページ | Fluid Type（`clamp()`） | ビューポートに応じた滑らかなスケーリングが期待される |
| アプリUI・管理画面・ダッシュボード | Fixed Scale（固定 `rem`） | 予測可能なレイアウトとコンポーネントの安定性が優先される |

**Fluid Type の実装例：**
```css
h1 {
  font-size: clamp(1.5rem, 1rem + 2vw, 3rem);
}
```

**Fixed Scale が適切な理由（アプリUI）：**
- Material Design、Shopify Polaris、GitHub Primer、IBM Carbon など主要デザインシステムはいずれも Fluid Type を採用していない
- コンポーネントのサイズが予測可能であることが、アプリUIの安定性に直結する
- ブレークポイントでのステップ変更（レスポンシブ対応）で十分である

### 判断基準

- コンテンツ主体のページでは `clamp()` の使用を検討する
- アプリUIでは固定 `rem` を基本とし、ブレークポイントで切り替える
- 両者を混在させる場合は、適用範囲を明確にする

## OpenType機能

フォントが持つ OpenType 機能を活用することで、
細部の読みやすさとプロフェッショナルな仕上がりを実現する。

### 推奨する OpenType 機能

| 機能 | CSSプロパティ | 用途 |
|---|---|---|
| `tabular-nums` | `font-variant-numeric: tabular-nums` | データテーブルの数値揃え |
| `diagonal-fractions` | `font-variant-numeric: diagonal-fractions` | レシピ、寸法表記 |
| `all-small-caps` | `font-variant-caps: all-small-caps` | 略語（HTML, CSS, API 等） |
| `ordinal` | `font-variant-numeric: ordinal` | 序数表記（1st, 2nd 等） |

### コードでのリガチャ無効化

コードブロックやターミナル表示では、リガチャは**誤読の原因**になるため無効化する。

```css
code, pre, .monospace {
  font-variant-ligatures: none;
  font-feature-settings: 'liga' 0, 'calt' 0;
}
```

### 判断基準

- データテーブルに `tabular-nums` が適用されていること
- コードブロックでリガチャが無効化されていること
- 使用フォントが該当の OpenType 機能をサポートしていることを事前に確認する

## アクセシビリティ

### 単位

フォントサイズは `rem` または `em` で指定する。`px` は使用しない。

**理由：** ユーザーがブラウザのフォントサイズ設定を変更した際に、`px` 指定では反映されない。

```css
/* 推奨 */
body { font-size: 1rem; }
h1 { font-size: 2rem; }

/* 非推奨 */
body { font-size: 16px; }
h1 { font-size: 32px; }
```

### 最小フォントサイズ

- body text の最小サイズは **16px**（`1rem`）相当とする
- これより小さいサイズは、キャプションや注釈など限定的な用途に限る
- `0.75rem`（12px 相当）を下回るサイズは使用しない

### タップターゲット

- テキストリンクやインラインボタンのタップ領域は **44px** 以上を確保する
- `line-height` と `padding` の組み合わせで自然に確保する

### ズーム無効化の禁止

```html
<!-- 禁止 -->
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no">
<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1">

<!-- 正しい -->
<meta name="viewport" content="width=device-width, initial-scale=1">
```

### 判断基準

- フォントサイズが `rem` / `em` で指定されていること
- body text が `1rem`（16px 相当）以上であること
- タップターゲットが 44px 以上であること
- ビューポート設定でズームが無効化されていないこと

## 判断に迷いやすいポイント

### システムフォント vs カスタムフォント

**トレードオフ：** 性能 vs 視覚的個性

**判断軸：**
1. ブランドの差別化がプロジェクトの要件か
2. 初回表示速度（LCP）への影響が許容範囲か
3. プラットフォーム間の一貫性が求められるか

**判断例：**
- コーポレートサイト・プロダクト → カスタムフォント（ブランド優先）
- 内部ツール・管理画面 → システムフォント（性能優先）
- パフォーマンスが最重要なLP → システムフォント + CSSで個性を出す

### 一貫性 vs 表現力

**トレードオフ：** フォントファミリー数の制限 vs デザインの豊かさ

**判断軸：**
1. 1ファミリーのウェイト違いで十分な階層が作れるか
2. 2つ目のファミリーに明確なコントラスト軸があるか
3. 3つ目が本当に必要か（ほとんどの場合、不要）

### Fluid Type vs Fixed Scale

**トレードオフ：** 滑らかなスケーリング vs 予測可能なレイアウト

**判断軸：**
1. ページの性質（コンテンツ主体 vs アプリUI）
2. コンポーネントのサイズ安定性が重要か
3. デザインシステムとの整合性

### 垂直リズムの厳密さ

**トレードオフ：** 数学的な正確さ vs 実装コスト

**判断軸：**
1. 完璧なベースライングリッドは実装コストが高い
2. 「近似的なベースライン揃え」でも十分なリズム感が得られる場合が多い
3. ベースラインからの逸脱が視覚的に気になるレベルかどうか

## よくある失敗パターン

### モノスペースフォントの安易な使用

- **問題**：「技術的な雰囲気」を出すためにモノスペースフォントを本文や見出しに使用する。可読性が低下し、テンプレート感が出る
- **改善**：モノスペースはコードブロックとデータ表示に限定する。技術的な印象はフォント以外の要素（レイアウト、カラー）で表現する

### サイズ段階が多すぎて差が小さい

- **問題**：12px, 13px, 14px, 15px, 16px のように近接するサイズを複数定義する。ユーザーもデベロッパーも差異を認識できない
- **改善**：モジュラースケールで5段階に制限する。隣接サイズは視覚的に明確に区別できる差を持たせる

### 垂直リズムの無視

- **問題**：要素ごとにバラバラなマージンが設定され、ページ全体のリズム感がない
- **改善**：ベースライン単位の倍数で余白を統一する。スペーシングトークンと組み合わせる

### 見出し上の大きな角丸アイコン

- **問題**：見出しの上に大きな角丸アイコンを配置するレイアウト。テンプレートサイトに多用されており、独自性を損なう
- **改善**：アイコンが情報伝達に必要か再検討する。必要な場合はサイズと配置を抑制する

### 行長の未制限

- **問題**：ワイドスクリーンでテキストが画面幅いっぱいに広がり、読みづらくなる
- **改善**：`max-width: 65ch` を本文コンテナに適用する

### font-display 未指定

- **問題**：カスタムフォント読み込み中にテキストが表示されない（FOIT）
- **改善**：`font-display: swap` を指定し、フォールバックフォントで即座に表示する

## このreferenceの使い方

以下のコマンドスキルから参照される:
- `typeset-ui` — タイポグラフィ設定時のフォント選定・スケール・垂直リズムの判断に参照
- `design-ui` — UI設計時のフォント・サイズ設計に参照
- `implement-ui` — UI実装時のCSS タイポグラフィ実装に参照
- `boost-ui` — 視覚的インパクト強化時のタイポグラフィ階層設計に参照
- `calm-ui` — 視覚的ノイズ軽減時のタイポグラフィ簡素化に参照
- `score-ui` — UI品質スコアリングのタイポグラフィ評価時に参照
- `arrange-ui` — レイアウト調整時の垂直リズム・行長設計に参照
**関連リファレンス:**
- `color-system.md` — テキスト色・コントラスト比・ダークモードでのウェイト調整
- `accessibility.md` — フォントサイズ・行間のアクセシビリティ基準
- `spatial-layout.md` — 垂直リズムとグリッドシステムとの連携
- `anti-patterns.md` — 使い古されたフォント・モノスペース安易使用等のアンチパターン
