## このドキュメントの役割
UI/UXの設計・実装における**タイポグラフィの判断基準と実践指針**。フォント選定・サイズ設計・垂直リズム・可読性・性能の観点で、文脈と制約に応じた基準を整理する。

## 垂直リズム

垂直間隔をベースライン単位で統一し、画面にリズムと秩序を生む手法。`line-height` を全垂直余白の基本単位とする。

- body の `line-height: 24px` を基本単位に
- セクション間：`24px` の倍数（24/48/72/96px）
- 要素間：`24px` または半分の `12px`

```css
:root {
  --baseline: 1.5rem; /* 24px（body 16px × 1.5） */
}
h2 {
  margin-top: calc(var(--baseline) * 3);  /* 72px */
  margin-bottom: var(--baseline);          /* 24px */
}
```

### 判断基準

- すべての垂直余白がベースライン単位の倍数であること
- 見出し上の余白は見出し下より大きく（グルーピング原則）
- 関連要素間は狭く、無関係な要素間は広く
- 半分（`0.5 × baseline`）までは許容、それ以下の端数は避ける

## モジュラースケール

フォントサイズを数学的比率で段階化したもの。段階は **5段階** に制限する（それ以上は視覚差が識別しにくい）。

| トークン名 | 用途 | 比率 1.25 (Major Third) | 比率 1.333 (Perfect Fourth) | 比率 1.5 (Perfect Fifth) |
|---|---|---|---|---|
| `text-xs` | 補助テキスト、キャプション | 0.8rem (12.8px) | 0.75rem (12px) | 0.667rem (10.7px) |
| `text-sm` | セカンダリテキスト | 0.9rem (14.4px) | 0.875rem (14px) | 0.833rem (13.3px) |
| `text-base` | 本文テキスト | 1rem (16px) | 1rem (16px) | 1rem (16px) |
| `text-lg` | セクション見出し | 1.25rem (20px) | 1.333rem (21.3px) | 1.5rem (24px) |
| `text-xl+` | ページ見出し、ヒーロー | 1.563rem (25px) | 1.777rem (28.4px) | 2.25rem (36px) |

### 比率の選び方

- **1.25 (Major Third)**：コンパクトなUI・アプリ画面向き。差が小さく落ち着いた印象
- **1.333 (Perfect Fourth)**：汎用的。アプリにもコンテンツにも
- **1.5 (Perfect Fifth)**：コンテンツ主体のページ向き。見出しと本文の差が大きい

### 判断基準

- 隣接サイズの差が**視覚的に明確に識別できる**こと
- 差が小さすぎる段階が2つ以上あれば、段階を減らすか比率を変更
- 6段階以上が必要なら、サイズではなくウェイトや色で階層を表現

## 可読性

### 行長の制限

行が長すぎると視線移動が増え、行頭に戻る際に行を見失う。

```css
p, .prose { max-width: 65ch; /* 約65文字幅 */ }
```

- `65ch` はアルファベット基準の推奨値
- 日本語では `40ch`〜`50ch` が適切な場合もある
- カード内やサイドバーなど狭い領域は自然に制限されるため追加指定不要

### 行長と行間の関係

行長と行間は**逆相関**。行が長いほど行頭復帰の視線移動が大きくなるため、行間を広げて行を識別しやすくする。

| 行長 | 推奨 line-height |
|---|---|
| 短い（~45ch） | 1.4〜1.5 |
| 中程度（45ch〜65ch） | 1.5〜1.6 |
| 長い（65ch〜） | 1.6〜1.8 |

### ダーク背景での調整

ダーク背景では明るいテキストが膨張して見える（ハレーション）ため、`line-height` を **+0.05〜0.1** 広げると可読性が向上する。

```css
body { line-height: 1.5; }
@media (prefers-color-scheme: dark) {
  body { line-height: 1.6; }
}
```

### 判断基準

- 本文の行長が `65ch` を超えていないこと
- 行長に応じた `line-height` が設定されていること
- ダークモードで `line-height` 調整を検討していること

## フォント選定

### 使い古されたフォントの回避

以下は使われすぎており、個性・差別化に貢献しない。

**避ける：** Inter / Roboto / Arial / Open Sans / システムデフォルト（差別化が不要なら許容）

**代替（サンセリフ）：** Instrument Sans / Plus Jakarta Sans / Outfit / Onest / Figtree

**代替（セリフ）：** Fraunces / Newsreader

### システムフォント vs カスタムフォント

- **システム**：読み込みゼロ（性能最良）、レイアウトシフトなし、OSネイティブに馴染む
- **カスタム**：ブランドアイデンティティを確立、プラットフォーム間で一貫した見た目

### フォントペアリング

- **コントラストを複数軸で作る**：セリフ + サンセリフ、ジオメトリック + ヒューマニスト、コンデンス + ワイド
- 1ファミリー内のウェイト違いだけで十分な場合が多い

**禁止：**
- **似ているが同一でない**フォントのペアリング（例：Inter + Roboto。どちらもネオグロテスクでコントラストが生まれず「間違えた」ように見える）
- 3つ以上のファミリーの同時使用

### 判断基準

- フォント選定の根拠が「デフォルトだから」ではないこと
- ペアリングに明確なコントラスト軸があること
- 使用ファミリー数が2以下であること
- 差別化が不要なプロジェクト（内部ツール等）ではシステムフォントが最適

## Webフォント性能

### font-display 戦略

```css
@font-face {
  font-family: 'BrandFont';
  src: url('/fonts/brand.woff2') format('woff2');
  font-display: swap; /* フォールバックで即表示し、読み込み後に差し替え */
}
```

- `swap`：フォールバックで即座に表示。もっとも一般的
- `optional`：高速接続でのみカスタムフォントを適用。性能重視向け

### メトリクスマッチング

フォールバックとカスタムフォントのメトリクスを揃え、読み込み時のレイアウトシフトを最小化する。

```css
@font-face {
  font-family: 'BrandFont-Fallback';
  src: local('Arial');
  size-adjust: 100.5%;     /* 文字幅を合わせる */
  ascent-override: 95%;    /* アセンダー高を合わせる */
  descent-override: 22%;   /* ディセンダー高を合わせる */
  line-gap-override: 0%;   /* 行間ギャップを合わせる */
}
body {
  font-family: 'BrandFont', 'BrandFont-Fallback', sans-serif;
}
```

### 判断基準

- `font-display` が指定されていること（未指定だとブラウザによりFOIT発生）
- レイアウトシフトが最小化されていること
- フォントファイルは `woff2` 形式であること

## Fluid Type vs Fixed Scale

| ページの性質 | 推奨 | 理由 |
|---|---|---|
| マーケティング・LP・コンテンツ | Fluid Type（`clamp()`） | ビューポートに応じた滑らかなスケーリングが期待される |
| アプリUI・管理画面・ダッシュボード | Fixed Scale（固定 `rem`） | 予測可能なレイアウトとコンポーネント安定性を優先 |

**Fluid Type の例：**
```css
h1 { font-size: clamp(1.5rem, 1rem + 2vw, 3rem); }
```

**アプリUIで Fixed Scale が適切な理由：**
- Material Design、Shopify Polaris、GitHub Primer、IBM Carbon など主要デザインシステムはいずれも Fluid Type を採用していない
- コンポーネントサイズの予測可能性がアプリUIの安定性に直結する
- ブレークポイントでのステップ変更で十分

### 判断基準

- コンテンツ主体のページでは `clamp()` を検討
- アプリUIでは固定 `rem` を基本とし、ブレークポイントで切り替える
- 混在させる場合は適用範囲を明確にする

## OpenType機能

細部の読みやすさとプロフェッショナルな仕上がりを実現する。

### 推奨機能

| 機能 | CSSプロパティ | 用途 |
|---|---|---|
| `tabular-nums` | `font-variant-numeric: tabular-nums` | データテーブルの数値揃え |
| `diagonal-fractions` | `font-variant-numeric: diagonal-fractions` | レシピ、寸法表記 |
| `all-small-caps` | `font-variant-caps: all-small-caps` | 略語（HTML, CSS, API 等） |
| `ordinal` | `font-variant-numeric: ordinal` | 序数表記（1st, 2nd 等） |

### コードでのリガチャ無効化

コードブロックやターミナル表示ではリガチャが**誤読の原因**になるため無効化する。

```css
code, pre, .monospace {
  font-variant-ligatures: none;
  font-feature-settings: 'liga' 0, 'calt' 0;
}
```

### 判断基準

- データテーブルに `tabular-nums` が適用されていること
- コードブロックでリガチャが無効化されていること
- 使用フォントが該当機能をサポートしているか事前確認すること

## アクセシビリティ

### 単位

フォントサイズは `rem` / `em` で指定し、`px` は使わない。`px` 指定だとユーザーのブラウザフォントサイズ設定が反映されないため。

```css
body { font-size: 1rem; }  /* 推奨 */
h1 { font-size: 2rem; }
/* 非推奨: body { font-size: 16px; } */
```

### 最小フォントサイズ

- body の最小は **16px**（`1rem`）相当
- それ未満はキャプションや注釈など限定用途のみ
- `0.75rem`（12px 相当）を下回るサイズは使用しない

### タップターゲット

- テキストリンク・インラインボタンのタップ領域は **44px** 以上を確保（`line-height` と `padding` の組み合わせで自然に）。詳細は accessibility.md

### ズーム無効化の禁止

```html
<!-- 禁止: user-scalable=no / maximum-scale=1 -->
<!-- 正しい -->
<meta name="viewport" content="width=device-width, initial-scale=1">
```

### 判断基準

- フォントサイズが `rem` / `em` 指定であること
- body が `1rem`（16px 相当）以上であること
- タップターゲットが 44px 以上であること（→ accessibility.md）
- ビューポートでズームが無効化されていないこと

## 判断に迷いやすいポイント

### システムフォント vs カスタムフォント

**トレードオフ：** 性能 vs 視覚的個性
**判断軸：** ①ブランド差別化が要件か ②初回表示速度（LCP）への影響が許容範囲か ③プラットフォーム間の一貫性が必要か
**例：** コーポレート/プロダクト→カスタム（ブランド優先）／ 内部ツール・管理画面→システム（性能優先）／ 性能最重要なLP→システム + CSSで個性

### 一貫性 vs 表現力

**トレードオフ：** ファミリー数の制限 vs デザインの豊かさ
**判断軸：** ①1ファミリーのウェイト違いで十分な階層が作れるか ②2つ目に明確なコントラスト軸があるか ③3つ目が本当に必要か（ほぼ不要）

### Fluid Type vs Fixed Scale

**トレードオフ：** 滑らかなスケーリング vs 予測可能なレイアウト
**判断軸：** ①ページの性質（コンテンツ主体 vs アプリUI） ②コンポーネントのサイズ安定性が重要か ③デザインシステムとの整合性

### 垂直リズムの厳密さ

**トレードオフ：** 数学的な正確さ vs 実装コスト
**判断軸：** ①完璧なベースライングリッドは実装コストが高い ②「近似的なベースライン揃え」でも十分なリズムが得られる場合が多い ③逸脱が視覚的に気になるレベルか

## よくある失敗パターン

### モノスペースフォントの安易な使用
- **問題**：「技術的雰囲気」目的で本文・見出しに使用し、可読性低下とテンプレート感を招く
- **改善**：モノスペースはコード・データ表示に限定。技術的印象はレイアウトやカラーで表現

### サイズ段階が多すぎて差が小さい
- **問題**：12/13/14/15/16px のように近接サイズを複数定義し、差異が認識できない
- **改善**：モジュラースケールで5段階に制限し、隣接サイズに明確な差を持たせる

### 垂直リズムの無視
- **問題**：要素ごとにバラバラなマージンでページ全体のリズムがない
- **改善**：ベースライン単位の倍数で余白を統一し、スペーシングトークンと組み合わせる

### 見出し上の大きな角丸アイコン
- **問題**：見出し上の大きな角丸アイコン配置。テンプレートサイトに多用され独自性を損なう
- **改善**：情報伝達に必要か再検討。必要ならサイズと配置を抑制する

### 行長の未制限
- **問題**：ワイドスクリーンでテキストが画面幅いっぱいに広がり読みづらい
- **改善**：本文コンテナに `max-width: 65ch` を適用

### font-display 未指定
- **問題**：カスタムフォント読み込み中にテキストが表示されない（FOIT）
- **改善**：`font-display: swap` でフォールバックを即座に表示
